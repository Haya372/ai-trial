# ADR作成スキル

## 目的

技術的意思決定の背景・選択肢・理由を、後から読んだ人が判断を再検証できる形で `docs/adr/` に残す。

## 手順

### ステップ 1: 既存ADRを確認する

`docs/adr/` 配下のADRのタイトルと「決定」を読み、今回の判断と同じテーマを扱うADRを探す。

- 同じテーマの承認済みADRがあり、その決定を変える場合: ステップ 4 の置き換え手順に従う
- 同じテーマの承認済みADRがあり、決定を変えずに補足する場合: 新規ADRを作らず、既存ADRに追記する
- 今回の判断が別の承認済みADRの決定と矛盾する場合: 書き始める前に矛盾点をPDMに提示し、どちらを優先するか合意する

### ステップ 2: ファイルを作成する

- 番号: `docs/adr/` 配下の最大番号 + 1 を3桁ゼロ埋めで使う
- ファイル名: `docs/adr/ADR-XXX-[英小文字ケバブケースのタイトル].md`（例: `ADR-033-session-token-hashing.md`）
- `docs/adr/template.md` をコピーして書き始める

### ステップ 3: テンプレートの各セクションを書く

`write-document` スキルに従って書く。セクションごとに以下を書く。

| セクション | 書く内容 |
|---|---|
| ステータス | セッション内で議論・合意した内容は「承認済」。合意が取れていない場合だけ「提案中」 |
| コンテキスト | 意思決定が必要になった背景・課題と、選択肢を評価する観点。前提にした既存ADRは番号で参照する |
| スコープ外 | 関連するが今回決めない判断。別ADRで決定済みのものはADR番号を併記する |
| 決定 | 採用した選択肢と、採用に伴う構造上のルール |
| 検討した選択肢 | 実際に比較した選択肢を、採用したものも含めて2つ以上書く。テンプレートの選択肢の数は比較した数に合わせて増減する |
| 決定理由 | コンテキストの評価観点に照らして、採用した選択肢が他より優れる理由 |
| 結果 | 採用によって生じる良い影響・悪い影響。悪い影響には対処方針も書く |

書くときの判断基準:

- コンテキストに現在の実装状態（「現時点では〜のみ」）を書かない。時間が経つと事実と食い違う
- 「なぜその構造を選んだか」はADRに書く。「どのステータスコードをいつ使うか」などの運用ルール・対応表は `docs/guidelines/` に書き、ADRからは参照だけを置く
- 「SSoT」などの技術ジャーゴンは使わず、「参照」「定義」など平易な表現にする
- gitignore対象・未コミットのファイルを参照しない（他の環境でリンク切れになる）

### ステップ 4: 既存ADRを置き換える場合は双方を更新する

- 旧ADRのステータスを `廃止（YYYY-MM-DD、[ADR-XXX](./ADR-XXX-xxx.md) により置き換え）` に変更する。日付は置き換えた日にする
- 新ADRのステータス行の下に `- 本ADRは [ADR-YYY](./ADR-YYY-yyy.md) を置き換える` を追加する
- 新ADRのコンテキストに、旧ADRの決定と再検討が必要になった状況変化を書く

### ステップ 5: 参照元を更新する

`grep -rn "ADR-YYY" docs .agents` で旧ADR（置き換えた場合）や関連ADRの参照箇所を探し、置き換え後のADRを参照すべき箇所を更新する。

### ステップ 6: lintを実行する

```bash
mise exec -- markdownlint-cli2 <変更したファイル>
```

## チェックリスト

- [ ] 同じテーマの既存ADRを確認し、新規作成・追記・置き換えのどれにするか決めたか
- [ ] 番号が既存ADRと重複していないか
- [ ] ステータスが合意状況と一致しているか
- [ ] 検討した選択肢が2つ以上あり、決定理由がコンテキストの評価観点と対応しているか
- [ ] 置き換えた場合、旧ADRのステータスと新ADRの置き換え表記の両方を更新したか
- [ ] `docs/guidelines/document-review-criteria.md` の観点を満たしているか
- [ ] markdownlintの指摘が0件か
