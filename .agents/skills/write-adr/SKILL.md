# ADR作成スキル

## 目的

技術的意思決定の背景・選択肢・理由を、後から読んだ人が判断を再検証できる形で `docs/adr/` に残す。

## 手順

### ステップ 1: 既存ADRを確認する

`docs/adr/` 配下のADRのタイトルと「決定」を読み、今回の判断と同じテーマを扱うADRを探す。

- 同じテーマの承認済みADRがあり、その決定を変える場合: 新しいADRを作成し、ステップ 4 の置き換え手順に従う
- 同じテーマの承認済みADRがあり、決定を変えずに補足する場合: 新しいADRを作成し、コンテキストで補足対象のADRを番号で参照する
- 今回の判断が別の承認済みADRの決定と矛盾する場合: 書き始める前に矛盾点をPDMに提示し、どちらを優先するか合意する

### ステップ 2: ファイルを作成する

- 番号: `docs/adr/` 配下の最大番号 + 1 を3桁ゼロ埋めで使う
- ファイル名: `docs/adr/ADR-XXX-[英小文字ケバブケースのタイトル].md`（例: `ADR-033-session-token-hashing.md`）
- `docs/adr/template.md` をコピーして書き始める

### ステップ 3: テンプレートの各セクションを書く

`write-document` スキルに従って書く。セクションごとに以下を書く。

| セクション | 書く内容 |
|---|---|
| ステータス | セッション内で議論・合意した内容は「承認済」。合意が取れていない場合だけ「提案中」 |
| コンテキスト | 意思決定が必要になった背景・課題と、選択肢を評価する観点。前提にした既存ADRは番号で参照する。背景はIssueを読まなくても分かるようにADR本文に書く |
| スコープ外 | 関連するが今回決めない判断。別ADRで決定済みのものはADR番号を併記する |
| 決定 | 採用した選択肢と、採用に伴う構造上のルール。「〜する場合は検討する」「後続Issueで決める」と先送りせず、やる・やらないまで決める。既存Issueの内容と矛盾した場合はADRの決定を優先し、Issue側を後から修正する |
| 検討した選択肢 | 実際に比較した選択肢を、採用したものも含めて2つ以上書く。テンプレートの選択肢の数は比較した数に合わせて増減する |
| 決定理由 | コンテキストの評価観点に照らして、採用した選択肢が他より優れる理由 |
| 検証結果 | 採用判断の根拠となる主張を実環境で確認した場合に、「決定理由」の後へセクションを追加し、検証手順と結果を書く。検証で解消できなかった点は「既知の制約」として書く。検証で判明した実装上の必須事項（必要な権限・失敗時の挙動など）は「決定」にも書く |
| 結果 | 採用によって生じる良い影響・悪い影響。悪い影響には対処方針も書く |

書くときの判断基準:

- 「ツールXでYができる」「Zは安全である」のような採用判断の根拠となる主張は、実際に動作を確認してから書く。確認できていない主張が残る場合はステータスを「提案中」にする
- コンテキストに現在の実装状態（「現時点では〜のみ」）を書かない。時間が経つと事実と食い違う
- 「なぜその構造を選んだか」はADRに書く。「どのステータスコードをいつ使うか」などの運用ルール・対応表は `docs/guidelines/` に書き、ADRからは参照だけを置く
- 「SSoT」などの技術ジャーゴンは使わず、「参照」「定義」など平易な表現にする
- gitignore対象・未コミットのファイルを参照しない（他の環境でリンク切れになる）
- 構成要素の配置・通信経路を説明する場合はmermaidで図示する。同種の構成要素は省略せずすべて描く（片方のコンテナだけにファイアウォールを描くと、もう片方は制限なしと読まれる）
- 環境ごとに値が変わる設定（例: `core.hooksPath` の値、ローカルのディレクトリ構成）は、具体的な値ではなく設定の意味で説明する
- セキュリティ上の保証を書く場合は、想定する脅威モデルを明示する。その保証が成り立たない経路（例: push後にCI・ホスト環境で実行される経路）は「既知の制約」として書き、影響範囲を根拠なく「〜に限られる」と書かない

### ステップ 4: 既存ADRを置き換える場合は双方を更新する

- 旧ADRのステータスを `廃止（YYYY-MM-DD、[ADR-XXX](./ADR-XXX-xxx.md) により置き換え）` に変更する。日付は置き換えた日にする
- 旧ADRで変更するのはステータス行だけにする。本文を書き換えると意思決定の履歴が失われる
- 新ADRのステータス行の下に `- 本ADRは [ADR-YYY](./ADR-YYY-yyy.md) を置き換える` を追加する
- 新ADRのコンテキストに、旧ADRの決定と再検討が必要になった状況変化を書く

### ステップ 5: 参照元を更新する

`git grep -n "ADR-YYY"` でリポジトリ全体（ドキュメント・スキル・Agent定義・コードコメント）から旧ADR（置き換えた場合）や関連ADRの参照箇所を探し、置き換え後のADRを参照すべき箇所を更新する。

### ステップ 6: lintを実行する

```bash
mise exec -- markdownlint-cli2 <変更したファイル>
```

## チェックリスト

- [ ] 同じテーマの既存ADRを確認し、置き換えにするかどうか決めたか
- [ ] 番号が既存ADRと重複していないか
- [ ] ステータスが合意状況と一致しているか
- [ ] Issueを読まなくてもADR単体で背景と決定が分かるか
- [ ] 「〜する場合は」「後続で決める」など、決定を先送りする表現が残っていないか
- [ ] 検討した選択肢が2つ以上あり、決定理由がコンテキストの評価観点と対応しているか
- [ ] 採用判断の根拠となる主張を実環境で確認したか
- [ ] 検証結果に書いた実装上の必須事項が「決定」にも書かれているか
- [ ] 置き換えた場合、旧ADRのステータスと新ADRの置き換え表記の両方を更新し、旧ADRの本文は変更していないか
- [ ] `docs/guidelines/document-review-criteria.md` の観点を満たしているか
- [ ] markdownlintの指摘が0件か
