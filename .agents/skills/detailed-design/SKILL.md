# 詳細設計スキル

## 目的

sub-issueの担当範囲を、バックエンド・フロントエンド双方の実装可能な技術設計に落とし込む。

```text
PRD作成 → Issue作成 → 仕様定義 → sub-issue起票 → [詳細設計 ← 今ここ] → TDD実装 → PRレビュー → マージ
```

仕様書（`docs/spec/`）の「設計」セクション（ドメインモデル・DB設計・API設計）を前提に、sub-issueに閉じるレイヤー内部の設計（UseCaseの構成・エラー定義・コンポーネント構成・画面など）を行う。

## 設計手順

### ステップ 1: Issue・仕様書・PRD確認

- sub-issueの設計メモから、担当する仕様書の設計要素を確認する
- 仕様書と `docs/prd/` 配下の対象PRDを読み、ゴール・要件・非目標・制約を把握する
- 仕様書・PRDから判断できない不明点だけをPDMに確認する
- 仕様書の設計（ドメインモデル・DB設計・API設計）を変更しないと実現できない場合は、設計を進めずに仕様書の変更案をPDMに提示し、再合意を得て仕様書を更新してから進める
- 成功指標を確認し、設計がそれを達成できるか意識する
- **関連PRDが存在しないchore/infra Issueの場合**: `docs/spec/`（PRD由来の機能仕様専用、`docs/spec/template.md` もPRD参照必須）は使わない。ライブラリ選定などの意思決定はステップ6のADRに残し、それ以外の実装詳細（配置構成・初期化手順など）はADR本文に収めるか、コミット不要なローカル設計メモとして実装者に直接引き継ぐ

### ステップ 2: アーキテクチャ設計

設計原則は `docs/guidelines/guidelines.md` を参照。

- コンポーネント・モジュールの責務を分割する（SOLID準拠）
- 依存関係の方向を整理する
- データフローとコンポーネント間の相互作用を図または箇条書きで明示する

### ステップ 2.5: ADRが必要な判断を洗い出す

設計を進める前に、(1) 今回の設計が既存の承認済みADRに違反していないかを確認し、(2) 既存ADRでカバーされていない技術的意思決定を洗い出す。

#### 既存ADRとの整合性確認

`docs/adr/` 配下の承認済みADR、特にレイヤー間の依存方向を規定するもの（例: ADR-022のCQRS方針 — Queryは書き込み系のRepositoryに依存せず、読み取り専用インターフェースに依存してReadModelを直接返す）に照らし、今回の設計が違反していないかを確認する。違反する設計になりそうな場合は、既存ADRに沿う形（例: Query側のUseCaseが別集約の書き込み用Repositoryに依存しないと実現できなさそうな場合は、そのデータ取得をQueryService側のクエリ自体（JOIN/UNION等）で表現できないか検討する）に設計を修正する。既存ADR自体の見直しが必要と判断した場合はPDMに提示し合意を得てから進める。

#### 新規ADRが必要な判断の洗い出し

以下は判断が必要になりやすい観点の例:

- DBのenum値管理方針（VARCHAR + アプリ定数 / PostgreSQL ENUM / CHECK制約 / マスターテーブル）
- エンティティの変更履歴管理方針（最新のみ / 監査ログ / 履歴テーブル）
- セッション管理方式（DBセッション / JWT）
- 外部サービス選定（メール送信 / ストレージ等）

判断が必要な項目を発見したら：

1. PDMに選択肢とトレードオフを提示する
2. 合意が得られたらADRを作成して設計に反映する
3. 今回のスコープ外（他の機能にまたがる横断的な判断等）なら、現在のIssueのsub-issueとして `chore: ADRを作成する - [判断テーマ]` を起票し、**設計作業を一時中断してPDMに報告する**
4. sub-issueが解決（ADR作成済み）になってから設計を再開する

### ステップ 3: バックエンド設計（必要な場合）

バックエンド設計指針は `docs/guidelines/design-guidelines.md` を参照。

- レイヤー設計（責務の分割）を決める
- 入力バリデーションのルールと適用箇所を定義する
- Value Object（VO）の設計: バリデーションルールを持つプリミティブ型（Email・パスワード等）はVOとして設計することを検討する
- UseCase層のエラー定義: UseCaseが返すドメインエラーの種別と、仕様書のAPI設計にあるHTTPステータスへのマッピングを定義する

### ステップ 4: フロントエンド設計（必要な場合）

フロントエンド設計指針は `docs/guidelines/design-guidelines.md` を参照。

- 画面ごとのUIイメージをテキストモックアップまたは図で示す
- UIコンポーネントの構成と責務を定義する
- 状態管理の方針を決める（グローバル状態 vs ローカル状態）
- 画面遷移と遷移条件（成功時・エラー時・未ログイン時）を定義する
- API通信設計（ローディング・エラー状態の扱いを含む）を定義する

### ステップ 5: インターフェース設計

- 公開インターフェース（API・関数シグネチャ・Props・イベント）を実装詳細より先に確定させる
- 入出力の型・形式・エラーケースを明示する

### ステップ 6: ADR作成

重要な技術的意思決定が生じたら `docs/adr/template.md` に沿ってADRを作成する。

保存先: `docs/adr/ADR-XXX-[タイトル].md`

#### ADR作成時の注意事項

- **ステータス**: セッション内で議論・合意した内容は「承認済」にする。「提案中」はまだ合意が取れていない場合のみ使う
- **コンテキスト**: 現在の実装状態（「現時点では〜のみ」）は時間が経つと陳腐化するため書かない。意思決定が必要な背景・課題を書く
- **設計決定 vs 運用ルール**: ADRには「なぜその構造を選んだか」を書く。「どのステータスコードをいつ使うか」などの運用ルール・対応表は `docs/guidelines/` に書く
- **ドキュメント内の言語**: 「SSoT」などの技術ジャーゴンは使わない。「参照」「定義」など平易な表現にする
- **書く内容の絞り込み**: `write-document` スキルに従う
- **参照先の完全性**: gitignore対象・未コミットのファイルをADRから参照しない（他の環境でリンク切れになる）

## 完了チェックリスト

- [ ] sub-issueが担当する要件が設計に反映されているか
- [ ] 仕様書の設計（ドメインモデル・DB設計・API設計）と矛盾していないか
- [ ] SOLID原則に違反している箇所がないか（詳細: `docs/guidelines/guidelines.md`）
- [ ] 既存の承認済みADR（特にレイヤー間の依存方向を規定するもの）と矛盾していないか
- [ ] バックエンド・フロントエンド双方のインターフェースが確定しているか
- [ ] UseCase層のエラー種別とHTTPステータスへのマッピングを定義したか
- [ ] 重要な技術的意思決定がADRに記録されているか
- [ ] 作成したドキュメントが `docs/guidelines/document-review-criteria.md` の観点を満たしているか
- [ ] 実装者がこの設計だけで実装を開始できる粒度か
