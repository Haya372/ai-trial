# レビューコメント対応スキル

## 目的

PRについているレビューコメントを整理し、対応するものはTDDで実装・コミットし、対応しないものは理由とともにGitHubに返信する。最後に全コメントへ具体的な返信を残す。

---

## 手順

### ステップ 1: PR番号の特定とコメント取得

PR番号が会話から分からない場合は、`<PR番号>` を省略して現在のブランチのPRを取得する。

```bash
# PRの作成者とベースブランチを取得
gh pr view <PR番号> --json number,title,url,author,baseRefName

# レビュー本文・通常コメント・レビュースレッド（インラインコメント）を全件取得
bash scripts/fetch-pr-review-threads.sh <PR番号> >| "$TMPDIR/pr-<PR番号>-threads.json"
```

出力の `reviews`・`issue_comments`・`threads` を一覧にして整理する。各コメントについて以下を記録する。スレッドは、最初のコメント（`threads[].comments[0]`）と、PRの作成者の最後の返信より後に投稿されたコメントを指摘として記録する。作成者の返信がないスレッドは、すべてのコメントを指摘として記録する。それ以外のコメントは、返信の経緯として内容の把握に使う。PRの作成者の返信は、`author` が `author.login` と一致し、本文の先頭が `<!-- pr-review -->` で始まらないコメントとする（作成者と `pr-review` の投稿者が同じアカウントの場合があるため）。

| フィールド | 内容 |
|---|---|
| ID | 返信時に使う。スレッドは `threads[].comments[0]` の `url`・`id`、通常コメントは `issue_comments[]` の `url`・`id`、レビュー本文は `reviews[]` の `id` |
| 投稿者 | レビュワー名（`author`） |
| 場所 | ファイル名・行番号（スレッドの場合。`path`・`line`。`line` が `null` なら表の下の手順で探す） |
| 内容 | コメントの要約 |
| 状態 | スレッドは `threads[].is_resolved` が `true` なら resolved、`false` なら unresolved。レビュー本文・通常コメントは空欄 |

`line` が `null` のスレッド（outdated）の `original_line` は、コメントした時点のファイルの行番号で、今のファイルの行番号ではない。`git fetch origin <comments[0].original_commit_id>` を実行してから（リベース後はローカルにないため）、指摘したコードを確認し、今のファイルで同じコードを探して場所を記録する。指摘したコードは、`diff_side` が `RIGHT` なら `git show <original_commit_id>:<path>`、`LEFT` なら `git show $(git merge-base origin/<baseRefName> <original_commit_id>):<path>` の `original_line` 行目にある。

### ステップ 2: 対応判断

各コメントについて「対応する」「しない」を判断する。

**対応する基準:**

- 指摘が正しく、コードの品質・安全性・正確性が向上する
- 要件の理解に基づく重要なフィードバック

**対応しない基準:**

- すでに意図的にそうしている（設計上の意思決定であり根拠がある）
- スコープ外（別Issueで対応すべき）
- **現PRの正確性・安全性に影響しない設計改善・重複排除などの技術的負債**

> **判断の原則**: 対応スコープは「現PRが正しく動くこと」に限定する。構造改善や重複排除は別Issueに切り出す。
>
> **例外**: 技術的負債であっても、**このPRで新たに導入したコード**に起因する問題（冗長なテスト・重複実装など）はこのPRで対応する。別ブランチから持ち込んだ既存コードへの指摘のみスコープ外とする。

**同じ関心事への指摘が続いた場合:**

前回のレビューで修正した関心事（同じ状態の扱い・同じ処理の流れ）に、再び指摘がついた場合は、指摘ごとの修正タスクにしない。関心事全体の振る舞いを洗い出して設計を見直し、その方針をユーザーに提示してから実装する（Claude Codeでは designer または advisor に設計の見直しを依頼する）。

**判断に迷ったらユーザーに確認する。**

```text
以下のコメントの対応判断を確認してください：
- [コメント内容] → [迷っている理由]
```

---

### ステップ 3: タスクリストの作成

対応するコメントについて、対応方針を決めてタスクに分解する。

**タスクの粒度:**

- 1タスク = 1コミットになる粒度
- 複数コメントが同じ箇所への修正に集約できる場合はまとめる
- 依存関係がある場合は順序を付ける

**タスク形式:**

```markdown
# レビュー対応タスクリスト

## タスク 1: [修正内容の簡潔な説明]
- 対応コメント: [コメントURL or 内容の要約]
- 方針: [具体的に何をどう変えるか]
- 対象ファイル: [ファイル名]

## タスク 2: ...
```

**方針に迷ったらユーザーに確認する。**

```text
以下の対応方針を確認してください：
- [コメント] → [提案している方針] / [代替案]
```

タスクリストはユーザーに提示するが、承認は待たずに実装に進む。方針に迷うタスクがある場合のみ、上記の形式で確認してから進める。

---

### ステップ 4: TDDで実装（1タスク1コミット）

タスクを順に実装する。各タスクで `implementation` スキルのサイクルを使う。

#### Red（テストを書く）

- 修正内容を検証するテストを先に書く
- テストを実行し、意図した理由で失敗することを確認する

#### Green（実装する）

- テストを通す最小限の実装をする
- テストを実行し、全て通ることを確認する

#### Refactor（整理する）

- テストがGreenを維持したままコードを整理する

#### コミット

コミットメッセージにレビュー対応であることを示す。

```bash
git add <変更ファイル>
git commit -m "fix: <変更内容の説明>"
```

コミットSHAを記録しておく（返信時に使う）。

```bash
git rev-parse HEAD  # コミットSHAを確認
```

---

### ステップ 5: Push

全タスクの実装が完了したらpushする。

画面の見た目や挙動（スクロール・フォーカス・クリック可否など）に関わる修正がある場合は、push の前に、`implementation` スキルの「フロントエンドのUI変更を実装するとき」の手順で、それらの修正をまとめてブラウザ上で確認する。ステップ6の返信に書く振る舞いは、ブラウザで確認できたものだけにする。

```bash
git push
```

---

### ステップ 6: コメントへの返信

各コメントに返信する。対応したものもしなかったものも全て返答する。

#### 対応したコメントへの返信

以下の情報を含める。

```text
対応しました。

方針: [何をどう変えたか]
コミット: <SHA> ([コミットメッセージ])
```

#### 対応しないコメントへの返信

設計上の意思決定・好みの違い:

```text
ご指摘ありがとうございます。今回は対応しない方針としました。

理由: [設計上の意図・スコープ外である根拠など]
```

現PRの正確性に影響しない技術的負債・設計改善の場合は **GitHub Issue を起票してからコメントに返信する**:

```bash
gh issue create --title "[chore] <改善内容>" --body "<指摘の内容と対応方針>"
```

```text
ご指摘ありがとうございます。現PRのスコープ外のため別Issueとして起票しました。

Issue: <Issue URL>
```

#### GitHub APIでコメントに返信する

インラインレビューコメントへの返信:

```bash
# インラインコメントのスレッドに返信
gh api repos/{owner}/{repo}/pulls/{PR番号}/comments/{comment_id}/replies \
  --method POST \
  -f body="返信内容"
```

一般的なPRコメントへの返信:

```bash
gh pr comment <PR番号> --body "返信内容"
```

owner/repoの取得:

```bash
gh repo view --json nameWithOwner --jq '.nameWithOwner'
```

## チェックリスト

- [ ] 全コメントの対応判断が済んでいるか
- [ ] 判断に迷ったコメントはユーザーに確認したか
- [ ] タスクリストをユーザーに提示したか
- [ ] 前回修正した関心事に再び指摘がついた場合、設計を見直してから実装したか
- [ ] 各タスクでテストを先に書いているか（TDD遵守）
- [ ] 画面の挙動に関わる修正をブラウザで確認したか
- [ ] 1タスク1コミットになっているか
- [ ] pushが完了しているか
- [ ] 全コメントに返信したか（対応しなかったものも含む）
- [ ] 返信にコミットSHAと方針が含まれているか

---

## よくあるパターンと対処

| 状況 | 対処 |
|---|---|
| コメントが既にresolvedになっている | スキップしてよいが、実装済みかどうかを確認してから |
| 同じ問題への複数コメント | タスクをまとめ、返信で「まとめて対応しました」と書く |
| 設計変更を伴う大きな指摘 | ユーザーに確認してから対応方針を決める |
| テストが書けない変更（設定ファイル等） | 理由をコミットメッセージに書き、レビュワーに伝える |
