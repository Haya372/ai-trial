# レビューコメント対応スキル

## 目的

PRについているレビューコメントを整理し、対応するものはTDDで実装・コミットし、対応しないものは理由とともにGitHubに返信する。最後に全コメントへ具体的な返信を残す。

---

## 手順

### ステップ 1: PR番号の特定とコメント取得

PR番号が会話から分からない場合は、`gh pr view` の `<PR番号>` を省略して現在のブランチのPRを取得し、以降の `<PR番号>` には出力の `number` を使う。

```bash
# ベースブランチを取得
gh pr view <PR番号> --json number,title,url,baseRefName

# レビュー本文・通常コメント・レビュースレッド（インラインコメント）と、作成者が返信していないコメントの判定を取得
bash scripts/fetch-pr-review-threads.sh <PR番号> >| "$TMPDIR/pr-<PR番号>-threads.json"

# ステップ5で確認する差分の起点
git rev-parse HEAD
```

出力のうち `needs_reply` が `true` のものだけを、対応するコメントとして一覧にする。`needs_reply` が `false` のものは、前回までに返信済みのコメントと `pr-review` のレビュー本文なので、一覧に入れない。`needs_reply` が `true` でも、下記で指摘として記録するコメントが、依頼・質問を含まないコメント（「了解です」「LGTM」などの相槌、作成者自身のメモ）だけの場合は一覧に入れない。

- スレッド（`threads[]`）: `unanswered_comments` を指摘として記録する。それ以外のコメント（`comments`）は、返信の経緯として内容の把握に使う
- レビュー本文（`reviews[]`）・通常コメント（`issue_comments[]`）: そのコメントを指摘として記録する

| フィールド | 内容 |
|---|---|
| ID | 返信時に使う。スレッドは `threads[].comments[0]` の `url`・`id`、通常コメントは `issue_comments[]` の `url`・`id`、レビュー本文は `reviews[]` の `id` |
| 投稿者 | レビュワー名（`author`） |
| 場所 | ファイル名・行番号（スレッドの場合。`path`・`line`。`original_line` が `null` ならファイル全体へのコメントなので `path` だけ。それ以外で `is_outdated` が `true` なら表の下の手順で探す） |
| 内容 | コメントの要約 |
| 状態 | スレッドは `threads[].is_resolved` が `true` なら resolved、`false` なら unresolved。レビュー本文・通常コメントは空欄 |

`is_outdated` が `true` のスレッドの `original_line` は、コメントした時点のファイルの行番号で、今のファイルの行番号ではない。`git fetch origin <comments[0].original_commit_id>` を実行してから（リベース後はローカルにないため）、指摘したコードを確認し、今のファイルで同じコードを探して場所を記録する。指摘したコードは、`diff_side` が `RIGHT` なら `git show <original_commit_id>:<path>`、`LEFT` なら `git show $(git merge-base origin/<baseRefName> <original_commit_id>):<path>` の `original_line` 行目にある。

### ステップ 2: 対応判断

各コメントについて「対応する」「しない」を判断する。

**対応する基準:**

- 指摘が正しく、コードの品質・安全性・正確性が向上する
- 要件の理解に基づく重要なフィードバック

**対応しない基準:**

- すでに意図的にそうしている（設計上の意思決定であり根拠がある）
- スコープ外（別Issueで対応すべき）
- **現PRの正確性・安全性に影響しない設計改善・重複排除などの技術的負債**

> **判断の原則**: 対応スコープは「現PRが正しく動くこと」に限定する。構造改善や重複排除は別Issueに切り出す。
>
> **例外**: 技術的負債であっても、**このPRで新たに導入したコード**に起因する問題（冗長なテスト・重複実装など）はこのPRで対応する。別ブランチから持ち込んだ既存コードへの指摘のみスコープ外とする。

**レビュワーが修正方法を提案している場合:**

指摘が正しくても、提案された修正方法（「期待する振る舞い」など）が正しいとは限らない。採用する前に以下を確認し、当てはまるものがあれば、修正方法を変えてステップ3の方針に書く。

| 確認すること | 確認方法 |
|---|---|
| 提案どおりに直しても問題が残る入力・状態がないか | 提案で使う関数・設定・判定条件の仕様を公式ドキュメントで確認し、それをすり抜ける入力を探す（例: 文字列だけを検査する関数とシンボリックリンク、ページ単位の設定とSPAのクライアント側の遷移） |
| 提案に従うと壊れる既存の使い方がないか | 提案が対象にする範囲のコード・設定を `git grep` で探し、提案の条件に合わない使い方がないか確認する（例: JavaScriptから読む必要があるCookieに `HttpOnly` を求める） |
| 既存のLinter・ガイドライン・ADRと重複・衝突しないか | Linterの設定（`apps/backend/.golangci.yml`・`biome.jsonc`・`.markdownlint-cli2.jsonc` など）、`docs/guidelines/`、`docs/adr/` を、修正内容のキーワードで検索する。Linterで検出できる規約は、ドキュメントに書かずLinterに任せる |

**前回のレビュー対応で修正した箇所に、再び指摘がついた場合:**

指摘ごとの修正タスクにしない。ステップ3の洗い出しに加えて、修正の方式（一覧で列挙するか条件で書くか、どこで判定するか）を見直し、その方針をユーザーに提示してから実装する（Claude Codeでは designer または advisor に方式の見直しを依頼する）。

**判断に迷ったらユーザーに確認する。**

```text
以下のコメントの対応判断を確認してください：
- [コメント内容] → [迷っている理由]
```

### ステップ 3: タスクリストの作成

対応するコメントについて、対応方針を決めてタスクに分解する。タスクにするのは、ステップ1の一覧のコメントへの対応だけにする。作業中に見つけた、どのコメントにも紐づかない改善・不具合は、レビュー対応のコミットに含めず、ユーザーに伝えて別PR・別Issueにする。

**同じ種類のケースの洗い出し:**

方針を決めるとき、指摘に挙がった具体例だけでなく、同じ原因で漏れているケースを洗い出し、同じタスクでまとめて直す。

| 指摘の種類 | 洗い出し方 |
|---|---|
| 一覧（対象ファイル・パス・条件・項目）の漏れ | 一覧の元になる情報（関連するADR・設定ファイル・`git ls-files` の結果など）から全件を出し、一覧と突き合わせる |
| 判定・条件の誤り | 同じ判定・同じ書き方をしている箇所を `git grep` で探し、同じ誤りがないか確認する |
| 項目どうしの食い違い | 修正する項目と同じ表・同じファイルの他の項目を読み、判定が矛盾しないか確認する |

**タスクの粒度:**

- 1タスク = 1コミットになる粒度
- 複数コメントが同じ箇所への修正に集約できる場合はまとめる
- 依存関係がある場合は順序を付ける

**タスク形式:**

```markdown
# レビュー対応タスクリスト

## タスク 1: [修正内容の簡潔な説明]
- 対応コメント: [コメントURL or 内容の要約]
- 方針: [具体的に何をどう変えるか。提案から変えた場合はその理由]
- 洗い出した範囲: [同じ種類のケースとして確認した箇所と、まとめて直す箇所]
- 対象ファイル: [ファイル名]

## タスク 2: ...
```

**方針に迷ったらユーザーに確認する。**

```text
以下の対応方針を確認してください：
- [コメント] → [提案している方針] / [代替案]
```

タスクリストはユーザーに提示するが、承認は待たずに実装に進む。方針に迷うタスクがある場合のみ、上記の形式で確認してから進める。

---

### ステップ 4: TDDで実装（1タスク1コミット）

タスクを順に実装する。各タスクで `implementation` スキルのサイクルを使う。ドキュメント・スキル・設定ファイルなど、テストを書けない修正は、Red・Greenを省いて実装し、ステップ5の差分確認で確認する。

#### Red（テストを書く）

- 修正内容を検証するテストを先に書く
- テストを実行し、意図した理由で失敗することを確認する

#### Green（実装する）

- テストを通す最小限の実装をする
- テストを実行し、全て通ることを確認する

#### Refactor（整理する）

- テストがGreenを維持したままコードを整理する

#### コミット

コミットメッセージにレビュー対応であることを示す。

```bash
git add <変更ファイル>
git commit -m "fix: <変更内容の説明>"
```

コミットSHAを記録しておく（返信時に使う）。

```bash
git rev-parse HEAD  # コミットSHAを確認
```

### ステップ 5: 修正差分の確認

全タスクのコミット後、`git diff <ステップ1で記録したHEAD>..HEAD` を、次のレビュワーとして確認する。変更した行ごとに、以下に当たる入力・状態・ファイルを具体的に探す。

- その記述・コードに従っても、指摘された問題が起きる入力・状態（回避方法）
- その記述・コードに従うと壊れる既存の使い方
- 同じファイル・同じ表の他の項目と判定が食い違うケース
- 一覧・条件の対象から漏れる同じ種類のケース

確認する観点は、変更したファイルの種類に応じて `pr-review` スキルのステップ3の表で決める。Claude Codeでは、qa エージェントに、対応したコメントと差分の範囲を渡して確認を依頼する。

見つかった問題は、ステップ3に戻ってタスクにする。見つからなくなったら次のステップへ進む。

画面の見た目や挙動（スクロール・フォーカス・クリック可否など）に関わる修正がある場合は、`implementation` スキルの「フロントエンドのUI変更を実装するとき」の手順で、それらの修正をまとめてブラウザ上で確認する。ステップ7の返信に書く振る舞いは、ブラウザで確認できたものだけにする。

### ステップ 7: コメントへの返信

返信する前に、ステップ1のスクリプトを再実行する。`needs_reply` が `true` のコメントのうち、ステップ1の出力になかったもの（作業中に追加されたコメント。スレッドは `unanswered_comments[].id` で照合する）に、ステップ1と同じ基準を当てはめる。一覧に入るものがあれば、一覧に加えてステップ2に戻る。返信すると、それより前のコメントは返信済みと判定されるため、追加されたコメントを残したまま返信しない。

ステップ1の一覧のコメントすべてに返信する。対応したものもしなかったものも全て返答する。

#### 対応したコメントへの返信

以下の情報を含める。

```text
対応しました。

方針: [何をどう変えたか]
コミット: <SHA> ([コミットメッセージ])
```

#### 対応しないコメントへの返信

設計上の意思決定・好みの違い:

```text
ご指摘ありがとうございます。今回は対応しない方針としました。

理由: [設計上の意図・スコープ外である根拠など]
```

現PRの正確性に影響しない技術的負債・設計改善の場合は **GitHub Issue を起票してからコメントに返信する**:

```bash
gh issue create --title "[chore] <改善内容>" --body "<指摘の内容と対応方針>"
```

```text
ご指摘ありがとうございます。現PRのスコープ外のため別Issueとして起票しました。

Issue: <Issue URL>
```

#### GitHub APIでコメントに返信する

インラインレビューコメントへの返信:

```bash
# インラインコメントのスレッドに返信
gh api repos/{owner}/{repo}/pulls/{PR番号}/comments/{comment_id}/replies \
  --method POST \
  -f body="返信内容"
```

一般的なPRコメントへの返信:

```bash
gh pr comment <PR番号> --body "返信内容"
```

owner/repoの取得:

```bash
gh repo view --json nameWithOwner --jq '.nameWithOwner'
```

## チェックリスト

- [ ] `needs_reply` が `true` のコメントだけを一覧にしたか
- [ ] 全コメントの対応判断が済んでいるか
- [ ] 判断に迷ったコメントはユーザーに確認したか
- [ ] レビュワーが提案した修正方法を、反例・既存の使い方・Linter・ガイドライン・ADRと照らしてから採用したか
- [ ] 前回修正した箇所に再び指摘がついた場合、修正の方式を見直してから実装したか
- [ ] 指摘の具体例だけでなく、同じ種類のケースを洗い出したか
- [ ] どのコメントにも紐づかない変更を、レビュー対応のコミットに含めていないか
- [ ] タスクリストをユーザーに提示したか
- [ ] 各タスクでテストを先に書いているか（TDD遵守）
- [ ] push前に修正差分を次のレビュワーとして確認したか
- [ ] 画面の挙動に関わる修正をブラウザで確認したか
- [ ] 1タスク1コミットになっているか
- [ ] pushが完了しているか
- [ ] 返信の直前にスクリプトを再実行し、作業中に追加されたコメントがないか確認したか
- [ ] 全コメントに返信したか（対応しなかったものも含む）
- [ ] 返信にコミットSHAと方針が含まれているか

## よくあるパターンと対処

| 状況 | 対処 |
|---|---|
| コメントが既にresolvedになっている | スキップしてよいが、実装済みかどうかを確認してから |
| 同じ問題への複数コメント | タスクをまとめ、返信で「まとめて対応しました」と書く |
| 設計変更を伴う大きな指摘 | ユーザーに確認してから対応方針を決める |
