# 詳細設計スキル

## 目的

PRDをバックエンド・フロントエンド双方の実装可能な技術設計仕様に落とし込む。

```
PRD作成 → Issue作成 → [詳細設計 ← 今ここ] → TDD実装 → PRレビュー → マージ
```

## 設計手順

### ステップ 1: PRD確認

- `docs/prd/` 配下の対象PRDを読み、ゴール・要件・非目標・制約を把握する
- 不明な箇所はPDMに確認してから次のステップへ進む
- 成功指標を確認し、設計がそれを達成できるか意識する

### ステップ 2: アーキテクチャ設計

設計原則は `docs/guidelines/guidelines.md` を参照。

- コンポーネント・モジュールの責務を分割する（SOLID準拠）
- 依存関係の方向を整理する
- データフローとコンポーネント間の相互作用を図または箇条書きで明示する

### ステップ 3: バックエンド設計（必要な場合）

バックエンド設計指針は `docs/guidelines/design-guidelines.md` を参照。

- APIエンドポイント・リクエスト・レスポンス形式を定義する
- レイヤー設計（責務の分割）を決める
- 入力バリデーションのルールと適用箇所を定義する
- DBテーブル設計（テーブル名・カラム名・型・制約・インデックス・リレーション）を定義する

### ステップ 4: フロントエンド設計（必要な場合）

フロントエンド設計指針は `docs/guidelines/design-guidelines.md` を参照。

- 画面ごとのUIイメージをテキストモックアップまたは図で示す
- UIコンポーネントの構成と責務を定義する
- 状態管理の方針を決める（グローバル状態 vs ローカル状態）
- 画面遷移と遷移条件（成功時・エラー時・未ログイン時）を定義する
- API通信設計（ローディング・エラー状態の扱いを含む）を定義する

### ステップ 5: インターフェース設計

- 公開インターフェース（API・関数シグネチャ・Props・イベント）を実装詳細より先に確定させる
- 入出力の型・形式・エラーケースを明示する

### ステップ 6: ADR作成

重要な技術的意思決定が生じたら `docs/adr/template.md` に沿ってADRを作成する。

保存先: `docs/adr/ADR-XXX-[タイトル].md`

### ステップ 7: ドメインモデル定義

ドメイン固有の概念・用語を `docs/domain/template.md` に沿って定義する。

保存先: `docs/domain/[ドメイン名].md`

## 完了チェックリスト

- [ ] 全ての要件が設計に反映されているか
- [ ] SOLID原則に違反している箇所がないか（詳細: `docs/guidelines/guidelines.md`）
- [ ] バックエンド・フロントエンド双方のインターフェースが確定しているか
- [ ] 重要な技術的意思決定がADRに記録されているか
- [ ] ドメイン用語が定義されているか
- [ ] 実装者がこの設計だけで実装を開始できる粒度か
