# PRレビュースキル

## 目的

PR差分をカテゴリ別（frontend / backend / document）に分析し、重要度の高い指摘のみGitHub PRにインラインコメントとして投稿する。レビュー処理をサブAgentに委譲することでメインAgentのコンテキスト消費を最小化する。

---

## 手順

### ステップ 1: PR情報取得

```bash
# リポジトリ情報（owner/repo形式）
gh repo view --json nameWithOwner -q .nameWithOwner

# PR差分取得
gh pr diff <PR番号>

# 変更ファイル一覧取得
gh pr view <PR番号> --json files -q '.files[].path'
```

### ステップ 2: カテゴリ判定

変更ファイルの拡張子から対象カテゴリを判定する。拡張子だけでは判断できない場合（`.ts` など）はファイルパスやdiff内容から総合的に判断する。

| カテゴリ | 主な拡張子 |
|----------|-----------|
| frontend | `.tsx`, `.jsx`, `.vue`, `.svelte`, `.css`, `.html` |
| backend | `.go`, `.py`, `.rs`, `.java`, `.sql` |
| document | `.md`, `.yaml`, `.json`（設定ファイル） |

- 複数のカテゴリに該当するファイルが存在する場合は、複数のカテゴリを対象にする
- どのカテゴリにも該当しない場合はユーザーに通知して終了する

### ステップ 3: カテゴリ別サブAgentの起動

該当カテゴリごとに `Agent` ツール（`subagent_type: "general-purpose"`）でサブAgentを起動する。複数カテゴリがある場合は並列実行する。

各サブAgentへのプロンプト：

```
あなたはPRレビュアーです。以下の差分を `docs/guidelines/<カテゴリ>-review-criteria.md` の観点に従ってレビューしてください。

## 差分
<該当カテゴリのファイルのdiff内容>

## レビュー手順

1. 差分全体を最初から最後まで注意深く読む
2. 問題の候補を見つけたら、**必ず当該行を差分から引用して**問題が実際に存在することを確認する
3. 確認できた問題のみ報告する（不確かな場合は報告しない）
4. 誤検知チェックリストを確認する（後述）

## 誤検知を防ぐためのチェックリスト

以下に該当する場合は報告しない:

- Linter・型チェック・CIで自動検出できる（フォーマット・unused import等）
- 差分に存在しない内容への指摘（「〇〇が不足」と書く前に差分内に本当に存在しないか確認）
- 将来起こるかもしれない仮定的リスク（「〇〇が変更されたら問題になる可能性がある」等）
- コードオーナーが意図的に選択した設計（前後の文脈から明らかな場合）
- スタイルの好みや個人的な意見（「〇〇の方が読みやすい」等）

## 出力形式

指摘事項を以下の形式で列挙してください。問題が見つからない場合は「指摘なし」とだけ返してください。

---
**[スコア: X/10] [確信度: Y%]**
- ファイル: `path/to/file.go`
- 行: 42
- カテゴリ: セキュリティ / パフォーマンス / 設計 / アクセシビリティ / 正確性 / etc.
- 根拠（差分から引用）: `実際のコード行`
- 指摘: 問題の説明（具体的に）
- 提案: 改善案（コード例があれば記載）
---

## スコア基準

| スコア | 意味 |
|--------|------|
| 10 | セキュリティ脆弱性・データ損失リスク（マージブロック必須） |
| 8〜9 | 重大なバグ・設計上の明確な欠陥（強く修正推奨） |
| 7 | 修正が望ましい問題（コメント投稿の最低ライン）— 「修正しないと機能上の問題が発生する」レベルに限定 |
| 4〜6 | 軽微な問題・スタイル（投稿しない） |
| 1〜3 | 好み・提案レベル（投稿しない） |

## 確信度基準

| 確信度 | 意味 |
|--------|------|
| 90〜100% | 差分を読んで問題を直接確認できた |
| 70〜89% | 問題の存在はほぼ確実だが、一部文脈に依存する |
| 50〜69% | 問題の可能性はあるが確認できていない |
| 50%未満 | 報告しない |
```

### ステップ 4: 指摘の収集・フィルタリング

1. 全サブAgentの結果を収集する
2. 同一ファイル・同一行への重複指摘は内容を統合して1件にまとめる
3. **スコア7以上かつ確信度70%以上** の指摘のみを抽出する
4. 抽出結果が0件の場合はステップ5をスキップしてステップ6に進む

### ステップ 5: インラインコメントの投稿

スコア7以上の指摘を `gh api` でPRにインラインコメントとして投稿する。

```bash
gh api repos/<owner>/<repo>/pulls/<PR番号>/reviews \
  --method POST \
  --input - <<'JSON'
{
  "body": "## PRレビュー\n\nカテゴリ別サブAgentによる自動レビューです。スコア7以上の指摘のみ掲載しています。",
  "event": "COMMENT",
  "comments": [
    {
      "path": "src/handlers/auth.go",
      "line": 42,
      "side": "RIGHT",
      "body": "**[スコア: 8/10] セキュリティ**\n\n**指摘:** 認証トークンの有効期限チェックが不足しています。\n\n**提案:** `token.ExpiresAt.Before(time.Now())` で有効期限を検証してください。"
    }
  ]
}
JSON
```

インラインコメントの本文フォーマット：

```
**[スコア: X/10] カテゴリ名**

**指摘:** <問題の説明>

**提案:** <改善案>
```

### ステップ 6: サマリー報告

ユーザーに以下の形式でレビュー結果を報告する。

```
## レビュー完了 (PR #<番号>)

| カテゴリ  | 全指摘数 | 投稿（スコア7以上） | スキップ |
|-----------|---------|-------------------|---------|
| backend   | 5       | 3                 | 2       |
| frontend  | 2       | 1                 | 1       |
| document  | 1       | 0                 | 1       |
| **合計**  | **8**   | **4**             | **4**   |

投稿済みコメントはPR上で確認できます。
```

---

## エラーハンドリング

| エラー | 対処 |
|--------|------|
| PR差分取得失敗（PR不存在・権限なし） | エラーメッセージを出力してスキルを中断 |
| サブAgent失敗・タイムアウト | そのカテゴリをスキップしてサマリーにエラーを記録 |
| インラインコメント投稿失敗 | 指摘内容を標準出力に出力して手動投稿を促す |
