# リファクタリングスキル

## 目的

外部から見た振る舞いを変えずにコード品質を改善する。
リファクタリングは「動作を変えない」という安全保証のもとで行う。テストがその保証を担う。

## 前提

このスキルはTDD実装（`implementation` スキル）の後、またはコードレビューで品質課題が発見された際に使う。
開発フロー上は「TDD実装 → PRレビュー」の間、または「PRレビュー」で指摘を受けた後に適用する。

## 手順

### 1. テストの確認（安全確認）

リファクタリングを始める前に、必ずテストが通ることを確認する。
テストがなければ、先にテストを追加してから進む。テストなしのリファクタリングは動作保証がなく危険。

```
# テストを実行して全て通ることを確認
```

- テストがない場合 → 先に `test-design` スキルを使ってテストを追加する
- テストが失敗している場合 → 先にバグを修正してからリファクタリングする

### 2. リファクタリング対象の特定

以下の観点でコードを読み、改善対象を列挙する。優先度の高いものから着手する。

#### DRY違反（重複コード）
- 同じロジックが複数箇所に存在する
- コピー&ペーストで作られた類似コード
- 対処: 共通関数・モジュールに切り出す

#### 単一責任の違反
- 1つのクラス・関数が複数の責務を持っている
- 関数が長すぎる（目安: 20〜30行超）
- クラスが肥大化している
- 対処: 責務ごとに分割する

#### 不明瞭な命名
- 変数名・関数名がその役割を表していない（`data`, `tmp`, `flag` など）
- 略語や文脈なしでは意味が取れない名前
- 対処: 役割が一目でわかる名前に変更する

#### その他の観点（SOLID・KISS）
- 抽象に依存していない（依存関係逆転の原則違反）
- 拡張のたびに既存コードを修正している（開放閉鎖の原則違反）
- 不必要に複雑な実装（KISS違反）

### 3. 小さく変更する（反復サイクル）

1回の変更は1つの改善に絞る。複数の改善を同時に行うと、テスト失敗時の原因特定が難しくなる。

```
変更 → テスト実行 → 通ればコミット → 次の改善へ
```

- 変更のたびにテストを実行する
- テストが通ったらその時点でコミットする（`refactor:` プレフィックスを使う）
- テストが失敗したら、その変更を元に戻して原因を分析する

### 4. 完了確認

- 全てのテストが通るか確認する
- 変更前と比べてコードが読みやすくなっているか確認する
- 外部インターフェース（関数シグネチャ・APIレスポンス等）が変わっていないか確認する

## コミットメッセージの規約

リファクタリングのコミットには `refactor:` プレフィックスを使う。

```
refactor: UserService から認証ロジックを AuthService に分離
refactor: calculateTax の重複実装を共通関数に統合
refactor: 不明瞭な変数名 d, tmp を deadline, tempBuffer に変更
```

## チェックリスト

- [ ] リファクタリング前にテストが全て通っているか
- [ ] テストがない場合は先にテストを追加したか
- [ ] 1回の変更を1つの改善に限定しているか
- [ ] 変更のたびにテストを実行して確認しているか
- [ ] SOLID・DRY・KISS原則に沿った改善か
- [ ] 外部から見た振る舞いが変わっていないか
- [ ] コミットメッセージに `refactor:` プレフィックスを使っているか
