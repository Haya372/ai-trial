# コードレビュースキル

## 目的

コードの品質・正確性・ガイドライン準拠を体系的に確認し、問題点の指摘と改善提案を行う。

## レビュー手順

以下の順序で進める。問題を発見したら都度フィードバックし、手順を最後まで完走する。

### 1. 要件との整合性確認

- 対応するIssueまたは設計ドキュメントを特定する
- 実装されている機能・変更範囲がIssueのスコープに収まっているか確認する
- 設計で定義されたインターフェースと実装が一致しているか確認する

### 2. TDD準拠確認

- コミット履歴を確認し、テストコードが実装コードより先にコミットされているか確認する
- テストなし実装のみのコミットが先行する場合はTDD違反と判断する

### 3. テストカバレッジ確認

`docs/guidelines/test-guidelines.md` の網羅観点を参照して確認する。

- 正常系・異常系・エッジケースが揃っているか
- テストが公開インターフェースの振る舞いをテストしているか
- 各テストが独立して実行できるか

### 4. SOLID・DRY・KISS・YAGNI準拠確認

詳細は `docs/guidelines/guidelines.md` を参照。

- SOLID（S/O/L/I/D それぞれ）の違反がないか
- DRY: 同じロジックが複数箇所に重複していないか
- KISS: 不必要に複雑な実装をしていないか
- YAGNI: 現時点で不要な機能・抽象化がないか

### 5. セキュリティ確認

- 入力バリデーションが適切に行われているか（SQLインジェクション・XSS等の防止）
- 認証・認可が必要な操作に漏れなく適用されているか
- 機密情報（APIキー・パスワード等）がハードコーディングされていないか
- エラーメッセージが内部情報（スタックトレース・DB構造等）を漏らしていないか

### 6. パフォーマンス確認

- N+1クエリが発生していないか（ループ内でのDB問い合わせ）
- 大量データを一度にメモリに読み込んでいないか
- 不必要な再計算・再レンダリングが発生していないか

### 7. コードコメント確認

詳細は `docs/guidelines/guidelines.md` を参照。

- コードコメントがWHYのみか（WHATは書かない）
- 古くなったコメントや実装と乖離したコメントがないか

## チェックリスト

- [ ] 要件・設計との整合性（スコープ逸脱なし、インターフェース一致）
- [ ] TDD準拠（テストが実装より先）
- [ ] テストカバレッジ（`docs/guidelines/test-guidelines.md` の観点を網羅）
- [ ] SOLID・DRY・KISS・YAGNI準拠
- [ ] セキュリティ（入力バリデーション・認証認可・機密情報・エラー情報漏洩）
- [ ] パフォーマンス（N+1・大量データ・不必要な再計算）
- [ ] コードコメントはWHYのみ

## Issue の整理

スコアリング前に、内容が重複・包含関係にある Issue は1つにまとめる。
（例: 「特定の用語Aが未登録」と「複数の用語が未登録」は後者に統合する）

## フィードバックの書き方

- **問題:** 何が問題か（具体的なファイル・行番号を示す）
- **理由:** なぜ問題か（どのガイドラインに違反しているか）
- **提案:** どう改善すればよいか

重大度を区別する:
- `[必須]` — マージ前に修正が必要
- `[推奨]` — 修正が望ましいが必須ではない
- `[提案]` — 今後の参考として
