# テスト設計スキル

テスト設計の目的は「実装の正しさを検証できる最小限のテスト群を、実装より先に定義すること」。

## 前提確認

詳細設計ドキュメントが存在することを確認する。インターフェースが未確定であればDesignerに戻る。

## 手順

### 1. テスト対象の確認

- 詳細設計のインターフェースを確認する
- テスト対象の責務を1つに絞る（SRP違反があれば設計に差し戻す）
- 関連するIssueや受け入れ条件（Acceptance Criteria）を確認する

### 2. テストケースの洗い出し

`docs/guidelines/test-guidelines.md` の網羅観点を参照してテストケースを洗い出す。

確認すべき観点:
- 正常系（仕様通りの入力で期待通りの出力が返るか）
- 異常系（不正な入力・権限エラー・外部依存の失敗など）
- エッジケース（境界値・null・空・最大値など）
- 状態・条件の組み合わせ（複数条件が絡む場合）
- フロントエンドの場合はUIの状態変化も含める

### 3. テストコードの作成（Red）

- テストを先に書き、実装コードは書かない
- 1テストで1シナリオを検証する。同一シナリオ内で複数アサーションをまとめてよい
- テスト名はシナリオ（条件・状況）と期待結果が伝わるようにする（詳細: `docs/guidelines/test-guidelines.md`）
- 外部依存（DB・API・ファイルIO）はモック・スタブで差し替える

### 4. テストの失敗確認（Redの確認）

- テストを実行し、全て失敗することを確認する
- 失敗の理由が「実装がないから」であることを確認する（設定ミスや構文エラーで落ちている場合は修正する）

## チェックリスト

- [ ] 詳細設計のインターフェースを確認したか
- [ ] `docs/guidelines/test-guidelines.md` の全網羅観点を検討したか
- [ ] テストコードは実装コードより先に書かれているか
- [ ] テストが意図した理由で失敗しているか（Red確認）
- [ ] テストは他のテストに依存せず独立して実行できるか
