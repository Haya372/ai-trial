# レビューコメント対応スキル

## 目的

PRについているレビューコメントを整理し、対応するものはTDDで実装・コミットし、対応しないものは理由とともにGitHubに返信する。最後に全コメントへ具体的な返信を残す。

---

## 手順

### ステップ 1: PR番号の特定とコメント取得

PR番号が会話から分からない場合は現在のブランチから取得する。

```bash
# 現在のブランチに対応するPR番号を取得
gh pr view --json number,title,url

# レビューコメント（インラインコメントを含む）を取得
gh pr view <PR番号> --json reviews,comments
gh api repos/{owner}/{repo}/pulls/<PR番号>/comments
```

取得したコメントを一覧にして整理する。各コメントについて以下を記録する。

| フィールド | 内容 |
|---|---|
| ID | コメントのURL（返信時に使う） |
| 投稿者 | レビュワー名 |
| 場所 | ファイル名・行番号（インラインの場合） |
| 内容 | コメントの要約 |
| 状態 | resolved / unresolved |

---

### ステップ 2: 対応判断

各コメントについて「対応する」「しない」を判断する。

**対応する基準:**
- 指摘が正しく、コードの品質・安全性・正確性が向上する
- 要件の理解に基づく重要なフィードバック

**対応しない基準:**
- すでに意図的にそうしている（設計上の意思決定）
- スコープ外（別Issueで対応すべき）
- 好みの違いで、どちらでも正当性がある

**判断に迷ったらユーザーに確認する。**

```
以下のコメントの対応判断を確認してください：
- [コメント内容] → [迷っている理由]
```

---

### ステップ 3: タスクリストの作成

対応するコメントについて、対応方針を決めてタスクに分解する。

**タスクの粒度:**
- 1タスク = 1コミットになる粒度
- 複数コメントが同じ箇所への修正に集約できる場合はまとめる
- 依存関係がある場合は順序を付ける

**タスク形式:**

```
# レビュー対応タスクリスト

## タスク 1: [修正内容の簡潔な説明]
- 対応コメント: [コメントURL or 内容の要約]
- 方針: [具体的に何をどう変えるか]
- 対象ファイル: [ファイル名]

## タスク 2: ...
```

**方針に迷ったらユーザーに確認する。**

```
以下の対応方針を確認してください：
- [コメント] → [提案している方針] / [代替案]
```

タスクリストをユーザーに提示し、承認を得てから実装に進む。

---

### ステップ 4: TDDで実装（1タスク1コミット）

タスクを順に実装する。各タスクで `implementation` スキルのサイクルを使う。

#### Red（テストを書く）

- 修正内容を検証するテストを先に書く
- テストを実行し、意図した理由で失敗することを確認する

#### Green（実装する）

- テストを通す最小限の実装をする
- テストを実行し、全て通ることを確認する

#### Refactor（整理する）

- テストがGreenを維持したままコードを整理する

#### コミット

コミットメッセージにレビュー対応であることを示す。

```bash
git add <変更ファイル>
git commit -m "fix: <変更内容の説明>"
```

コミットSHAを記録しておく（返信時に使う）。

```bash
git rev-parse HEAD  # コミットSHAを確認
```

---

### ステップ 5: Push

全タスクの実装が完了したらpushする。

```bash
git push
```

---

### ステップ 6: コメントへの返信

各コメントに返信する。対応したものもしなかったものも全て返答する。

#### 対応したコメントへの返信

以下の情報を含める。

```
対応しました。

方針: [何をどう変えたか]
コミット: <SHA> ([コミットメッセージ])
```

#### 対応しないコメントへの返信

```
ご指摘ありがとうございます。今回は対応しない方針としました。

理由: [設計上の意図・スコープ外である根拠など]
```

#### GitHub APIでコメントに返信する

インラインレビューコメントへの返信:

```bash
# インラインコメントのスレッドに返信
gh api repos/{owner}/{repo}/pulls/{PR番号}/comments/{comment_id}/replies \
  --method POST \
  -f body="返信内容"
```

一般的なPRコメントへの返信:

```bash
gh pr comment <PR番号> --body "返信内容"
```

owner/repoの取得:

```bash
gh repo view --json nameWithOwner --jq '.nameWithOwner'
```

## チェックリスト

- [ ] 全コメントの対応判断が済んでいるか
- [ ] 判断に迷ったコメントはユーザーに確認したか
- [ ] タスクリストをユーザーに承認してもらったか
- [ ] 各タスクでテストを先に書いているか（TDD遵守）
- [ ] 1タスク1コミットになっているか
- [ ] pushが完了しているか
- [ ] 全コメントに返信したか（対応しなかったものも含む）
- [ ] 返信にコミットSHAと方針が含まれているか

---

## よくあるパターンと対処

| 状況 | 対処 |
|---|---|
| コメントが既にresolvedになっている | スキップしてよいが、実装済みかどうかを確認してから |
| 同じ問題への複数コメント | タスクをまとめ、返信で「まとめて対応しました」と書く |
| 設計変更を伴う大きな指摘 | ユーザーに確認してから対応方針を決める |
| テストが書けない変更（設定ファイル等） | 理由をコミットメッセージに書き、レビュワーに伝える |
