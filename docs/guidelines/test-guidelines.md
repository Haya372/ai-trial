# テストガイドライン

## テストの種類と使い分け

| 種別 | 対象 | 速度 | 外部依存 |
|---|---|---|---|
| 単体テスト（Unit） | 関数・クラスの単一責務 | 高速 | モック・スタブで差し替え |
| 統合テスト（Integration） | 複数コンポーネントの連携 | 中速 | 実際のDB・APIを使う場合も |
| E2Eテスト（End-to-End） | ユーザー操作フロー全体 | 低速 | 実際のブラウザ・API |

TDDで書くテストは主に**単体テスト**。統合テスト・E2Eテストは別途計画する。

## テストケースの網羅観点

### 1. 正常系（Happy Path）

- 仕様通りの入力で期待通りの出力が返るか
- 代表的なユースケースを最低1件

### 2. 異常系（Error Cases）

- 不正な入力（バリデーションエラー）
- 権限エラー（認証・認可）
- 外部依存の失敗（DB接続エラー、API障害など）
- 各エラーが仕様通りの形式で返されるか

### 3. エッジケース（Boundary Cases）

**数値の境界値:**
- 最小値 / 最小値-1 / 最大値 / 最大値+1
- 0・負数・整数/小数の境界

**文字列の境界値:**
- 空文字 / 1文字 / 最大長 / 最大長+1

**コレクションの境界値:**
- 空リスト / 1件 / 最大件数

**null・未入力系:**
- null / undefined / 空オブジェクト

### 4. 状態・条件の組み合わせ

複数の条件が絡む場合は等価クラス分割を使う。

- 有効な入力グループから代表値を選ぶ（正常系）
- 無効な入力グループから代表値を選ぶ（異常系）
- 全組み合わせをテストする必要はない。リスクの高い組み合わせを優先する

### 5. フロントエンド固有の観点

- 初期表示: データなし・ローディング中・エラー状態
- ユーザー操作: クリック・入力・フォーム送信
- APIレスポンスの成功・失敗による状態変化
- 条件付きレンダリング（要素の表示/非表示）

## テストの品質基準

- **独立性**: 他のテストに依存せず単独で実行できる
- **再現性**: 何度実行しても同じ結果になる（フレーキーテストを作らない）
- **1テスト1シナリオ**: 1テストが検証するシナリオを1つに絞る。同一シナリオ内で複数のアサーションをまとめてよい
- **命名**: テスト名でシナリオ（条件・状況）と期待結果がわかるようにする

```
# シナリオ + 期待結果が伝わる命名
test_カートが空のとき_合計金額は0を返す
test_負の価格を指定したとき_商品追加はバリデーションエラーになる
test_認証済みユーザーが自分のデータを取得するとき_200と該当データが返る
test_未認証ユーザーが保護リソースにアクセスするとき_401が返る
```

## コミットメッセージの規約

テストコードのコミットには `test:` プレフィックスを使う。

```
test: ユーザー登録APIの異常系テストを追加
test: カート合計金額の境界値テストを追加
```
