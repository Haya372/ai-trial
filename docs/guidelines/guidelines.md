# 開発ガイドライン

## 設計原則

### DRY（Don't Repeat Yourself）

同じロジックや知識を複数の場所に重複して記述しない。重複はバグや変更漏れの原因になる。共通処理は関数・モジュールに切り出して再利用する。

### YAGNI（You Ain't Gonna Need It）

今必要でない機能は実装しない。将来の要件を先読みして作り込むと、不要なコードが増え保守コストが上がる。実際に必要になった時点で追加する。

### KISS（Keep It Simple, Stupid）

シンプルさを優先する。複雑な解決策より単純な解決策を選ぶ。コードは書いた人以外が読むものと考え、理解しやすさを重視する。

## SOLID原則

### Single Responsibility Principle（単一責任の原則）

クラスや関数は1つの責務のみを持つ。変更理由が1つになるよう設計する。

### Open/Closed Principle（開放閉鎖の原則）

拡張に対して開き、修正に対して閉じる。既存コードを変更せずに機能を追加できる構造にする。

### Liskov Substitution Principle（リスコフの置換原則）

派生クラスは基底クラスの代わりに使えるように設計する。

### Interface Segregation Principle（インターフェース分離の原則）

使わないインターフェースに依存させない。インターフェースは必要最小限に分割する。

### Dependency Inversion Principle（依存関係逆転の原則）

上位モジュールは下位モジュールに依存しない。どちらも抽象に依存する。

## コードコメント

- WHYが自明でない場合のみコメントを書く
- コードが何をしているかではなく、なぜそうしているかを書く
- 古くなったコメントはコードより有害なので定期的に見直す

## コミットメッセージ

- 1行目: 変更の要約（命令形、50文字以内）
- 本文: 必要に応じてWHYを説明（72文字で折り返し）
- 種別プレフィックスを使う（例: `feat:`, `fix:`, `docs:`, `refactor:`）
