# 開発フロー

このフローは使用するAIツール（Claude Code / Codex / Gemini CLI等）によらず共通。
各ステップの「担当Agent」は工程の責務を表す。Claude Codeではsubagentとして呼び出し、
それ以外のツールでは同一セッション内で該当のSkillファイル（`AGENTS.md` を参照）を見ながら進める。

## フロー概要

```text
PRD作成 → Issue作成 → 仕様定義 → sub-issue起票 → 詳細設計 → TDD実装 → PRレビュー → マージ
```

PRDと仕様書はそれぞれPRとしてmainにマージしてから次のステップへ進む。

## 各ステップ

### 1. PRD作成

- **担当Agent**: pdm
- **成果物**: `docs/prd/` 配下のPRDドキュメント
- PRDをPRとしてmainブランチにマージする
- `docs/prd/template.md` に沿って記述する

### 2. Issue作成

- **担当Agent**: pdm
- **成果物**: GitHubのIssue（機能単位の親Issue）
- マージしたPRDをもとに機能単位のIssueを作成する
- IssueにはPRDへの参照を含める

### 3. 仕様定義

- **担当Agent**: pdm（詳細仕様）・designer（ドメインモデル・DB設計・API設計）
- **成果物**: `docs/spec/` 配下の仕様書ドキュメント、`docs/domain/` 配下のドメインモデル
- PRDをもとに詳細仕様とドメインモデル・DB設計・API設計を作成する
- `docs/spec/template.md` に沿って記述する
- PDM合意後にステータスを `PDM合意済` に更新し、PRとしてmainブランチにマージする
- 仕様変更時は仕様書を更新し、PDMの再合意を得る
- 実装完了後はステータスを `アーカイブ` に更新する

### 4. sub-issue起票

- **担当Agent**: pdm
- **成果物**: GitHubのsub-issue
- マージ済み仕様書の設計（ドメインモデル・DB設計・API設計）をもとに、親Issueを実装単位のsub-issueに分割する
- 分割の基準・順序は `create-sub-issue` スキルに従う

### 5. 詳細設計

- **担当Agent**: designer
- **成果物**: 設計ドキュメント・ADR
- sub-issueごとに、仕様書の設計を前提としてレイヤー内部の設計（UseCase・コンポーネント構成・画面など）を行う
- 仕様書の設計を変更する必要が出た場合は、仕様書を更新してPDMの再合意を得る
- 重要な意思決定は `write-adr` スキルでADRに残す

### 6. TDD実装

- **担当Agent**: implementer
- **成果物**: テストコード・実装コード
- 設計ドキュメントのインターフェースに従って実装する
- Red-Green-Refactorサイクルを厳守する（テストを先に書く）
- 実装・テストが完了したら、ユーザーの確認を挟まずに次の「7. PRレビュー」まで連続して進める

### 7. PRレビュー

- **担当Agent**: qa
- **成果物**: レビューコメント・承認
- テストカバレッジと要件との整合性を確認する
- 実装完了後、以下を連続して実行する（各ステップの完了ごとにユーザーへ確認しない）
  1. `commit` スキルでコミットする
  2. `create-pr` スキルでPRを作成する
  3. `code-review` スキルでPRをレビューし、`--comment` オプションで日本語のインラインコメントを投稿する
- ユーザーへの確認は、レビューコメントの投稿が完了した後に行う

### 8. マージ

- レビュー承認後にmainブランチへマージする

## ユーザー確認ポイント

ユーザーの確認を待つのは以下の場面に限る。これ以外では確認のために止まらず、次の作業へ進む。

| 場面 | 工程・スキル | 理由 |
|---|---|---|
| PRDの要件が不足している | `requirements-definition` | 要件はユーザーにしか決められない |
| 仕様書（詳細仕様・ドメインモデル・DB設計・API設計）の合意 | `specification` | sub-issue分割と後続の設計すべての前提になる |
| sub-issue分割案の承認 | `create-sub-issue` | 複数Issueの起票は取り消しコストが高い |
| 既存ADRでカバーされない技術判断、既存ADRの見直し | `detailed-design`・`create-sub-issue` | 判断を後から覆すと手戻りが大きい |
| 仕様書の設計を変更する必要が出た | `detailed-design` | 合意済みの前提が変わる |
| レビューコメントの対応要否・方針を判断できない | `review-response` | 根拠をもって判断できない場合のみ |
| PRのマージ | 全工程 | マージはユーザーが行う |
| レビューコメント投稿の完了報告 | 7. PRレビュー | 実装サイクルの区切り |

以下では確認を求めずに進める。

- `start-issue` で次の工程が決まった後（そのまま次のスキルへ進む）
- 仕様書の合意後の引き継ぎ（PRを作成し、マージを依頼する）
- 詳細設計で仕様書に記載済みの内容の再確認
- 単一Issueの起票（`create-issue`）
- レビュー対応のタスクリスト（判断できるものはそのまま実装する）

## PR分割ガイドライン（gh-stack）

### PRを分割するタイミング

**複数の独立した関心事が混在している場合** は、gh-stackを使ってスタックPRに分割する。

独立した関心事の例：

- DBスキーマ変更 / マイグレーション
- APIエンドポイント（エンドポイントごとに1PR）
- フロントエンドのUI実装
- 認証・認可の追加

1つのPRは「1つの関心事 = 1つのレビュー単位」を目安にする。

### gh-stack の基本的な使い方

```bash
# 1. スタックを初期化（mainブランチをベースに）
gh stack init

# 2. 分割した単位で実装・コミットし、次のブランチを追加
gh stack add <branch-name>

# 3. 全ブランチをプッシュしてGitHubにスタックPRをまとめて作成
gh stack submit

# 4. レビュー後に修正が入った場合、対象ブランチで修正しリベース
gh stack rebase

# 5. 全PRがApproveされたらスタックをマージ
gh stack merge
```

詳細な手順は `stack-pr` スキルを参照。
