# バックエンド レビュー観点

## セキュリティ

- SQLインジェクション・コマンドインジェクションのリスクがないか（プレースホルダを使っているか）
- 認証・認可が必要な操作に漏れなく適用されているか
- 機密情報（APIキー・パスワード・トークン）がハードコーディングされていないか
- エラーレスポンスが内部情報（スタックトレース・DBスキーマ）を漏らしていないか（`docs/guidelines/design-guidelines.md` のセキュリティ制約参照）
- 入力バリデーションがシステム境界（HTTPリクエスト・外部API）で実施されているか
- 認証トークンの有効期限・失効処理が実装されているか
- ログにPII（個人識別情報: メールアドレス・電話番号・氏名等）が出力されていないか

## 設計・SOLID原則

`docs/guidelines/guidelines.md`・`docs/guidelines/design-guidelines.md` の原則に沿っているか確認する。

- 単一責任: 関数・構造体・クラスが1つの責務のみを持つか
- 開放閉鎖: 既存コードを変更せずに機能追加できる構造か
- リスコフ置換: インターフェースの実装が契約を守っているか
- インターフェース分離: 使わないメソッドへの依存が発生していないか
- 依存逆転: 具体実装ではなく抽象（インターフェース）に依存しているか
- レイヤー設計: Controller / Service / Repository の責務が混在していないか
- ビジネスルールがドメイン層に集約されているか（インフラ層に漏れていないか）

## パフォーマンス

- N+1クエリが発生していないか（ループ内でのDB問い合わせ）
- 必要なカラムのみ取得しているか（`SELECT *` の不適切な使用）
- インデックスが必要なカラムに付与されているか
- 大量データを一度にメモリへ読み込んでいないか（ページネーション・カーソル）
- 不必要な繰り返しDB問い合わせをキャッシュで回避できるか

## エラー処理

`docs/guidelines/design-guidelines.md` のAPIエラー定義に沿っているか確認する。

- エラーが握りつぶされていないか（`_` で無視・ログだけして継続）
- エラーの種類が適切に区別されているか（バリデーションエラー vs システムエラー）
- ユーザーへのエラーレスポンスが適切なHTTPステータスコードを返しているか
- エラーにコンテキスト情報（操作名・IDなど）がラップされているか
- パニック・例外のリカバリーが適切に行われているか

## API設計

- RESTの原則に沿ったエンドポイント設計か（リソース名・HTTPメソッドの使い分け）
- レスポンスの形式が既存APIと一貫しているか
- ページネーションが必要な一覧エンドポイントに実装されているか
- 破壊的変更がバージョニングなしに行われていないか

## テスタビリティ

- 外部依存（DB・外部API・時刻）が依存注入でテスト可能になっているか
- 関数が副作用を最小化しているか（純粋関数に近いか）
- DRY: 同じロジックが複数箇所に重複していないか
- YAGNI: 現時点で不要な機能・抽象化がないか
