# バックエンド レビュー観点

## ガイドライン準拠

以下のガイドラインに沿っているか確認する。

- `docs/guidelines/guidelines.md` — 設計原則（SOLID・DRY・YAGNI・KISS・コメント）
- `docs/guidelines/design-guidelines.md` — バックエンド設計（レイヤー・API設計・エラー定義）
- `docs/guidelines/observability-guidelines.md` — ログ・メトリクス・トレーシング
- `docs/guidelines/data-handling-guidelines.md` — 情報のDBへの保存方法と、APIレスポンス・ログ・トレースに出してよい情報
- `docs/guidelines/transaction-guidelines.md` — トランザクション管理（DBへの書き込みを伴うCommandの実装）

## レビュー固有の観点

ガイドラインに定義されていないが、PRで確認が必要な観点。

### セキュリティ

- SQLインジェクション・コマンドインジェクションのリスクがないか（プレースホルダを使っているか）
- 認証・認可が必要な操作に漏れなく適用されているか
- リクエストのIDでリソースを取得・更新・削除する操作で、リクエストしたユーザーがそのリソースの所有者（または共有先）かを確認しているか（他人のIDを指定して操作できないか）
- 機密情報（APIキー・パスワード・トークン）がハードコーディングされていないか
- 認証トークンの有効期限・失効処理が実装されているか
- ログイン時にセッションIDを新しく発行しているか（ログイン前のセッションIDを引き継いでいないか）
- トークンなどの秘密の値を `==` ではなく `subtle.ConstantTimeCompare` で比較しているか。パスワードは `bcrypt.CompareHashAndPassword` で照合しているか
- ログインなど総当たりされうるエンドポイントに、試行回数の制限があるか
- Cookie認証のAPIで、状態を変更する操作をGETで受けていないか
- CORSで、Cookieを送る（`Access-Control-Allow-Credentials: true`）レスポンスの `Access-Control-Allow-Origin` を、許可するオリジンとの完全一致で決めているか（リクエストの `Origin` をそのまま返す・`*`・前方一致や後方一致での照合・`null` の許可をしていないか）
- ユーザー入力をファイルパスに使う箇所で、`os.Root`（`os.OpenInRoot`）を使い、絶対パス・`..`・シンボリックリンクでベースディレクトリの外にアクセスできないようにしているか（`filepath.IsLocal` は文字列だけを検査し、シンボリックリンクを辿らない）
- ユーザー入力のURLへサーバーからリクエストする箇所で、許可したホストだけに送っているか。リダイレクト先（`http.Client` の `CheckRedirect`）と、接続時に解決したIPアドレス（`net.Dialer` の `Control`）も検証し、内部ネットワーク・メタデータエンドポイントに届かないようにしているか

### パフォーマンス

- N+1クエリが発生していないか（ループ内でのDB問い合わせ）
- 必要なカラムのみ取得しているか（`SELECT *` の不適切な使用）
- インデックスが必要なカラムに付与されているか
- 大量データを一度にメモリへ読み込んでいないか（ページネーション・カーソル）

### テスタビリティ

- 外部依存（DB・外部API・時刻）が依存注入でテスト可能になっているか
