# ADR-016: スキーマ駆動開発

- ステータス: 承認済

## コンテキスト

バックエンド（Go、ADR-003）とフロントエンド（TypeScript、ADR-005）は言語が異なるため、APIの型定義を直接共有できない。ADR-003の時点で「型定義の共有はコード生成（OpenAPI等）を介する必要がある」と言及されていたが、採用するスキーマフォーマットとコード生成ツールは未決定のままだった。

この状況では、API仕様の変更がコード変更に反映されない、またはフロントエンドとバックエンドで型の乖離が起きるリスクがある。スキーマをAPI仕様の定義元とし、そこからコードを自動生成することで、型安全なAPI通信と仕様の一元管理を実現する必要がある。

## スコープ外

- OpenAPIスキーマの記述ルール・ファイル分割方針（運用ルールとして別途定義する）
- コード生成ツールのCI/CD統合方法（パイプライン設計時に決定する）
- gRPC・GraphQLなどHTTP REST以外のプロトコル対応
- APIバージョニング戦略
- 生成コードのカスタマイズルール（テンプレートのオーバーライド等）

## 決定

APIスキーマフォーマットとして **OpenAPI 3.1** を採用する。

バックエンド（Go）のコード生成ツールとして **oapi-codegen** を採用する。
フロントエンド（TypeScript）のコード生成ツールとして **orval** を採用する。

OpenAPIスキーマファイルは `packages/schema/` で管理し、APIの仕様変更はスキーマファイルを先に変更してからバックエンド・フロントエンドのコードを生成する。

## 検討した選択肢

### 選択肢1: OpenAPI 3.1（oapi-codegen + orval）

#### 概要

OpenAPI 3.1のYAMLスキーマをAPI定義の参照元とする。バックエンドは `oapi-codegen` でGoの型定義とchi互換のサーバーインターフェースを生成し、フロントエンドは `orval` でTypeScriptの型定義とTanStack QueryフックAPIを生成する。

#### メリット

- OpenAPIは業界標準で、ツールエコシステムが最も成熟している
- `oapi-codegen` はchiの `net/http` 互換コードを生成するため、ADR-004の決定（chi採用）と完全に整合する
- `orval` はTanStack Query（React Query v5）のフックを直接生成するため、ADR-007の決定と完全に整合する
- バックエンドとフロントエンドの双方がスキーマから生成された型を使うため、APIの変更がコンパイルエラーとして検出できる
- スキーマファイル単体でAPIドキュメントとして機能する

#### デメリット

- API仕様の変更時はスキーマファイルの更新 → コード生成 → 実装更新という手順が必要で、直接コードを変更するより手順が増える
- 生成コードがスキーマから外れた実装を書けないため、スキーマ設計の品質がAPIの品質に直結する

### 選択肢2: Go コードファースト（swaggo/swag によるスキーマ生成）

#### 概要

Goのソースコードにswaggoアノテーションを記述し、そこからOpenAPIスキーマを生成する。生成されたスキーマをフロントエンドのコード生成に利用する。

#### メリット

- Goコードを書くことでスキーマが自動生成されるため、スキーマファイルを別途管理する必要がない
- 実装と仕様が同じファイルに存在するため、アノテーションのコードコメントを見れば仕様を確認できる

#### デメリット

- アノテーションが増えることでGoコードの可読性が低下し、ADR-001のClean Architectureのレイヤー設計の妨げになる
- アノテーションを書き忘れた場合にスキーマとコードが乖離し、型安全性が崩れる
- フロントエンドのコード生成がバックエンドのビルドパイプラインに依存するため、フロントエンド単体での開発が難しくなる

### 選択肢3: gRPC + Protocol Buffers

#### 概要

`.proto` ファイルでAPIスキーマを定義し、gRPCでバイナリ通信する。`protoc-gen-go` でGoコードを、`protoc-gen-ts` でTypeScriptコードを生成する。

#### メリット

- バイナリシリアライゼーションによる高い通信効率
- Protocol Buffersによる厳格な型定義と後方互換性の管理
- ストリーミングRPCにより、将来的なリアルタイム通知（PRD-006）を同一プロトコルで実現できる

#### デメリット

- ADR-004でchiとREST APIを採用済みであり、gRPCへの切り替えはWebフレームワーク変更を伴う大きな設計変更になる
- ブラウザから直接gRPCを呼ぶには `grpc-web` が必要で、プロキシ設定の運用コストが発生する
- OpenAPIに比べてエコシステムが限られており、APIドキュメントの閲覧・テストツールの選択肢が少ない

## 決定理由

- **既存ADRとの整合**: ADR-004でchi（`net/http` 互換）を採用済みのため、`oapi-codegen` が生成する `net/http` 互換のサーバーインターフェースはそのまま利用できる。ADR-007でTanStack Queryを採用済みのため、`orval` が生成するReact Queryフックはそのまま利用できる。gRPCへの切り替えはADR-004を覆す変更になるため採用しない
- **型安全性の確保**: スキーマからGoとTypeScriptの双方のコードを生成することで、APIの変更が型エラーとして即座に検出できる。コードファーストのswaggoはアノテーションの書き忘れで型安全性が崩れるため採用しない
- **フロントエンドの独立性**: スキーマファイルを `packages/schema/` で独立管理することで、フロントエンドはバックエンドのビルドに依存せずにスキーマからコードを生成できる。コードファーストのアプローチではこの独立性が保てない
- **OpenAPIエコシステム**: ADR-003でGoとTypeScriptの型共有に「OpenAPI等のコード生成」を言及しており、プロジェクトの当初想定と一致する。OpenAPIはAPIドキュメントとしても機能し、Swagger UIなどのツールとも連携しやすい

## 結果

### 良い影響

- バックエンド（Go）とフロントエンド（TypeScript）がスキーマから生成された型を共有するため、APIの変更が型エラーとして検出できるようになり、型の乖離リスクがなくなる
- `oapi-codegen` が生成するサーバーインターフェースを実装するGoコードは、コンパイル時に全エンドポイントの実装有無が確認できる
- `orval` が生成するTanStack Queryフックにより、APIクライアントの実装コードを手書きする必要がなくなる
- `packages/schema/` のスキーマファイルがAPIドキュメントとして機能するため、別途ドキュメントを維持する必要がない

### 悪い影響

- API仕様の変更手順がスキーマ変更 → コード生成 → 実装更新という順序に固定されるため、直接コードを変更する開発スタイルと比べて手順が増える
- 生成コードは手動で編集してはならず、スキーマを経由して変更する規律がチームに必要になる
- スキーマ設計のスキルがAPI品質に直結するため、OpenAPI記述の学習コストが発生する
