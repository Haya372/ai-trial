# ADR-036: APIで扱う日時のタイムゾーン

- ステータス: 承認済
- 関連Issue: #350
- 関連ADR: ADR-013（APIエラー構造）, ADR-016（スキーマ駆動開発）

## コンテキスト

カレンダーの予定取得API（`GET /events`）は、表示期間を `YYYY-MM-DD` 形式の日付（`startDate` / `endDate`）で受け取り、バックエンドでUTCの0時として解釈していた。クライアントはローカル日付を送るため、UTC以外のタイムゾーンのユーザーでは検索範囲が時差の分ずれる。例えばJSTのユーザーでは、2026-11-01 05:00 JST（2026-10-31 20:00 UTC）の予定が11月の月ビューに出ず、10月の月ビューに出る。

「1日の区切り」はユーザーのタイムゾーンに依存するため、日付だけを受け渡すAPIでは、どこかでタイムゾーンを補う必要がある。この問題を個別に直すのではなく、APIで日時を受け渡すときのタイムゾーンの扱いを決める。

また、DBの日時カラムは `TIMESTAMPTZ` で、時刻そのもの（瞬間）を保存している。一方、DBアクセスに使うpgx（ADR-009）は、`TIMESTAMPTZ` を読み取ると、デフォルトではアプリケーションサーバーのローカルタイムゾーンの `time.Time` を返す。そのため、レスポンスの日時に付くオフセットは、サーバーのタイムゾーン設定によって変わる。

選択肢は以下の観点で評価する。

- 分かりやすさ: APIの利用者・実装者が、日時の形式とタイムゾーンを迷わず判断できるか
- 正確さ: 夏時間を含め、ユーザーのローカルの1日・1週・1ヶ月の区切りで正しく検索できるか
- 実装の単純さ: バックエンドにタイムゾーンの計算やタイムゾーンデータベースを持ち込まずに済むか

## スコープ外

- 予定の表示・入力をユーザーのローカルタイムゾーン以外（ユーザー設定のタイムゾーンなど）で行う機能
- 終日予定の表現方法
- ログ・監査ログに記録する日時の形式（ADR-014, ADR-018）

## 決定

1. APIで受け渡す日時は、リクエスト・レスポンスともにUTCで表したRFC3339形式（末尾が `Z`）に統一する。例: `2026-10-31T15:00:00Z`。秒の小数部は任意とする
2. リクエストの日時（クエリパラメータ・リクエストボディ）は、末尾が `Z` のものだけを受け付ける。`+09:00` や `+00:00` などのオフセット表記は、同じ瞬間を表していても 400 `VALIDATION_ERROR`（ADR-013）を返す
3. 「1日」「1週」「1ヶ月」のようなローカルの区切りが必要な範囲指定では、APIは日付ではなく日時の範囲を受け取る。区切りの計算はクライアントがユーザーのローカルタイムゾーンで行い、結果をUTCに変換して送る。範囲は開始を含み、終了を含まない（`[開始, 終了)`）
4. `GET /events` の検索範囲は、クエリパラメータ `startAt` / `endAt`（決定1の形式）で受け取る。`startDate` / `endDate` は廃止する。`endAt` が `startAt` 以前の場合は 400 `VALIDATION_ERROR` を返す
5. バックエンドは、pgxの `TIMESTAMPTZ` の読み取り先タイムゾーン（`ScanLocation`）をUTCに設定する。DB接続の作成時に1か所で設定し、レスポンスの日時がサーバーのタイムゾーン設定に依存しないようにする
6. OpenAPIスキーマ（ADR-016）の日時項目は `format: date-time` とし、`description` にUTC（末尾 `Z`）であることを書く

## 検討した選択肢

### 選択肢1: 日時をUTCに統一し、区切りの計算はクライアントで行う（採用）

#### 概要

APIの日時はすべてUTC（末尾 `Z`）とする。ローカルの区切りが必要な範囲は、クライアントが計算したUTCの日時範囲で送る。

#### メリット

- 日時の形式が1種類になり、リクエスト・レスポンスのどちらでも迷わない
- 区切りは、表示に使うのと同じクライアントのタイムゾーン情報で計算するため、夏時間をまたぐ期間でも正しい
- バックエンドは受け取った瞬間を比較するだけで、タイムゾーンの計算が不要になる

#### デメリット

- `GET /events` のクエリパラメータの名前と形式が変わり、既存のクライアントとの互換性がなくなる
- オフセット付きの日時を送るクライアントは、UTCに変換してから送る必要がある

### 選択肢2: 日付とIANAタイムゾーン名を受け取り、バックエンドで区切りを計算する

#### 概要

`startDate` / `endDate` を残し、`timezone=Asia/Tokyo` のようなIANAタイムゾーン名を追加する。バックエンドが `time.LoadLocation` でローカルの0時をUTCに変換する。

#### メリット

- 既存のクエリパラメータを残せる
- 夏時間を含めて正しく計算できる

#### デメリット

- バックエンドの実行環境にタイムゾーンデータベースが必要になる
- 区切りの計算がクライアント（表示）とバックエンド（検索）に分かれ、両者のタイムゾーンデータの差で結果が食い違う可能性がある
- レスポンスの日時の形式は別途決める必要があり、日時の扱いが統一されない

### 選択肢3: 日付と分単位のUTCオフセットを受け取る

#### 概要

`startDate` / `endDate` を残し、`tzOffset=540` のようなオフセット（分）を追加する。

#### メリット

- 既存のクエリパラメータを残せる
- バックエンドにタイムゾーンデータベースが不要

#### デメリット

- オフセットは1つの値なので、夏時間をまたぐ期間（例: 3月の月ビュー）では範囲の片端が1時間ずれる
- 選択肢2と同じく、日時の扱いが統一されない

### 選択肢4: オフセット付きの日時を任意のオフセットで受け付ける

#### 概要

選択肢1と同じく日時範囲を受け取るが、`Z` に限らず `+09:00` などのオフセット表記も受け付け、バックエンドでUTCに変換する。

#### メリット

- クライアントがローカル時刻をそのまま送れる

#### デメリット

- 同じ瞬間に複数の表記があり、APIの利用者・実装者が形式を判断しにくい
- レスポンスとリクエストで表記がそろわない

## 決定理由

- 分かりやすさ: 選択肢1は日時の表記をUTC（末尾 `Z`）の1種類に限定する。選択肢4は同じ瞬間に複数の表記を許し、選択肢2・3は日付と日時が混在する
- 正確さ: 選択肢1は、区切りの計算をクライアントのタイムゾーン情報で行うため、夏時間をまたぐ期間でも正しい。選択肢3は夏時間をまたぐ期間で誤差が出る
- 実装の単純さ: 選択肢1は、バックエンドが瞬間の比較だけを行えばよい。選択肢2はタイムゾーンデータベースと区切りの計算をバックエンドに持ち込む

互換性がなくなるデメリットについては、`GET /events` の利用者が自前のWebクライアントだけで、APIとクライアントを同じPRで更新できるため、影響は小さいと判断した。

## 検証結果

- JavaScriptの `Date.prototype.toISOString()` が、実行環境のタイムゾーンによらずUTC（末尾 `Z`、ミリ秒付き）を返すことを確認した。`new Date(2026, 10, 1).toISOString()` は、`Asia/Tokyo` で `2026-10-31T15:00:00.000Z`、`America/New_York` で `2026-11-01T04:00:00.000Z` を返す
- pgx v5.10.0 の `pgtype.TimestamptzCodec` が、`ScanLocation` が未設定の場合は `time.Unix` で生成したローカルタイムゾーンの `time.Time` を返し、設定した場合はそのタイムゾーンに変換することを、ソースコードで確認した

## 結果

### 良い影響

- UTC以外のタイムゾーンのユーザーでも、月・週ビューの境界の予定が正しい期間に表示される
- APIの日時の形式が1種類になり、新しいエンドポイントでも同じ規則に従えばよい
- レスポンスの日時が、アプリケーションサーバーのタイムゾーン設定に依存しなくなる

### 悪い影響

- `GET /events` のクエリパラメータが変わるため、APIとWebクライアントを同時に更新する必要がある。同じPRで両方を変更して対処する
- 決定2により、オフセット付きの日時を受け付けていた既存のエンドポイント（予定の作成・更新、共有リンクの作成）は、受け付ける形式が狭くなる。Webクライアントはこれらのリクエストで `toISOString()` の値を送っているため影響はない。これらのエンドポイントへの検証の追加は、Issueを起票して対応する
