# ADR-041: バウンス通知受信エンドポイントの認証と内部形式

- ステータス: 提案中

## コンテキスト

PRD-010 のメール通知基盤では、送信したメールのバウンス通知を受け取って送信履歴に記録する必要がある。多くのメール送信サービスはバウンス通知を Webhook（HTTPS POST）でアプリケーションへ送る。

ADR-038 で送信サービスの選定を後ろ倒しし、アプリケーションは送信サービスに非依存な抽象に閉じている。バウンス通知の受信も、送信サービスを特定しない前提で設計する必要がある。

選定観点:

- 送信サービスを特定しない状態でもエンドポイントを実装できること
- 多くの送信サービスの Webhook 設定で指定できる認証方式であること（送信サービスが任意の `Authorization` ヘッダーを付けられないケースが多い）
- 送信サービスが変わっても、受け口のエンドポイントと内部処理を保てる構造にできること
- 受信した通知の送信元がアプリケーションの意図した送信サービスであることをなりすましから守れること

送信サービス側の制約:

- クラウドの通知サービス（例: Amazon SNS）や多くの SaaS 系送信サービスの Webhook 設定は、任意の `Authorization` ヘッダーを登録できない場合がある
- ほぼ全ての送信サービスは、Webhook URL に `https://<user>:<pass>@host/path` 形式の Basic 認証クレデンシャルを含めることを許容する

## スコープ外

- 本番で使う送信サービス（具体ベンダー）の選定（[ADR-038](./ADR-038-email-transport-protocol.md) で後ろ倒し）
- 送信サービス固有の Webhook ペイロード（JSON の形・フィールド名・必須項目）を内部形式へマップする具体仕様（送信サービス選定時に SPEC-010 へ追記）
- ネットワークレベルの IP 許可リスト・WAF・リバースプロキシ（インフラ運用）
- クレデンシャルの自動ローテーション（運用で手動対応）

## 決定

1. バウンス通知は `POST /webhooks/email-bounces` エンドポイントで受ける
2. エンドポイントは **Basic 認証** で保護する。送信サービスの Webhook URL 設定に `https://<user>:<pass>@host/webhooks/email-bounces` の形で埋め込む
3. 認証情報は環境変数 `EMAIL_BOUNCE_WEBHOOK_USER` と `EMAIL_BOUNCE_WEBHOOK_PASSWORD` で与え、比較は `crypto/subtle.ConstantTimeCompare` による定数時間比較で行う。未設定（空文字）の場合は全リクエストを拒否する（fail closed）
4. 認証に失敗したときは 401 を返し、`WWW-Authenticate: Basic realm="email-bounces"` ヘッダーを付ける
5. エンドポイントは送信サービス固有のペイロードを受け取り、**受け口のアダプタ層で内部形式** `BounceNotification{messageId, bounceType, occurredAt}` へ変換する。ユースケース層はこの内部形式だけに依存する
6. 送信サービス選定後に、具体的なペイロード形式と内部形式へのマッピング（フィールド名・値域変換）を SPEC-010 へ追記する
7. アクセスログに Basic 認証クレデンシャルを残さないため、ミドルウェア・プロキシのログ設定で URL のユーザー情報部分・`Authorization` ヘッダーをマスクする運用を Issue で追加する

## 検討した選択肢

### 選択肢1: Basic 認証（URL 埋め込み）+ 受け口アダプタで内部形式へ変換（採用）

#### 概要

Webhook エンドポイントを RFC 7617 の Basic 認証で保護する。送信サービスには `https://<user>:<pass>@host/webhooks/email-bounces` 形式で URL を設定する。送信サービス固有のペイロードは、Infrastructure 層のアダプタで内部形式に変換してユースケースに渡す。

#### メリット

- RFC 7617 の標準で、ほぼ全ての送信サービスの Webhook URL 設定で使える（任意の `Authorization` ヘッダーを登録できない送信サービスでも URL に埋め込める）
- 固定クレデンシャルで検証がシンプルで、`crypto/subtle.ConstantTimeCompare` で定数時間比較できる
- 送信サービス固有のペイロードはアダプタ層で吸収するため、送信サービスを切り替えてもエンドポイント・ユースケース層のコードは変わらない

#### デメリット

- URL に平文クレデンシャルが含まれるため、アクセスログ・エラーログ・リバースプロキシのログに残らないように設定する運用が必要
- HTTPS 前提でないとネットワーク経路で平文が流れる（本プロジェクトは全環境 HTTPS 前提で問題ない）
- クレデンシャルが漏洩したときはなりすまし送信を防げない（IP 許可リストなど別レイヤの保護を併用する）

### 選択肢2: HTTP ヘッダー `Authorization: Bearer <token>` 認証

#### 概要

Webhook エンドポイントを Bearer Token 認証で保護する。送信サービスの Webhook 設定に任意の `Authorization` ヘッダーを登録する必要がある。

#### メリット

- URL に平文クレデンシャルが入らず、アクセスログに残らない
- `/metrics` の認証（ADR-032）と同じパターンで、プロジェクト内で統一できる

#### デメリット

- Webhook 設定で任意の `Authorization` ヘッダーを登録できない送信サービスでは成立しない（SNS など代表的な通知サービスで対応不可）
- 送信サービスを特定しない前提では、どの送信サービスでも使える方式を選ぶ必要があり、採用できない

### 選択肢3: 送信サービス固有の署名検証（HMAC・公開鍵署名等）

#### 概要

送信サービスが Webhook ペイロードに付ける署名（HMAC または公開鍵署名）をアプリケーション側で検証する。

#### メリット

- クレデンシャルが URL に入らず、なりすまし耐性が最も高い
- ペイロードの改ざんも検出できる

#### デメリット

- 送信サービスごとに署名アルゴリズム・ヘッダー名・検証手順が異なり、送信サービスを特定しないと実装できない
- 送信サービスを切り替えるたびに検証ロジックを書き直す必要がある
- 送信サービス未定の段階で採用できない

### 選択肢4: IP アドレス許可リストのみ

#### 概要

送信サービスの Webhook 発信元 IP アドレスを許可リストで絞る。

#### メリット

- アプリ側の認証実装が不要
- クレデンシャル管理が不要

#### デメリット

- 送信サービスの IP 範囲が公開されていない・頻繁に変わる場合に実用的でない
- 送信サービスを特定しない現時点では IP 範囲が分からない
- アプリ層単独での保護にならず、インフラ側の設定に依存する

## 決定理由

- **送信サービス非依存**: Basic 認証は RFC 7617 の標準で、Webhook URL に埋め込める。送信サービスを特定しない段階でも採用できる唯一の HTTP 認証方式
- **実装の単純さ**: ADR-032 の Bearer 認証実装（`crypto/subtle.ConstantTimeCompare`）と同じパターンで実装でき、プロジェクト内で検証ロジックを揃えられる
- **送信サービス切替の容易性**: 送信サービスを後から変えても、受け口アダプタで内部形式に変換する構造なら、エンドポイント・ユースケース層の変更は不要
- **選択肢3を選ばない理由**: 送信サービスごとの固有仕様が必要で、現時点で実装できない。送信サービス選定後に本ADRを置き換えて署名検証へ移行する余地は残す
- **選択肢4を選ばない理由**: アプリ層の認証がなく、ネットワーク層だけに依存するためアプリ単独では完結しない

## 結果

### 良い影響

- 送信サービスを特定しない段階でエンドポイント実装を進められる
- 送信サービスを切り替えても、受け口アダプタの実装を差し替えるだけで済み、ユースケース層・エンドポイントの認証ロジックは変わらない
- `crypto/subtle.ConstantTimeCompare` による定数時間比較で、タイミング攻撃に対する最低限の保護が得られる

### 悪い影響

- URL に平文クレデンシャルが含まれるため、アクセスログ・エラーログ・リバースプロキシのログでクレデンシャル部分をマスクする運用が必要（マスク設定の追加は実装 Issue で扱う）
- クレデンシャルの手動ローテーションが必要（運用で対応）
- 送信サービス選定後に、より強力な署名検証方式が利用可能であれば、本 ADR を置き換えて移行する余地を残す
