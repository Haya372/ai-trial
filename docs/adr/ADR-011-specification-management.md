# ADR-011: 仕様書の管理方針

- ステータス: 承認済

## コンテキスト

PRD作成後・詳細設計前に、PDMと開発者が実装内容について合意するための仕様定義フェーズを設ける。
その際に作成する仕様書をどこで管理するかを決定する必要がある。

仕様書は変更されうるものであり、管理方針として「腐らせない仕組み」を持つことが重要。

## スコープ外

- PRD自体の管理方針（既存の `docs/prd/` 管理を継続）
- 詳細設計ドキュメント・ADRの管理方針（既存の `docs/adr/` 管理を継続）

## 決定

仕様書をGitリポジトリの `docs/spec/` 以下で管理する。
腐化防止のため、ステータスフィールドの明示・PR紐付け・アーカイブポリシーを運用ルールとして定める。

## 検討した選択肢

### 選択肢1: Gitリポジトリ管理（`docs/spec/` 以下）

#### 概要

仕様書をMarkdownファイルとして `docs/spec/` に保存し、Gitで管理する。

#### メリット

- 既存のドキュメント管理（PRD・ADR）と一貫性がある
- バージョン履歴が残り、仕様の変遷を追える
- 全Agentがファイルパスでアクセスでき、詳細設計・実装の入力として使いやすい
- PRレビューで仕様変更を明示的に承認できる

#### デメリット

- 実装完了後に更新されなければ腐化するリスクがある
- 管理ルールを徹底しないとファイルが溜まり続ける

### 選択肢2: 外部ツール管理（Notionなど）

#### 概要

仕様書をNotion等の外部ツールで管理する。

#### メリット

- コメント・承認フローのUIが使いやすい

#### デメリット

- AgentがURLアクセスしにくく、詳細設計・実装の入力として使いにくい
- リポジトリと分離しており、コードとの対応関係が不明確になる

### 選択肢3: 永続化しない（Issue・PRのコメントに残す）

#### 概要

ファイルとして作成せず、合意内容をIssueコメントまたはPR本文に記録する。

#### メリット

- 腐化するファイルが残らない
- コードの変更と同じPRで仕様の変更を追える

#### デメリット

- AgentがIssue/PRのコメントを参照するには追加のコンテキストが必要
- 仕様書の構造化が難しく、詳細設計への引き継ぎが煩雑になる

## 決定理由

AgentがファイルパスでアクセスできるGitリポジトリ管理が、詳細設計・実装フェーズとの連携において最も効率的。
腐化リスクは以下のルールで防ぐ：

- **ステータスフィールドの必須化**: 仕様書は常に `有効 / アーカイブ` のいずれかを明示する（マージされた = PDM合意済みとみなす）
- **仕様変更時の更新ルール**: 仕様変更時はPRで仕様書の更新も必須とする
- **実装完了後のアーカイブ**: 実装完了時にステータスを `アーカイブ` へ更新する（削除はしない）

## 結果

### 良い影響

- 仕様書がリポジトリに存在することで、Agentがファイルパスで参照でき、詳細設計・実装フェーズへの引き継ぎが明確になる
- PRマージを合意の記録として使うことで、運用コストを最小化しながら合意の証跡を残せる
- 実装完了後にアーカイブするルールにより、腐化した仕様書が「現役」として残り続けることを防げる
- git log で仕様の変遷を追うことができる

### 悪い影響

- 実装完了後のアーカイブ更新（ステータス変更）を手動で行う必要があり、忘れると有効・アーカイブの区別が曖昧になる
- 仕様変更時に仕様書の更新を徹底しないと、コードと仕様書の乖離が生じる
- `docs/spec/` にファイルが蓄積されていくため、長期的にはアーカイブ済みファイルが増える
