# ADR-008: データベース

- ステータス: 承認済

## コンテキスト

本プロジェクトはユーザー・予定・タグ・共有リンクといった相互に関連するデータを扱うカレンダーアプリであり、以下のデータ管理要件を満たすDBが必要となる。

- ユーザーと予定（PRD-001, PRD-003）、予定とタグ（PRD-008）、予定と共有URL（PRD-004）といったリレーショナルな構造を扱う
- 繰り返し予定（PRD-009）で「特定回だけ変更」「以降すべて変更」「すべて変更」の複雑な検索・更新クエリを効率的に処理する（期間検索・重複判定を含む）
- 予定の更新・削除・共有トークン発行など、整合性が重要な操作にACID保証が必要
- ADR-003で採用したGoから安全かつ生産的にアクセスできること
- スキーマ変更を継続的に管理できるマイグレーション運用が可能なこと

候補としてPostgreSQL、MySQL、MongoDBを検討する。

## スコープ外

- DBアクセスライブラリの選定はADR-009で扱う
- DBマイグレーションツールの選定はADR-010で扱う
- キャッシュストア（Redis等）の採用可否は本ADRの対象外
- 全文検索エンジン（OpenSearch等）の導入は本ADRの対象外
- 具体的なテーブル設計・カラム定義はドメインモデル設計（`docs/domain/`）で扱う
- レプリケーション・バックアップ戦略などインフラ運用は本ADRの対象外
- クラウド提供のマネージドDBサービスの選定は本ADRの対象外

## 決定

データベースとして **PostgreSQL 16以降** を採用する。

## 検討した選択肢

### 選択肢1: PostgreSQL

#### 概要

オープンソースの高機能RDBMS。SQL標準への準拠度が高く、JSONB・配列・範囲型（`tstzrange` 等）・拡張機能（GiST/GINインデックス等）を備える。長期運用実績が豊富。

#### メリット

- **繰り返し予定（PRD-009）との相性**: `tstzrange`（タイムゾーン付き期間型）と GiST インデックスにより、予定の期間重複検索・カレンダー範囲での予定取得が高速に実装できる。MySQL/MongoDBには相当機能がない
- **リレーショナル整合性**: 外部キー制約・チェック制約・トランザクションが強力で、ユーザー・予定・タグ・共有リンクの整合性を宣言的に担保できる
- **柔軟なデータ型**: JSONB型により、繰り返しルール（RRULE相当）や例外リスト、タグの表示設定など半構造化データも整合性を保ちつつ格納できる。JSONBはインデックス対応・演算子が豊富で、MySQLのJSON型より機能的
- **ACID保証**: 予定共有トークンの発行、繰り返し予定編集の「以降すべて」操作など、複数レコードにまたがる整合性が必要な操作をトランザクションで安全に実装できる
- **DDLのトランザクション対応**: DDL文（ALTER TABLE等）もトランザクション内で実行でき、マイグレーション失敗時のロールバックが安全
- **エコシステム成熟度**: 長期運用の実績・情報量が豊富で、パフォーマンスチューニング情報も揃っている
- **Goとの相性**: Go向けのPostgreSQL専用ドライバ（pgx等）が成熟しており、ADR-003のGoから型安全にアクセスできる

#### デメリット

- 機能が豊富な分、機能選択（インデックス種別、JSONBとJSONの使い分け等）に知識が必要
- MySQLに比べて運用ノウハウを持つ人材がやや少ない場面がある
- PostgreSQL固有機能（`tstzrange` / JSONB / GiST）を活用するほど、他RDBMSへの移植性は下がる

### 選択肢2: MySQL

#### 概要

Oracleが提供するオープンソースRDBMS。長年のWebアプリケーション実績があり、多くのマネージドサービスで採用されている。

#### メリット

- 運用実績が豊富で、DBAスキルを持つ人材が見つけやすい
- マネージドサービス（AWS RDS、GCP Cloud SQL等）での提供が広い
- レプリケーション・シャーディングの実績とノウハウが豊富

#### デメリット

- **繰り返し予定への弱さ**: 範囲型・GiSTインデックスといった時間範囲検索を最適化する機能がなく、繰り返し予定の期間重複検索を効率化するには自前でインデックス設計を工夫する必要がある
- **JSON型の機能差**: MySQLのJSON型はPostgreSQLのJSONBに比べてインデックス機能・演算子が弱く、繰り返しルールの半構造化データ格納で表現力が劣る
- **DDLの制約**: MySQLはトランザクション内DDLの制約がPostgreSQLより厳しく、マイグレーション運用で気を配る場面が多い
- **チェック制約の歴史的経緯**: MySQL 8.0以前はチェック制約が実質無効だった経緯があり、宣言的整合性の実績はPostgreSQLに一歩譲る

### 選択肢3: MongoDB

#### 概要

ドキュメント指向のNoSQLデータベース。BSON形式で柔軟なスキーマを扱え、水平スケール（シャーディング）が得意。

#### メリット

- スキーマレスにより、予定の追加属性（タグ、繰り返しルール等）を柔軟に埋め込める
- ドキュメント単位で予定と関連情報（タグ、参加者等）を一体で取得でき、JOINを避けられる
- 水平スケール（シャーディング）が容易

#### デメリット

- **リレーショナル要件との不一致**: ユーザー・予定・タグ・共有リンクの多対多・外部キー整合性を、アプリケーション側で担保する必要があり、実装コストと不整合リスクが増す
- **ACID保証の制約**: ドキュメント単位のACIDは強いが、複数コレクションをまたぐトランザクションはレプリカセット必須で、単体構成では利用できない場面がある。予定共有・繰り返し予定編集などの整合性担保が難しい
- **繰り返し予定検索の弱さ**: 時間範囲検索・重複検索でRDBMSの範囲型・GiST相当の機能がなく、パフォーマンス最適化が難しい
- **スキーマガバナンス**: スキーマレスであることでアプリケーション側にスキーマ責任が集中し、Clean Architecture（ADR-001）のDomain層とDBスキーマの乖離を検知しにくい
- **Goエコシステム**: MongoDB用のGoライブラリはRDBMS用に比べて選択肢が少ない

## 決定理由

- **リレーショナルデータへの適合**: ユーザー・予定・タグ・共有リンクは典型的なリレーショナル構造であり、外部キー制約・JOIN・トランザクションを言語機能として持つRDBMSが最適。MongoDBのドキュメント指向は本プロジェクトの要件と不一致
- **繰り返し予定（PRD-009）への最適解**: PostgreSQLの `tstzrange` + GiSTインデックスにより、期間重複検索・カレンダー範囲での予定取得を効率化できる。MySQLにはこの機能がなく、繰り返し予定の展開クエリでPostgreSQLが明確に優位
- **半構造化データの扱い**: 繰り返しルール・例外リスト・タグの表示設定など半構造化データが必要になる箇所で、PostgreSQLのJSONB型が最も機能的（インデックス対応・演算子の豊富さ）
- **ACID保証**: 予定共有トークンの発行、繰り返し予定編集の「以降すべて」操作など、複数レコードにまたがる整合性が必要で、RDBMSのトランザクションが最適
- **DDLの安全性**: PostgreSQLはDDLもトランザクション内で実行でき、マイグレーション失敗時のロールバックが安全。MySQLはこの点で運用リスクが高い
- **Goとの相性**: Go向けのPostgreSQL専用ドライバ（pgx）が成熟しており、ADR-003のGoから型安全にアクセスできる（詳細はADR-009で扱う）

MySQLはリレーショナル要件は満たすものの、繰り返し予定・半構造化データの扱い・DDLトランザクションでPostgreSQLに劣ることから見送る。MongoDBはリレーショナル要件・ACID要件のいずれにおいても本プロジェクトに不適合であり、見送る。

## 結果

### 良い影響

- `tstzrange` + GiSTインデックスにより、カレンダー範囲・期間重複検索が効率的に実装できる（PRD-002, PRD-009）
- 外部キー制約・トランザクションによりデータ整合性が宣言的に担保され、アプリケーション側の防御的実装を減らせる
- JSONB型により、繰り返しルール・タグ設定などの半構造化データを整合性を保ちつつ柔軟に格納できる
- DDLトランザクションにより、マイグレーション失敗時のロールバックが安全に行える
- Go向けの成熟したドライバ・ORM選択肢があり、開発生産性を確保できる（ADR-009参照）

### 悪い影響

- PostgreSQL固有機能（JSONB、範囲型、GiST）を活用するため、他RDBMSへの移植性は下がる
- 範囲型・GiSTインデックス・JSONBなどPostgreSQL特有の機能に関する学習コストが発生する
- 機能が豊富な分、インデックス種別・データ型選択で設計判断が求められる場面が増える
