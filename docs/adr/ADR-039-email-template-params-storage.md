# ADR-039: メール送信待ちパラメータの保存方式

- ステータス: 提案中

## コンテキスト

PRD-010 のメール通知基盤では、送信待ちの履歴にメール本文テンプレートへ埋め込むパラメータ（例: パスワードリセット用の URL、アカウントロック通知の再設定リンク等）を保持する必要がある。これらは「アプリが元の値のまま使う一時的な秘密」で、受信者がそのまま本文を読んで利用する前提の値。

本プロジェクトの情報取り扱いガイドラインでは「アプリが元の値を使う秘密はDBに保存せず、シークレットマネージャーで管理する。DBに保存する必要が出た場合は暗号化する」としている。
一方、メール送信待ちのパラメータは1通ごとに発行される短命の値で、送信完了・送信失敗で即座に不要になる。シークレットマネージャー向きではない。

PRD-010・SPEC-010 の制約:

- 本文テンプレートとパラメータにパスワードを含めない（パスワード自体は保存されない）
- 送信履歴にメール本文・件名を保存しない
- 本文用パラメータは送信完了・送信失敗のどちらかになった時点で送信履歴から削除する（送信待ちの間だけ保持）
- 本文用パラメータはログ・トレースに出さない

選定観点:

- 終端状態（`sent` / `failed`）のレコードに本文用パラメータが残らないことを保証できるか
- DB 漏洩時に露出する時間・情報量を小さく保てるか
- 鍵管理・外部ストア導入の運用コストに見合うか

## スコープ外

- パスワードリセットトークン自体の発行・ハッシュ化・有効期限（PRD-011 側で扱う）
- シークレットマネージャー製品の選定
- DB のアクセス制御・監査ログ・バックアップ暗号化（インフラ運用）

## 決定

1. `email_notifications.template_params`（JSONB カラム）に **平文で保存** する
2. `status` が `pending` 以外になった時点でパラメータを `'{}'::jsonb`（空オブジェクト）にクリアする
3. 上記クリアを DB 制約で保証するため、以下の CHECK 制約を設ける

    ```sql
    CHECK (status = 'pending' OR template_params = '{}'::jsonb)
    ```

4. `template_params` の値はログ・トレース・レスポンスに出さない（情報取り扱いガイドラインの「ユーザーが入力した内容」「個人情報」と同等に扱う）
5. 将来、永続的な秘密（APIキー等）を本文に埋め込む用途が出た場合は、本 ADR を置き換えて暗号化方式を再検討する

## 検討した選択肢

### 選択肢1: JSONB に平文で保存し、終端状態への遷移時にクリア + CHECK 制約で保証（採用）

#### 概要

`template_params` カラムに JSON オブジェクトとして平文で保存する。`status` が `pending` 以外になる更新で `'{}'` にクリアし、CHECK 制約で終端状態のレコードに値が残らないことを保証する。

#### メリット

- 実装・運用が最もシンプルで、追加インフラ・鍵管理が不要
- CHECK 制約で「終端状態のレコードに本文用パラメータが残らない」をDB側で保証でき、アプリ側のクリア漏れを未然に防げる
- `pending` の時間は数秒〜数分と短く、終端状態で即クリアされるので DB 漏洩時に露出する平文の時間窓が最小
- 情報取り扱いガイドラインの「ログ・トレースに出さない」との整合を保てる

#### デメリット

- `pending` の間は DB ダンプから本文用パラメータが平文で読める。別の保護（DB アクセス制御・監査ログ・バックアップ暗号化）に頼る

### 選択肢2: アプリ層で対称鍵暗号化して JSONB に保存

#### 概要

`template_params` をアプリ側で対称鍵で暗号化してから JSONB に保存する。鍵は環境変数またはシークレットマネージャーで管理する。

#### メリット

- DB ダンプだけでは本文用パラメータを復元できない
- 情報取り扱いガイドラインの「元の値を使う秘密はDBに保存せず、暗号化して保存する」の方針と形式的に一致する

#### デメリット

- 鍵の管理コストが発生する（ローテーション・バックアップ・ローカル開発での扱い）
- 鍵が漏洩した場合は結局平文と同じ状態になる
- `pending` の時間が短いため、暗号化で防げるリスクの時間窓は小さく、鍵運用コストに見合うだけの保護量を得にくい
- CHECK 制約で「終端状態でクリアされていること」を直接保証できない（暗号文の空オブジェクト判定は CHECK 制約で表現できない）

### 選択肢3: 短命な外部ストア（Redis 等）にパラメータを置き、DB には参照キーだけを保存

#### 概要

`template_params` そのものは外部キャッシュストアに TTL 付きで保存し、`email_notifications` には参照キーだけを置く。

#### メリット

- TTL により、ワーカーがクラッシュして終端状態への遷移が走らない場合でも自動的にパラメータが消える

#### デメリット

- 追加インフラ（Redis 等）が増え、[ADR-038](./ADR-038-email-async-outbox.md) の「PostgreSQL だけでアウトボックスを実現」との整合が取れなくなる
- 業務データのトランザクションに外部ストアへの書き込みを参加させられず、DB コミット後に外部ストアへ書き損ねるケースが生じうる
- 2 つのストアに関連データが跨り、整合性担保のロジックが複雑化する

## 決定理由

- **保護時間窓の短さ**: `pending` の時間は数秒〜数分と非常に短く、暗号化による保護時間は限定的
- **保証の確実性**: 選択肢1の CHECK 制約は、アプリ側のクリア処理に漏れがあっても終端状態に本文用パラメータが残らないことを DB レベルで保証できる。選択肢2・3はこの保証をコード側に依存する
- **運用コストとのバランス**: 鍵管理・外部ストア導入の運用コストに見合うだけの保護を得られない。情報取り扱いガイドラインの意図（本文に含まれる平文の露出を最小化する）は、終端状態での即クリアと「ログ・トレースに出さない」で実質的に満たせる
- **将来の見直し余地**: 永続的な秘密を本文に埋め込む要件が出た場合は、本ADRを置き換えて暗号化方式を採用する

## 結果

### 良い影響

- 追加インフラ・鍵管理が不要で実装・運用がシンプル
- CHECK 制約により、終端状態のレコードに本文用パラメータが残らないことが DB レベルで保証される
- [ADR-038](./ADR-038-email-async-outbox.md) の「PostgreSQL だけで非同期送信を完結させる」方針と整合する

### 悪い影響

- `pending` の短期間は DB ダンプから本文用パラメータが平文で読める。DB のアクセス制御・監査ログ・バックアップ暗号化で別途保護する必要がある
- 将来、永続的な秘密を本文に埋め込む要件が出た場合は、本 ADR を置き換えて暗号化方式を採用する必要がある
