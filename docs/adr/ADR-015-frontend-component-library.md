# ADR-015: フロントエンドコンポーネントライブラリ

- ステータス: 承認済

## コンテキスト

ADR-005でReact + TypeScript、ADR-006でViteを採用した。これを前提に、UIコンポーネントを構築するためのコンポーネントライブラリを選定する。

本プロジェクトは月ビュー・週ビュー・タイムライン（PRD-002, PRD-007）といった高度にカスタマイズされたカレンダーUIを中心とするアプリケーションであり、以下の観点で評価する必要がある。

- カスタマイズ性（カレンダー固有のUIに対応できるか）
- バンドルサイズへの影響
- アクセシビリティ（a11y）対応の品質
- TypeScript対応の成熟度
- Clean Architecture（ADR-001）のAdapter層への閉じ込めやすさ
- メンテナンス状況と長期的な安定性

候補としてshadcn/ui、MUI（Material UI）、Chakra UI、Ant Designを検討する。

## スコープ外

- カレンダー描画専用ライブラリ（FullCalendar、react-big-calendar等）の選定は詳細設計時に別途決定する
- CSS処理系（Tailwind CSS等）の選定はshadcn/ui採用の前提として本ADRに含む
- アイコンライブラリの選定は詳細設計時に別途決定する
- フォーム管理ライブラリ（React Hook Form等）の選定は詳細設計時に別途決定する

## 決定

コンポーネントライブラリとして **shadcn/ui**（Tailwind CSS + Radix UI）を採用する。

## 検討した選択肢

### 選択肢1: shadcn/ui

#### 概要

Radix UIのアクセシブルなプリミティブコンポーネントとTailwind CSSを組み合わせた、コピーペースト型のコンポーネント集。npmパッケージとして配布されるのではなく、CLIでコンポーネントのソースコードをプロジェクトに直接追加する設計。TypeScriptファーストで構築されている。

#### メリット

- **完全なカスタマイズ性**: コンポーネントのソースコードをプロジェクトが所有するため、カレンダーUIの複雑なビジュアル要件（月ビュー・タイムラインのグリッド等）に合わせてコンポーネントを自由に改変できる
- **バンドルサイズへの影響がない**: ライブラリを npm install するのではなくソースをコピーするため、未使用コンポーネントがバンドルに混入しない
- **アクセシビリティ**: Radix UIのプリミティブを基盤としており、キーボードナビゲーション・WAI-ARIAが標準で組み込まれている
- **Tailwind CSSとの統合**: Tailwind CSSのユーティリティクラスで一貫したスタイリングができ、テーマ変更・ダークモード対応が宣言的に行える
- **TypeScript対応**: コンポーネントはTypeScriptで記述されており、Propsの型が明確で、エディタ補完が効く
- **Clean Architectureとの整合**: コンポーネントのソースを直接所有するため、ライブラリへの依存がない。コンポーネントをAdapter層のView部品として扱い、ライブラリ固有のAPIがドメイン層に漏れるリスクがない
- **Viteとの相性**: Tailwind CSS + PostCSSの設定がViteと標準的に統合されており、セットアップコストが低い

#### デメリット

- コンポーネントをプロジェクトに取り込むため、Radix UIやTailwind CSSのアップデートを手動で追従する必要がある
- Tailwind CSSを前提とするため、Tailwindを採用しない場合は利用できない
- MUI・Ant Designに比べてコンポーネントの種類が少なく、DataGrid等のエンタープライズ向けコンポーネントは自前実装が必要

### 選択肢2: MUI（Material UI）

#### 概要

GoogleのMaterial Designを実装した、Reactの代表的なコンポーネントライブラリ。DataGrid・DatePicker・Autocomplete等の高機能コンポーネントを含む包括的なエコシステムを持つ。

#### メリット

- コンポーネントの種類が最も豊富で、複雑なUIを素早く構築できる
- DataGrid等のエンタープライズ向けコンポーネントが充実している
- 長年の実績とコミュニティ規模があり、学習リソースが豊富
- TypeScript対応が成熟している

#### デメリット

- Material Designのビジュアルから離れるには `sx` prop や `styled` API による上書きが必要で、カスタムUIの構築コストが高い。カレンダー固有のグリッドUI（PRD-002, PRD-007）はMUIの想定範囲外のため、大幅なカスタマイズが必要になる
- バンドルサイズが大きく、Tree Shakingで不要分を削減しても他の選択肢より重い
- スタイリングがMUIの `sx` prop / emotion に依存するため、Tailwind CSS等との混在は複雑になる
- ADR-001のAdapter層への閉じ込めが難しく、MUI固有のPropsがコンポーネント全体に広がりやすい

### 選択肢3: Chakra UI

#### 概要

アクセシビリティを重視したモジュール型のコンポーネントライブラリ。v3ではArk UIをプリミティブに採用し、デザイントークンベースのカスタマイズに対応している。

#### メリット

- アクセシビリティがRad UI同等水準で組み込まれている
- デザイントークンによるテーマカスタマイズが直感的
- MUIより軽量で、APIがシンプル
- TypeScript対応が成熟している

#### デメリット

- shadcn/uiと異なりnpmパッケージとして配布されるため、利用するコンポーネントがすべてバンドルに含まれる
- v2からv3への移行でAPIが大幅に変わっており、v3の安定性・事例がまだ蓄積中
- Tailwind CSSとの共存は可能だが、Chakraのスタイリングシステム（Ark UI + design tokens）と二重管理になりやすい
- カレンダーUIの高度なカスタマイズにおいて、shadcn/uiほどの自由度はない

### 選択肢4: Ant Design

#### 概要

Alibabaが開発するエンタープライズ向けUIライブラリ。Table・Form・DatePicker等の高機能コンポーネントを多数提供し、管理画面・業務システムで広く採用されている。

#### メリット

- エンタープライズ向けコンポーネント（Table・Form・DatePickerなど）が最も充実している
- デザインが統一されており、業務系UIを素早く構築できる
- TypeScript対応が成熟している

#### デメリット

- バンドルサイズが最も大きく、Tree Shakingしても重い
- Ant DesignのデザインシステムはAlibabaの業務UIに最適化されており、カレンダーアプリ固有のビジュアル要件（PRD-002 タイムライン等）への適合には大幅なカスタマイズが必要
- カスタムスタイリングがCSS変数の上書きに依存しており、Tailwind CSS等との組み合わせは煩雑になる
- PC/タブレット向けカレンダーアプリには機能が過剰で、不要なコンポーネントがプロジェクトに混入するリスクがある

## 決定理由

- **カスタマイズ性の優先度**: 本プロジェクトの中心機能（月ビュー・週ビュー・タイムライン）はいずれも既存コンポーネントライブラリの標準コンポーネントでは対応できず、グリッドやドラッグ操作を含む独自UIの実装が必要。shadcn/uiはコンポーネントのソースを所有するため、ライブラリの制約なしに要件に合わせて改変できる
- **バンドルサイズ**: カレンダーUIの実装には外部のカレンダーライブラリ（詳細設計で別途選定）も加わる可能性があり、コンポーネントライブラリ自体のバンドルサイズを最小化することが望ましい。shadcn/uiは使用分のみをソースに含めるため、他の選択肢に比べて追加バンドルサイズがない
- **アクセシビリティ**: Radix UIのプリミティブを基盤とするshadcn/uiは、ダイアログ・ドロップダウン・ポップオーバー等のインタラクティブコンポーネントにおいてキーボードナビゲーション・WAI-ARIAが標準で組み込まれている
- **Clean Architectureとの整合**: コンポーネントのソースをプロジェクトが所有することで、ライブラリ固有のAPIをAdapter層のView部品に閉じ込めやすい。MUI・Ant Designは固有のスタイリングAPIがコンポーネント全体に広がりやすく、ADR-001の狙いに反する
- **Tailwind CSSとViteの相性**: Tailwind CSS + PostCSSはViteと標準的に統合されており（ADR-006）、shadcn/uiと組み合わせたセットアップ事例が豊富。MUIのemotionやAnt DesignのCSS-in-JSはViteでのTree Shaking設定に追加コストがかかる

MUIとAnt Designはコンポーネントの種類は豊富だが、カレンダー固有のカスタマイズコストとバンドルサイズで劣るため見送る。Chakra UIはアクセシビリティの水準は高いが、v3の安定性蓄積中の状況とTailwind CSSとの二重管理リスクからshadcn/uiに劣ると判断する。

## 結果

### 良い影響

- コンポーネントのソースをプロジェクトが所有するため、月ビュー・週ビュー・タイムラインの独自UIをライブラリの制約なしに構築できる
- 使用するコンポーネントのみをソースに取り込む設計で、バンドルサイズへの影響を最小化できる
- Radix UIベースのアクセシビリティ（キーボード操作・ARIA）が標準で組み込まれ、個別対応のコストを削減できる
- Tailwind CSSによる一貫したスタイリングで、テーマ変更・ダークモード対応を宣言的に行える
- ライブラリへのnpm依存がないため、Adapter層に外部ライブラリのAPIが漏れるリスクがない（ADR-001と整合）

### 悪い影響

- コンポーネントのソースをプロジェクトで管理するため、Radix UIやTailwind CSSのアップデートを手動で追従する運用ルールが必要
- DataGrid等のエンタープライズ向けコンポーネントはshadcn/uiに含まれず、必要になった場合は自前実装または別途ライブラリ選定が必要
- Tailwind CSSの習熟が前提となるため、チームメンバーへの学習コストが生じる
