# ADR-038: メール通知の非同期送信とアウトボックス方式

- ステータス: 承認済

## コンテキスト

PRD-010 のメール通知基盤では、以下の要件を満たす必要がある。

- 送信を要求してから1分以内に送信を完了すること（99%以上）
- 送信要求の処理は送信の完了を待たずに終わること
- 一時的な送信失敗（接続失敗・タイムアウト・レート制限・送信サービスの一時エラー）は自動で再送すること
- 送信処理が複数動いても同じ送信履歴を二重に送らないこと
- 送信を要求したユースケース（業務データの永続化を伴う）と、送信履歴の作成が原子的に扱われること

本プロジェクトは ADR-008 で PostgreSQL、ADR-022 で論理 CQRS、ADR-024 で UseCase 層の `TransactionManager` を採用している。これらの前提のもとで、非同期送信の仕組みを決める。

選定観点:

- 既存インフラ（ADR-008 の PostgreSQL）で実装できるか、追加インフラが必要か
- 業務データの永続化と送信履歴の `pending` 作成を同一トランザクションで扱えるか（トランザクショナルアウトボックス）
- 送信ワーカーが複数動く状況でも同じメールを二重に送らないか
- 送信ワーカーのプロセス構成をシンプルに保てるか

## スコープ外

- メールを実際に送る方法（送信サービス・送信プロトコル・送信ドメイン認証・バウンス通知の受信）。インフラの選定とあわせて別途決める
- 送信待ちパラメータの保存方式（[ADR-039](./ADR-039-email-template-params-storage.md)）
- 送信ワーカーをAPIサーバーと分離したプロセスで動かす場合のオーケストレーション（将来、スケール要件で別途検討）

## 決定

1. 送信待ちは `email_notifications` テーブルで管理する。業務データの永続化と送信履歴の `pending` 作成を、呼び出し元ユースケースの `TransactionManager.RunInTx`（[ADR-024](./ADR-024-transaction-management.md)）に参加させて同一トランザクションで実行する（トランザクショナルアウトボックス方式）
2. 送信ワーカーは `status = 'pending' AND next_attempt_at <= NOW()` の行を `SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1` で1件確保し、同じトランザクションで `attempt_count` を加算して `next_attempt_at` を確保の有効期限まで進めてからコミットする。送信はコミット後にトランザクションの外で行い、結果は確保時の `attempt_count` を条件にした別の短いトランザクションで記録する。これにより、ワーカーが複数動いても同じ行を同時に確保せず、送信の遅延でDB接続とロックを持ち続けず、送信中に停止しても試行回数が戻らない
3. 送信ワーカーは **API サーバーと同じプロセス内の常駐 goroutine** として動かす。起動時に `EmailSenderWorker.Run(ctx)` を呼び出し、プロセス終了時に `ctx.Done()` で停止する
4. 送信ワーカーの有効化は環境変数フラグで切り替えられるようにし、将来別プロセスとして切り出せるようコンポーネントを疎結合に保つ
5. 再送のバックオフは仕様書（SPEC-010）の値を使う（初回失敗から10秒後、2回目失敗から20秒後、最大試行回数は初回+再送2回=3回）
6. 送信ワーカーは `EmailTransport` インターフェースを通してメールを渡す。`EmailTransport` は、受け付けたか、一時的な失敗か、恒久的な失敗かを返す。送信サービス・送信プロトコルに依存する処理は `EmailTransport` の実装に閉じ込め、アウトボックス・再送・状態の管理はその実装を差し替えても変わらないようにする

## 検討した選択肢

### 選択肢1: PostgreSQL テーブル + FOR UPDATE SKIP LOCKED + 同一プロセス goroutine（採用）

#### 概要

送信待ちキューを `email_notifications` テーブルで持つ。送信ワーカーは API サーバーと同じプロセスで動く常駐 goroutine で、PostgreSQL をポーリングして 1 行ずつロック取得する。

#### メリット

- 既存インフラ（ADR-008 の PostgreSQL）だけで実装でき、追加のミドルウェアが不要
- 業務データの永続化と送信履歴の `pending` 作成を、`TransactionManager.RunInTx`（ADR-024）で同一トランザクションに参加させられる（トランザクショナルアウトボックスが自然に成立）
- `FOR UPDATE SKIP LOCKED` により、ワーカーが複数動いても同じ行を二重に取得しない
- デプロイ単位が API サーバー1つで済み、運用がシンプル
- 部分インデックス（`WHERE status = 'pending'`）により、送信待ちが少ない定常状態でもポーリングコストを低く保てる

#### デメリット

- 高スループットではポーリングが DB の負荷になる。現在の送信量（PRD-010 の想定）では問題にならないが、将来は再検討が必要になる可能性がある
- ワーカーと API サーバーが同プロセスのため、送信遅延や負荷が API リクエスト処理に影響する可能性がある

### 選択肢2: 外部メッセージキュー + 別プロセスワーカー

#### 概要

送信要求ごとに外部メッセージキュー（SQS・RabbitMQ・Redis Streams 等）へメッセージを送り、別プロセスで動くワーカーがメッセージを取り出して送信する。

#### メリット

- キュー専用のプロダクトを使うため、再送制御・DLQ・遅延メッセージ等の機能が整っている
- ワーカーと API サーバーを独立にスケールできる
- API サーバーの障害・デプロイが送信ワーカーに波及しない

#### デメリット

- 送信サービス用途のためだけに新しいインフラコンポーネントが増える
- どのキュー製品を使うかがインフラ（クラウド）の選定に依存し、インフラが決まるまで実装に着手できない
- 業務データの永続化とメッセージ投入の間に二相コミット問題が生じ、トランザクショナルアウトボックス（本質的に DB テーブルが必要）を結局併用することになる
- 現時点の送信量・SLO（1分以内99%）に対して過剰な設計

### 選択肢3: メモリ上の channel + 同一プロセス

#### 概要

送信要求ごとに Go の channel にメッセージを push し、goroutine が受け取って送信する。送信待ち状態を DB に持たない。

#### メリット

- 追加のインフラが不要
- 実装がシンプル

#### デメリット

- プロセスがクラッシュすると送信待ちメッセージが全て失われる（永続化がないため）
- 業務データのトランザクションと送信要求が原子化できず、業務データのコミット後にプロセスがクラッシュするとメールが送られない
- PRD-010 の「送信要求〜1分以内に99%送信完了」を達成できず、採用不可

## 決定理由

- **送信量と要件への適合**: PRD-010 の送信量（パスワードリセット・アカウントロック通知などユーザーアクション起点のメール）は、PostgreSQL のポーリングで1分以内 SLO を十分に達成できる規模
- **既存インフラでの実現**: ADR-008 で採用済みの PostgreSQL で完結し、新たなミドルウェアを増やさない
- **トランザクショナルアウトボックスの自然な成立**: 業務データと送信履歴の `pending` を同一トランザクションでコミットでき、業務データのコミット後に送信履歴が作られないケースを排除できる
- **二重送信の防止**: `FOR UPDATE SKIP LOCKED` は PostgreSQL の標準機能で、複数ワーカー構成でも1行の多重取得を防げる
- **運用のシンプルさ**: ワーカーを API サーバーと同一プロセスにすることでデプロイ単位が1つに収まる。将来スケール要件が出た場合は、コンポーネントが疎結合であれば別プロセス化できる

## 結果

### 良い影響

- 追加インフラなしで非同期送信・再送・冪等性を実装できる
- 業務データと送信履歴が同一トランザクションでコミットされ、「業務データは保存されたのにメール送信履歴が作られなかった」という不整合が起きない
- `FOR UPDATE SKIP LOCKED` により、ワーカーを複数動かしても二重送信を防げる（1プロセス=1ワーカーでも、デプロイ中の新旧プロセスが並走するタイミングで効果を発揮する）

### 悪い影響

- 送信量が増えたとき、ポーリング間隔と `FOR UPDATE SKIP LOCKED` のロック競合でスループットが頭打ちになる。PRD-010 の想定を超える規模になったら、外部キュー + 別プロセスワーカーへの移行を再検討する。その場合も `email_notifications` テーブルはアウトボックスとして残し、テーブルからキューへ流す中継処理を追加して移行する
- API サーバーと送信ワーカーが同一プロセスのため、送信処理の遅延が API リクエストと同じリソースを使う。運用で負荷の観測を行い、必要になった時点で別プロセス化する
