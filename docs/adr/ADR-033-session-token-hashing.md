# ADR-033: セッショントークンの生成・保存方式

- ステータス: 承認済
- 関連Issue: #246
- 関連ADR: ADR-020（セッション管理方式）, ADR-028（予定共有トークンの生成・保存方式）

## コンテキスト

ADR-020 はセッションIDをUUID v4で生成し、`sessions.id` にそのまま保存して、同じ値をHTTP-Only Cookieで送信すると定めている。この方式では、DBの内容だけが漏洩した場合（SQLインジェクションによる読み取り、バックアップの流出など）に、`sessions.id` をCookieにセットするだけで有効期限内の全ユーザーになりすませる。

一方、予定共有トークン（ADR-028）は、ランダム値の生成とSHA-256ハッシュのみの保存を採用しており、同じ「DB漏洩時の影響」に対する扱いが非対称になっている。

セッション識別子の生成方法・DBへの保存形式・既存セッションの扱いを決定する必要がある。

## スコープ外

- セッションのローテーション（ログイン時の再発行以外）、絶対/アイドルタイムアウトの見直し
- Cookie属性（`HttpOnly`・`Secure`・`SameSite`）の見直し
- 期限切れセッションの削除バッチ
- アプリケーションサーバー上でのCookie窃取、XSSによるCookie窃取への対策

## 決定

1. セッショントークンは、`crypto/rand` で生成した32バイトのランダム値をbase64url（パディングなし）でエンコードした文字列とする（ADR-028と同一）。Cookieにはこの平文トークンを設定する。
2. DBにはトークンのSHA-256ハッシュ（16進数文字列）のみを保存し、平文トークンは保存しない。リクエスト時はCookieのトークンをハッシュ化して照合する。
3. `sessions` テーブルには `token_hash TEXT NOT NULL UNIQUE` を追加する。`sessions.id`（UUID）は内部の行識別子として残し、Cookieには使わない。
4. 既存のセッションはマイグレーションで全件削除し、全ユーザーを強制ログアウトする。
5. トークンとハッシュの型は `domain/session` に独立して定義する。`domain/eventshare` には依存しない。

## 検討した選択肢

### 選択肢1: UUID v4のまま平文保存（現状）

#### 概要

ADR-020 の方式を維持する。

#### メリット

- 変更が不要

#### デメリット

- DB漏洩時に、有効期限内の全セッションがそのままなりすましに使われる

### 選択肢2: UUID v4を生成してハッシュだけ保存

#### 概要

生成方法はUUID v4のまま、DBにはそのSHA-256ハッシュを保存する。

#### メリット

- 生成部分の変更が小さい

#### デメリット

- UUID v4は約122bitのエントロピーで、`crypto/rand` の256bitより小さい
- 将来UUIDの種類（時刻ベースのv7など）に変わった場合に、推測しやすくなるリスクがある
- ADR-028 と生成方式が揃わない

### 選択肢3: ADR-028 と同じランダムトークン＋ハッシュ保存（本決定）

#### 概要

決定に記載のとおり。

#### メリット

- DB漏洩時に、ハッシュからCookie値を復元できない
- 256bitのエントロピーがあるため、bcrypt のような低速ハッシュが不要で、SHA-256で十分
- 標準ライブラリのみで実装でき、ADR-028 と同じパターンに揃う

#### デメリット

- ハッシュ化・照合の処理が増える
- DBの値から、発行済みセッションのCookie値を直接確認できない（これはハッシュ保存の意図した性質）

### 選択肢4: HMAC（サーバー側の秘密鍵＝pepper付き）でハッシュ化

#### 概要

SHA-256の代わりに、サーバーの秘密鍵を使ったHMAC-SHA256で保存する。

#### メリット

- DBとアプリの秘密鍵が別経路で管理されていれば、DB漏洩時にさらに安全

#### デメリット

- 秘密鍵の管理・ローテーション手段が必要になる
- 256bitのランダムトークンでは、ハッシュの原像探索が現実的でなく、鍵なしでも十分な強度がある

## 決定理由

- 256bitのランダムトークンはハッシュの原像探索が現実的でないため、SHA-256のみで十分に防御でき、HMACの鍵管理コストに見合う追加効果が小さい
- ADR-028 と同じパターンに揃えると、セッションと共有トークンで同じ前提のコードレビューができる
- `sessions.id` を内部識別子として残すと、FKや既存のインデックスに影響せずに済む。Cookieには使わないため、DB漏洩時にもなりすましには使えない
- 既存セッションの移行は、既存の `sessions.id`（UUID）が平文のまま `id` 列に残る問題がある。引き継ぐとDB漏洩時の保護が既存セッションにだけ効かないため、全件削除して再ログインさせる
- `domain/session` に独立した型を置くと、セッションと共有トークンの2つのドメインが互いに依存せず、ドメイン境界が保たれる。重複するのは約20行で、2か所に増えても許容範囲

## 結果

### 良い影響

- DB漏洩時に、DBの内容だけではセッションのなりすましができない
- セッションと共有トークンの保存方式が揃う

### 悪い影響

- デプロイ時に全ユーザーが一度ログアウトされる
- ハッシュ化・照合のコードが `domain/session` と `domain/eventshare` に重複する
- ログイン後にDBの `sessions` を見ても、実際のCookie値との対応が確認できず、調査の手がかりが減る
