# ADR-001: コーディングアーキテクチャ

- ステータス: 承認済

## コンテキスト

プロジェクトの成長に伴い、コードの整理・保守・テストを一貫して行うためのアーキテクチャ指針が必要になった。
既存ガイドライン（SOLID原則・依存性逆転の原則）と整合するアーキテクチャパターンを選定する。

## 決定

Clean Architecture（Robert C. Martin提唱）をコーディングアーキテクチャとして採用する。

Dependency Rule（依存の向きは常に内側＝Domain層へ）を全層で徹底する。
層の構成は `Domain` / `UseCase` / `Adapter`（Controller・Presenter・Gateway） / `Infrastructure` とする。

Clean Architectureは従来の階層型アーキテクチャの一種であり、最大の違いは「依存の向き」にある。
Clean Architectureでは外側から内側への一方向のみ依存を許可し（Dependency Rule）、Domain層はフレームワーク・DBに一切依存しない。

## 検討した選択肢

### 選択肢1: Clean Architecture

#### 概要

Robert C. Martinが提唱するアーキテクチャ。Dependency Ruleにより依存の向きを内側（Domain層）に統一する。

#### メリット

- Domain層がフレームワーク・DB・外部APIに依存しないため、技術的な変更の影響が局所化される
- Domain・UseCase層を単体テストしやすく、テストのしやすさが高い
- SOLID原則（特に依存性逆転の原則）との親和性が高く、既存ガイドラインと一貫する
- 責務が明確に分離されており、大規模化しても可読性を維持しやすい

#### デメリット

- 学習コストが高く、層の概念を理解するまでに時間がかかる
- 定型コードが増え、小規模機能でも複数ファイルにまたがる
- 設計の意図を理解していないと、依存の向きを誤りやすい

### 選択肢2: 従来の階層型アーキテクチャ

#### 概要

Presentation・Business Logic・Data Accessなどの層に分けて整理するシンプルな構成。依存の向きに厳格な制約はない。

#### メリット

- 構造がシンプルで理解しやすく、学習コストが低い
- 規約が少なく、素早く実装を始められる
- 小規模プロジェクトに適している

#### デメリット

- 依存の向きに制約がないため、ドメインロジックがDB・フレームワークに依存しやすい
- 上の層が下の層の実装詳細を知ってしまうため、変更時の影響範囲が広がりがち
- ドメインロジックの単体テストが難しくなる（DBや外部システムの差し替えが必要）

### 選択肢3: 機能単位型アーキテクチャ（Feature Sliced Design等）

#### 概要

機能ごとにディレクトリを分け、各機能が独立した構造を持つアーキテクチャ。

#### メリット

- 機能単位で凝集度が高く、機能ごとのチーム分業がしやすい
- 機能の追加・削除がしやすく、規模が大きくなっても対応しやすい

#### デメリット

- 複数の機能にまたがる処理の依存関係管理が複雑になる
- ドメインロジックが各機能に散在し、重複しやすい
- 日本語ドキュメントや事例が少なく、チームへの導入コストが高い

## 決定理由

- 既存ガイドライン（SOLID・依存性逆転の原則）と設計方針が一致している
- ドメインロジックを外部技術から完全に分離できるため、長期的な保守性・変更耐性が最も高い
- Domain・UseCase層の単体テストが容易で、将来的なテスト拡充の基盤になる

## 結果

### 良い影響

- Domain層・UseCase層の単体テストがフレームワーク・DBなしで実行できる
- フレームワークやDBの変更がDomain層に影響しない（Infrastructure層の差し替えで対応可）
- 責務が明確になり、新規メンバーが実装箇所を判断しやすくなる

### 悪い影響

- 学習コストがかかり、チーム全員がDependency Ruleを理解するまで設計にばらつきが生じる可能性がある
- 小さな機能でも複数の層にまたがるファイルが必要になり、実装量が増える
- プロジェクト規模に応じた適用範囲の判断を誤ると、過剰な設計になるリスクがある
