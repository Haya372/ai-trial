# ADR-003: バックエンド言語

- ステータス: 承認済

## コンテキスト

本プロジェクトはクラウドベースのカレンダーアプリであり、複数端末からの同時アクセス（PRD-001）・予定のCRUD（PRD-003）・繰り返し予定の展開計算（PRD-009）・共有URLからのアクセス（PRD-004）などをサーバー側で処理する。

バックエンド言語の選定にあたっては、以下の観点で評価する必要がある。

- ADR-001で採用したClean Architectureのレイヤー分離との相性（特にDependency Ruleを表現するインターフェースの表現力）
- 静的型付けによるDomain層の型安全性（不変条件を型で表現できるか）
- 複数端末からの同時アクセス（PRD-001）に耐える並行処理性能
- 繰り返し予定（PRD-009）で2年分展開するような計算処理の安定性
- ADR-002で採用したMonorepo構成への統合のしやすさ

候補としてGo、Node.js + TypeScript、Pythonを検討する。

## スコープ外

- Webフレームワークの選定はADR-004で扱う
- DBアクセスライブラリの選定はADR-009で扱う
- DBマイグレーションツールの選定はADR-010で扱う
- 認証ライブラリ・セッション管理ライブラリの選定はPRD-001の詳細設計時に決定する
- インフラ・デプロイ方法（コンテナ化、ホスティング環境）は本ADRの対象外

## 決定

バックエンド言語として **Go**（1.22以降）を採用する。

## 検討した選択肢

### 選択肢1: Go

#### 概要

Googleが開発した静的型付けコンパイル言語。goroutineによる軽量並行処理を言語機能として持ち、標準ライブラリ（`net/http`・`time`など）が充実している。構造的部分型のインターフェースを備える。

#### メリット

- goroutineとchannelによる並行処理が言語機能として組み込まれており、複数端末からの同時アクセス（PRD-001）を少ないリソースで捌ける
- インターフェース型が構造的部分型で、Clean ArchitectureのDependency Rule（UseCase層がインターフェースを定義し、Infrastructure層が暗黙的に実装する）を宣言的な `implements` なしで自然に表現できる
- 静的型付け + コンパイル時チェックにより、Domain層の型安全性が高く、実行時にも型情報が保たれる
- 単一バイナリにコンパイルされるため、デプロイと起動が高速でMonorepo内のCIビルドが単純化する
- 標準ライブラリの `time` パッケージが充実しており、繰り返し予定（PRD-009）のタイムゾーン・日時計算に強い
- コンパイル型言語のため、繰り返し予定の展開などCPUバウンドな処理でも安定した実行速度が得られる

#### デメリット

- ジェネリクスの導入が比較的新しく、既存ライブラリで活用されていないものが多い
- Node.js/Pythonに比べて開発者の学習コストがやや高い（ポインタ・インターフェース・エラーハンドリング）
- フロントエンド（TypeScript想定）と言語が異なるため、型定義の共有はコード生成（OpenAPI等）を介する必要がある
- Node.js中心のMonorepoツールとの統合にはGo modulesとの併用設計が別途必要

### 選択肢2: Node.js + TypeScript

#### 概要

V8エンジン上で動作するJavaScriptランタイム。TypeScriptを組み合わせて静的型付けを実現する。イベントループによる非同期I/Oを特徴とする。

#### メリット

- フロントエンド（TypeScript想定）と言語・型定義を共有でき、Monorepo内でDTOや型を共通パッケージ化しやすい
- TypeScriptによる型安全性が高く、Clean ArchitectureのDomain層をinterfaceで表現できる
- npmエコシステムが巨大で、認証（PRD-001）・バリデーション・日時処理などライブラリが豊富
- 非同期I/O（イベントループ）により、I/Oバウンドなカレンダー処理は少ないリソースで捌ける
- Monorepoツール（Turborepo・Nx等）との親和性が最も高い

#### デメリット

- シングルスレッド + イベントループのため、繰り返し予定の展開（PRD-009）のようなCPUバウンドな処理でイベントループを詰まらせるリスクがある（worker_threads等の追加設計が必要）
- TypeScriptは実行時に型情報が消えるため、境界での型検証を別途行う必要がある（zod等）
- ランタイムがGCベースで、Goに比べてメモリ使用量が大きくなりやすい
- 依存関係（node_modules）が肥大化しやすく、Monorepo全体のインストール時間・ディスク使用量が増える

### 選択肢3: Python

#### 概要

動的型付けの汎用言語。型ヒント（PEP 484）による静的解析が可能で、FastAPI等のモダンWebフレームワークで型ヒントを活用した開発ができる。

#### メリット

- 型ヒント + Pydanticによる自動バリデーションが強力で、Adapter層の実装が簡潔になる
- 開発者人口が多く、学習リソースが豊富
- 標準ライブラリが豊富で、日時処理・データ変換などが素直に書ける
- Clean Architectureのレイヤー分離をモジュール単位で実現できる

#### デメリット

- Pythonの型ヒントは実行時強制ではなく、Domain層の型安全性はGo/TypeScriptに劣る
- GIL（Global Interpreter Lock）によりマルチコアCPUを活用しにくく、複数端末からの同時アクセス性能でGoに劣る
- 非同期処理（async/await）は書けるが、同期ライブラリと混在すると性能劣化が起きやすく設計上の注意が必要
- 実行速度がGoに比べて遅く、繰り返し予定の展開など計算量が多い処理でレスポンスタイムに影響が出やすい
- Monorepo管理のツール（Turborepo等）はNode.jsエコシステム前提のものが多く、Pythonパッケージ管理との統合手順が別途必要

## 決定理由

- **並行処理性能**: PRD-001の「複数端末からの同じアカウントでのアクセス」および PRD-009の繰り返し予定展開（2年分生成）を安定して捌く必要があり、goroutineによる軽量並行処理を持つGoが最も要件に適合する。Node.jsはCPUバウンド処理でイベントループ詰まりの懸念があり、PythonはGILの制約がある
- **Clean Architectureとの親和性**: Goの構造的部分型（インターフェース）は、UseCase層でインターフェースを定義しInfrastructure層で実装を注入するというDependency Ruleを、宣言的な `implements` なしで自然に表現できる。ADR-001のレイヤー分離との相性が最も良い
- **型安全性**: 静的型付け + コンパイル時チェックにより、Domain層の不変条件を型で表現しやすい。TypeScriptと異なり実行時にも型が保たれ、Pythonの型ヒントに比べて強制力が高い
- **時刻処理の堅牢性**: 標準ライブラリの `time` パッケージが充実しており、繰り返し予定（PRD-009）のタイムゾーン考慮・日時計算を標準機能で完結できる
- **デプロイ単純性**: 単一バイナリでのデプロイにより、Monorepo（ADR-002）内でのCIビルド時間とデプロイ手順が単純化する

Node.jsは型共有の魅力があるものの、CPUバウンドな繰り返し予定展開でイベントループ詰まりの懸念があること、Clean Architectureのインターフェース表現がGoに比べて冗長になることから見送る。Pythonは並行処理性能と型安全性の観点で本プロジェクトの要件に対して弱く、見送る。

## 結果

### 良い影響

- goroutineにより少ないサーバーリソースで複数端末の同時アクセスを捌ける
- 単一バイナリでのデプロイにより、CIビルド時間とデプロイ手順が単純化する
- 標準ライブラリの `time` パッケージにより、繰り返し予定の日時計算を外部依存なしで実装できる
- 構造的部分型のインターフェースにより、Clean ArchitectureのDependency Ruleを冗長なコードなしで表現できる

### 悪い影響

- フロントエンド（TypeScript想定）と型定義を直接共有できず、APIスキーマ管理（OpenAPI等）を別途整備する必要がある
- Node.js中心のMonorepoツールとの統合手順が別途必要（Go modulesとNode.jsパッケージマネージャの併用設計）
- Go特有のイディオム（エラーハンドリング、インターフェースの受け側定義）に慣れるまでの学習コストが発生する
- ジェネリクスの活用がまだ発展途上で、汎用的なリポジトリパターン等を素直に書くには工夫が必要
