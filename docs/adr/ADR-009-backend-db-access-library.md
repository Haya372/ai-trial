# ADR-009: DBアクセスライブラリ

- ステータス: 承認済

## コンテキスト

ADR-003でGoを、ADR-008でPostgreSQLを採用した。これを前提に、GoからPostgreSQLへアクセスするためのアプローチを選定する。

本プロジェクトは繰り返し予定の期間検索（PRD-009）や共有トークン発行（PRD-004）など、SQLの表現力とトランザクション制御が重要な操作を多く含む。加えて、ADR-001で採用したClean ArchitectureのDependency Ruleに従い、Domain層をDB依存から完全に分離する必要がある。

DBアクセスアプローチの選定にあたっては、以下の観点で評価する。

- Clean Architecture（ADR-001）のInfrastructure層への閉じ込めやすさ（Domain層をDB依存から分離できるか）
- PostgreSQL固有機能（`tstzrange` 型・JSONB等、ADR-008で活用予定）の利用しやすさ
- SQLの制御のしやすさ（複雑なクエリへの対応）
- 型安全性とコンパイル時の検証（実行時エラーをどこまで防げるか）
- ボイラープレートの量（Infrastructure層の実装コスト）
- テストのしやすさ（挙動が予測可能で、リポジトリ層のテスト戦略が立てやすいか）

候補としてsqlc（コード生成）、pgx（手書きSQL）、GORM（フルORM）、sqlx（`database/sql` 拡張）を検討する。

## スコープ外

- コネクションプールのパラメータチューニングは運用設計時に決定する
- トランザクション境界のパターン（UseCase層での管理等）は詳細設計時に決定する
- リポジトリ層のテスト戦略（testcontainers・モック等）は品質保証設計時に決定する

## 決定

DBアクセスライブラリとして **sqlc**（`github.com/sqlc-dev/sqlc`）を採用する。ドライバには **pgx**（`github.com/jackc/pgx/v5`）を使用する。

`.sql` ファイルにSQLクエリを定義し、`sqlc generate` でInfrastructure層のGoコードを生成する。Domain層とsqlc生成コードの間はリポジトリ実装でマッピングを行う。

## 検討した選択肢

### 選択肢1: sqlc（コード生成）

#### 概要

SQLファイルに定義したクエリから型安全なGoコードを生成するツール。スキーマ定義（DDL）とクエリ定義（`-- name: GetEvent :one` 形式のコメント付きSQL）をもとに、`sqlc generate` コマンドで構造体・関数を自動生成する。内部ドライバとしてpgxを使用できる。

#### メリット

- **型安全性**: SQLクエリの引数と戻り値がGoの型として生成されるため、実行時の型ミスマッチをコード生成時点で検出できる
- **SQLの明示性**: 実行されるSQLがファイルに明示的に記述され、ORMの暗黙クエリ生成がない。デバッグ・パフォーマンスチューニングが容易
- **ボイラープレート削減**: pgxを直接使う場合に必要な手動の行スキャン・引数バインディングコードが生成され、Infrastructure層の実装コストが大幅に減る
- **Clean Architectureとの整合**: 生成コードはInfrastructure層に配置し、Domain層には流入させない。GORMと異なりDomain層エンティティへのタグ付けが不要
- **PostgreSQL固有機能の利用**: pgxをドライバとして利用するため、`tstzrange` 型・JSONB・配列等のPostgreSQL固有機能をSQLで直接扱える
- **生成コードのシンプルさ**: 生成されたGoコードは可読性が高く、デバッグ時に追跡しやすい

#### デメリット

- `sqlc generate` をスキーマ変更・クエリ変更のたびに実行する必要があり、開発フローにコード生成ステップが増える
- 動的なWhere句（検索フィルタが可変な場合等）の表現が苦手。複雑な動的クエリはRaw SQLへのエスケープが必要
- pgxやGORMと比べて知名度がやや低く、チームへの導入にキャッチアップコストがかかる

### 選択肢2: pgx（手書きSQL + 手動マッピング）

#### 概要

PostgreSQL専用のGoドライバ。`database/sql` 経由でもネイティブAPIでも利用でき、libpqをバイパスした独自プロトコル実装で動作する。SQLを直接記述し、行スキャンも手動で実装する。

#### メリット

- PostgreSQL固有機能（`tstzrange` / JSONB / LISTEN/NOTIFY 等）をネイティブAPIで型安全に扱える
- SQLを直接制御でき、複雑な動的クエリも制約なく書ける
- sqlcを使わない場合に比べてツールチェーンがシンプル

#### デメリット

- 行スキャン・引数バインディングを手動で書く必要があり、ボイラープレートが多い
- スキーマ変更時にSQL・構造体マッピングを両方手動で修正する必要がある
- 型安全性の保証がなく、SQLと構造体のズレは実行時まで検出されない（sqlcが解決する問題）

### 選択肢3: GORM（フルORM）

#### 概要

Goで最も普及しているORM。モデル定義から自動マイグレーション・関連ロード・フック・ソフトデリート等を提供するフルスタックなORMフレームワーク。

#### メリット

- モデル定義からCRUDまでボイラープレートが少なく、開発初速が速い
- 関連ロード・トランザクションヘルパー・フック等の便利機能が豊富
- 学習リソースが豊富で、日本語情報も多い

#### デメリット

- **Clean Architectureとの衝突**: Domain層のエンティティに `gorm:"..."` タグを埋め込むとDependency Rule（ADR-001）に違反する。回避するにはDBモデル用の別構造体とマッパーを用意する必要があり、GORMの生産性メリットが大きく減じる
- **マジックの多さ**: 生成されるSQLが暗黙的で、N+1・不要なJOIN等のパフォーマンス問題を追跡しにくい
- **PostgreSQL固有機能の弱さ**: `tstzrange` 型・JSONB・LISTEN/NOTIFY等はネイティブサポートが限定的で、Raw SQLに逃げる場面が増える
- **テストのしにくさ**: フック・自動生成SQL・ソフトデリート等の暗黙挙動があるため、リポジトリ層の挙動を予測しにくい

### 選択肢4: sqlx（`database/sql` 拡張）

#### 概要

`database/sql` を薄くラップし、構造体への自動マッピング（`StructScan`）・名前付きパラメータ等の便利機能を追加するライブラリ。ドライバは別途選択する。

#### メリット

- `StructScan` により手動スキャンより記述量が減る
- `database/sql` インターフェースを維持しており、標準ライブラリの知識で扱える
- ORMほどマジックが多くない

#### デメリット

- PostgreSQL固有機能（`tstzrange` / JSONB 等）の扱いはpgxネイティブAPIより不利。独自スキャナ実装が必要な場面がある
- pgxをドライバとして使う場合、sqlxの抽象化レイヤーが1段増えるだけになり、pgxの表現力を活かしきれない
- `db:"..."` タグを持つ構造体をDomain層に流入させない設計配慮が必要
- sqlcと比べて型安全性のコンパイル時検証がない

## 決定理由

- **型安全性とコンパイル時検証**: sqlcはSQLと構造体のズレをコード生成時点で検出する。pgx（手書き）やsqlxはスキーマ変更時の構造体ズレが実行時まで検出されず、リグレッションを起こしやすい。この点でsqlcが最も堅牢
- **ボイラープレートの削減**: pgxの手書きアプローチは型安全性・SQL制御の自由度は高いが、行スキャン・引数バインディングのコードが全リポジトリで繰り返される。sqlcはこれを生成で解消し、Infrastructure層の実装コストを下げる
- **Clean Architectureとの整合**: sqlcの生成コードはInfrastructure層に配置し、Domain層には持ち込まない。GORMのようにDomain層エンティティへのタグ付けを強いられず、ADR-001のDependency Ruleを維持できる
- **SQLの明示性**: ORMと異なりSQLファイルが成果物として残り、クエリの意図が明確。繰り返し予定の期間重複検索（PRD-009）のような複雑なクエリも、SQLで直接表現できる
- **PostgreSQL固有機能の利用**: pgxをドライバとして使用するため、`tstzrange` 型・JSONB等のADR-008で採用した機能をSQLレベルで直接活用できる
- **GORMの問題**: Domain層エンティティへの侵襲・マジックによるパフォーマンス問題・テストの困難さから不採用。Clean Architectureの方針（ADR-001）と根本的に相性が悪い

sqlx単体は手書きpgxからのメリットが限定的で、sqlcの型安全性・ボイラープレート削減に劣る。pgx直接利用はsqlcの下位互換であり（sqlcはpgxを内部で使う）、手動実装コストが高い割にsqlcで得られる恩恵を捨てることになる。

## 結果

### 良い影響

- SQLファイルに定義したクエリからコード生成されるため、スキーマ変更時の構造体ズレをコード生成フェーズで検出でき、実行時エラーを防ぎやすい
- Infrastructure層のボイラープレート（行スキャン・引数バインディング）が大幅に減り、実装コストが下がる
- SQLが `.sql` ファイルに明示的に記述されるため、クエリの意図が明確でパフォーマンスチューニングがしやすい
- pgxをドライバとして使うため、`tstzrange` 型・JSONB等のPostgreSQL固有機能をSQLで直接活用できる（ADR-008の決定と整合）
- Domain層をsqlc生成コードから完全に分離でき、ADR-001のDependency Ruleを守れる

### 悪い影響

- スキーマ変更・クエリ追加のたびに `sqlc generate` の実行が必要で、開発フローにコード生成ステップが加わる
- 動的なWhere句（複合フィルタ検索等）の表現が苦手で、その場合はRaw SQLへのエスケープが必要
- sqlcに不慣れなメンバーのキャッチアップコストが発生する
- Domain層とsqlc生成型の間のマッピングコード（変換関数）をリポジトリ実装で用意する必要がある
