# ADR-006: フロントエンドビルドツール

- ステータス: 承認済

## コンテキスト

ADR-005でフロントエンドフレームワークとしてReact + TypeScriptを採用した。これを前提に、開発サーバー・バンドラーとして機能するビルドツールを選定する。

本プロジェクトは複雑なカレンダーUI（PRD-002, PRD-007）を試行錯誤しながら構築するため、以下の観点で評価する必要がある。

- 開発時のHMR（Hot Module Replacement）速度（試行錯誤サイクルの短縮）
- TypeScript対応の成熟度（ビルド・型チェック統合）
- ADR-002で採用したMonorepo構成内での利用しやすさ（他パッケージとの依存共有・タスクランナー統合）
- 本番ビルド最適化（コード分割・Tree Shaking・アセット圧縮）

候補としてVite、Create React App（CRA）、webpack（直接設定）を検討する。

## スコープ外

- テスト実行環境（Vitest / Jest等）の選定は品質保証設計時に別途決定する
- CSS処理系（PostCSS・Tailwind等）の選定は詳細設計時に決定する
- Monorepoのタスクオーケストレーションツール（Turborepo・Nx等）の選定はADR-002の続きとして別途決定する
- 本番配信環境（CDN・静的ホスティング）は本ADRの対象外

## 決定

フロントエンドビルドツールとして **Vite** を採用する。

## 検討した選択肢

### 選択肢1: Vite

#### 概要

Evan You（Vue作者）が開発するモダンなフロントエンドビルドツール。開発時はネイティブESMベースで即時起動し、本番ビルドはRollupを利用する。React・Vue・Svelte等の主要フレームワークを公式サポートする。

#### メリット

- 開発サーバーがネイティブESMベースで即時起動し、HMRが極めて高速。複雑なカレンダーUIの試行錯誤サイクル（PRD-002, PRD-007）を大きく短縮できる
- TypeScript対応が標準で組み込まれており、追加設定不要で `.ts` / `.tsx` を扱える（型チェックは別途 `tsc --noEmit` またはIDEに委ねる設計思想）
- React公式テンプレート（`create-vite`）が用意されており、初期セットアップが最短で済む
- Monorepoツール（Turborepo・Nx等）のViteサポート事例が豊富で、ADR-002の運用と相性が良い
- 本番ビルドはRollupベースで、Tree Shaking・コード分割・アセット最適化が実用的な水準で組み込まれている
- 設定ファイル（`vite.config.ts`）がシンプルで、拡張が必要な場合もプラグイン機構で対応できる
- 活発にメンテナンスされており、React・Vue・Svelte等の主要フレームワークで採用が広がっている

#### デメリット

- 開発時と本番ビルドで異なるツール（esbuild/Rollup）を使うため、まれに挙動差が発生する
- 高度なカスタマイズが必要な場合はRollupプラグインの知識が必要になる
- 型チェックはビルドプロセスから分離されており、CIで別途 `tsc --noEmit` を実行する運用が必要

### 選択肢2: Create React App（CRA）

#### 概要

Meta（旧Facebook）が提供していた公式のReact初期セットアップツール。webpackを内部で利用し、設定を隠蔽して即座に開発を始められる構成を提供していた。

#### メリット

- 公式ツールとして長年利用され、学習リソースが豊富
- 設定を隠蔽するため初期セットアップの意思決定が最小限
- TypeScriptテンプレート（`create-react-app --template typescript`）が提供されていた

#### デメリット

- 2023年以降、Reactチームが公式に非推奨としVite等への移行を推奨している。長期メンテナンスの見通しが立たない
- HMR・起動速度がViteに比べて大幅に遅く、複雑なカレンダーUIの試行錯誤サイクルを阻害する
- webpack設定が隠蔽されているため、カスタマイズには `eject` または `craco` 等の追加ツールが必要で、拡張性に難がある
- Monorepoツール（Turborepo等）のリファレンスがViteほど整備されていない

### 選択肢3: webpack（直接設定）

#### 概要

長年フロントエンドバンドラーの標準として使われてきたツール。設定ファイル（`webpack.config.js`）で細かい制御ができる。ローダー・プラグインのエコシステムが最も広い。

#### メリット

- 設定の柔軟性が最も高く、複雑な要件にも対応できる
- ローダー・プラグインのエコシステムが最も広く、長年の実績がある
- 本番ビルド最適化の細かい制御が可能

#### デメリット

- 開発サーバーの起動時間・HMR速度がViteに比べて明確に遅い
- 設定ファイルが複雑になりやすく、TypeScript・React・PostCSS等の統合には多くのローダー/プラグイン設定が必要
- 初期セットアップの意思決定コストが高く、React + TypeScript環境をゼロから組むにはViteに比べて明らかに労力が大きい
- 新規プロジェクトでの採用事例が減少傾向にあり、コミュニティの関心もVite/esbuild/Rollup系に移りつつある

## 決定理由

- **HMR速度**: 複雑なカレンダーUI（PRD-002 月/週ビュー、PRD-007 タイムライン）を構築する試行錯誤サイクルにおいて、Viteのネイティブベース開発サーバーは体感で明確な差を生む。CRA/webpackはUIの規模が大きくなるほどHMRが遅くなる
- **TypeScript対応**: Viteは追加設定なしでTypeScriptを扱え、React + TypeScript環境の初期セットアップが最短で済む
- **Monorepo適合性**: Turborepo・Nx等のリファレンス実装でViteの採用が広がっており、ADR-002の運用と相性が良い
- **本番ビルド品質**: Rollupベースの本番ビルドは、Tree Shaking・コード分割・アセット最適化が実用的な水準で組み込まれており、追加設定が最小限
- **長期メンテナンス**: CRAは公式に非推奨となり、Reactコミュニティの推奨はViteに移っている。webpackは新規プロジェクトでの採用事例が減少傾向。Viteは活発にメンテナンスされており、主要フレームワークで採用が広がっている
- **設定のシンプルさ**: `vite.config.ts` の記述量が少なく、必要な拡張はプラグインで対応できる。webpackの複雑な設定を書く負担がない

CRAは公式に非推奨のため見送る。webpackは設定の柔軟性は最も高いが、React + TypeScriptの標準的な構成において必要以上の労力を要し、開発サーバー速度でもViteに劣るため見送る。

## 結果

### 良い影響

- ネイティブESMベースの開発サーバーによりHMRが極めて高速で、複雑なカレンダーUIの試行錯誤サイクルを短縮できる
- TypeScript対応が標準で組み込まれており、初期セットアップの労力が最小限
- Turborepo等のMonorepoツールとの統合事例が豊富で、ADR-002の運用に組み込みやすい
- 設定ファイルがシンプルで、長期的な保守負担が軽い

### 悪い影響

- 開発時（esbuild）と本番ビルド（Rollup）で異なるツールを使うため、まれに挙動差が発生する可能性があり、本番ビルド前の動作確認が必要
- 型チェックはビルドプロセスから分離されており、CIで別途 `tsc --noEmit` を実行する運用ルールを整備する必要がある
- 高度なビルドカスタマイズが必要になった場合はRollupプラグインの知識が必要になる
