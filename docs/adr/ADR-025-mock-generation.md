# ADR-025: モック自動生成ツールの採用

- ステータス: 承認済

## コンテキスト

ADR-001でClean Architectureを採用し、UseCase・Handler層のユニットテストではリポジトリなどの外部依存をモックに差し替える必要がある。現状は `testify` のみ導入済みで、モック生成ツールがないため手書きモックが必要な状態だった。

インターフェース定義から型安全なモックを自動生成し、ユニットテストの品質と保守性を高める。

## スコープ外

- 統合テスト・E2Eテストでのモック利用（実DBを使う）
- フロントエンドのモック戦略

## 決定

**`uber-go/mock`（`mockgen`）を採用する。**

- `go tool mockgen` でインターフェースからモックを自動生成する
- `//go:generate` ディレクティブをインターフェース定義ファイルに記述する
- 生成先は `<package>/generated/` ディレクティブで統一し、gitignore対象とする
- `go generate ./...` でプロジェクト全体のモックを一括再生成できる

## 検討した選択肢

### 選択肢1: uber-go/mock（mockgen）

#### 概要

Uberが管理する `go.uber.org/mock` パッケージ。もともとはGoogleの `golang/mock` だったが、アーカイブ後にuberがフォークして継続メンテしている。

#### メリット

- Go公式の `go tool` ディレクティブで管理できる（別途インストール不要）
- インターフェースから型安全なモックを自動生成する
- `EXPECT()` による期待値設定が明示的で可読性が高い
- testifyと相互排他ではなくアサーションには引き続きtestifyを使える
- アクティブにメンテされておりGo最新バージョンへの追従が速い

#### デメリット

- `gomock.Controller` のセットアップが少し冗長
- モックファイルを再生成し忘れるとインターフェースとズレる（CIで検知が必要）

### 選択肢2: testify/mock（手書き）

#### 概要

`github.com/stretchr/testify/mock` を使い、インターフェースに対するモック構造体を手書きする。

#### メリット

- 追加ツールが不要
- 既存の `testify` との親和性が高い

#### デメリット

- インターフェースが変わるたびに手作業でモックを更新する必要がある
- ボイラープレートが多く保守コストが高い
- 型安全性が低い（`Arguments` が `interface{}` ベース）

### 選択肢3: moq

#### 概要

`github.com/matryer/moq` を使い、シンプルな関数ベースのモックを生成する。

#### メリット

- 生成コードがシンプルで読みやすい
- `gomock.Controller` が不要

#### デメリット

- コールカウントや呼び出し順の検証には手書きコードが必要
- uber-go/mockほどメンテが活発ではない

## 決定理由

- `go tool` での管理が可能で、チームメンバーの環境差を排除できる点を最重視した
- 期待値の明示的な宣言（`EXPECT()` チェーン）により、テストの意図がコードから読み取りやすい
- 既存の `testify` との併用が自然にできる

## 結果

### 良い影響

- インターフェースが変わったとき `go generate ./...` で即座にモックを更新できる
- テストコードの記述量が減り、リポジトリなどの依存関係をユニットテストで安全に差し替えられる

### 悪い影響

- モックの再生成を忘れてインターフェースとズレた状態になるリスクがある（CIの `generate` ステップで検知する）
