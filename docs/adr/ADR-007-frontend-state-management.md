# ADR-007: フロントエンド状態管理

- ステータス: 承認済

## コンテキスト

ADR-005でフロントエンドフレームワークとしてReact + TypeScriptを採用した。これを前提に、状態管理ライブラリを選定する。

本プロジェクトのフロントエンドが扱う状態は、性質の異なる2種類に大別できる。

- **サーバー状態**: 予定データ・タグ一覧・共有リンク・認証状態など、バックエンドAPIから取得しキャッシュ・再検証する必要がある状態（PRD-001, PRD-003, PRD-004, PRD-008）
- **クライアント状態**: 選択中の日付・表示ビュー（月/週/日、PRD-002/PRD-007）・モーダル開閉・フィルター条件など、UI操作の結果として保持されクライアント内で完結する状態

これらの状態管理にあたって、以下の観点で評価する必要がある。

- サーバー状態（API取得・キャッシュ・再検証）の管理しやすさ（複数端末間のデータ鮮度管理、PRD-001）
- クライアント状態の管理しやすさ（軽量にグローバル状態を扱えるか）
- ブラウザ通知（PRD-006）や共有URL（PRD-004）などのイベント駆動処理との連携
- TypeScriptとの相性（型推論の精度）
- Clean Architecture（ADR-001）のAdapter層への閉じ込めやすさ
- ボイラープレートの少なさ・学習コスト

候補としてTanStack Query + Zustand、Redux Toolkit（RTK Query含む）、SWR + React Contextを検討する。

## スコープ外

- ルーティングライブラリ（React Router等）の選定は詳細設計時に決定する
- フォーム管理ライブラリ（React Hook Form等）の選定は詳細設計時に決定する
- バリデーションライブラリ（zod等）の選定は詳細設計時に決定する
- 認証情報の永続化戦略（Cookie / localStorage等）はPRD-001の詳細設計時に決定する
- サーバー状態の同期戦略（WebSocket / SSE / ポーリング等）は詳細設計時に決定する

## 決定

フロントエンド状態管理として、サーバー状態とクライアント状態を分離し、以下の2ライブラリを組み合わせて採用する。

- **サーバー状態**: TanStack Query（React Query v5）
- **クライアント状態**: Zustand

## 検討した選択肢

### 選択肢1: TanStack Query + Zustand

#### 概要

サーバー状態とクライアント状態を明確に分離し、それぞれに最適なライブラリを組み合わせる構成。TanStack Queryはサーバー状態のキャッシュ・再検証・楽観的更新に特化したライブラリ。Zustandはフックベースの軽量なクライアント状態管理ライブラリ。

#### メリット

- **役割分離の明快さ**: サーバー状態（TanStack Query）とクライアント状態（Zustand）が明確に分離され、コード上での責務が視覚的に区別できる
- **サーバー状態管理の強力さ**: TanStack Queryはキャッシュ・再検証・バックグラウンド更新・楽観的更新・無限クエリなどを標準機能として提供し、複数端末間のデータ鮮度管理（PRD-001）に必要な `refetchOnWindowFocus` 等が組み込まれている
- **クライアント状態の軽量性**: Zustandは1つのフックとストア定義のみで動作し、Providerが不要。ビュー切り替え（PRD-002/PRD-007）やモーダル開閉といった状態を最小のボイラープレートで扱える
- **TypeScript対応**: 両ライブラリともTypeScriptファースト設計で、型推論の精度が高い
- **通知・イベント連携**: TanStack QueryのミューテーションフックとZustandのストア更新を組み合わせて、Notification API（PRD-006）呼び出しや共有URL（PRD-004）発行後のUI更新を素直に書ける
- **Clean Architectureとの整合**: TanStack Queryの `useQuery` / `useMutation` はカスタムフックとしてラップしやすく、UseCase呼び出しをAdapter層のフックに集約する設計と親和性が高い
- **ボイラープレートの少なさ**: Redux Toolkitに比べて記述量が明確に少なく、学習コストも低い

#### デメリット

- 2つのライブラリを併用するため、それぞれの責務分担ルールをチームで統一する必要がある
- サーバー状態にクライアント状態を混ぜ込みたい場面（例: TanStack Queryのキャッシュに一時的なフィルタ結果を保存する等）で使い分けの判断が必要
- Reduxのような単一のグローバルストアではないため、開発ツールで状態全体を俯瞰する体験はReduxに劣る

### 選択肢2: Redux Toolkit（RTK Query含む）

#### 概要

Reduxの公式推奨ラッパー。ボイラープレートを大幅に削減し、`createSlice`・`createAsyncThunk`・RTK Queryを標準機能として提供する。RTK QueryはTanStack Query相当のサーバー状態管理機能を提供する。

#### メリット

- サーバー状態（RTK Query）とクライアント状態（Slice）が同一のストア・同一の開発ツールで一貫して扱える
- Redux DevToolsによる状態遷移のタイムトラベルデバッグが最も強力
- 大規模チームでの規約整備が最もしやすい（Reduxパターンの標準化が進んでいる）
- 学習リソース・ベストプラクティスが豊富

#### デメリット

- TanStack Query + Zustandに比べてボイラープレート（Slice定義・Action・Reducer・型定義）が多く、記述量が明確に増える
- 単一グローバルストアの思想がZustandの局所ストアに比べて重く、シンプルなクライアント状態にも一定の構造化コストがかかる
- RTK QueryはTanStack Queryに比べてキャッシュ制御・楽観的更新のAPI表現力で劣る場面がある
- ストアの型定義がChain of Type Argumentsで複雑になりやすく、Zustandに比べて型推論の直感性が劣る
- Providerが必要で、テスト時のセットアップがZustandより煩雑

### 選択肢3: SWR + React Context

#### 概要

Vercel製のサーバー状態管理ライブラリSWRと、React標準のContext APIを組み合わせる構成。SWRはTanStack Queryと類似のキャッシュ・再検証機能を提供する。

#### メリット

- SWRはAPIがシンプルで学習コストが低い
- React Contextは標準機能のため追加ライブラリ不要
- Vercel（Next.js作者）製で、Vercelエコシステムとの親和性が高い

#### デメリット

- SWRはTanStack Queryに比べて機能面（楽観的更新・無限クエリ・キャッシュ細粒度制御）で劣る場面が多く、複数端末のデータ鮮度管理（PRD-001）で必要な高度なキャッシュ制御が難しい
- React Contextはグローバル状態としては再レンダリング制御が難しく、頻繁に更新される状態（例: 選択中の日付）で不要な再レンダリングが発生しやすい。Zustandはセレクタベースで最適化されている
- Contextで状態を分割管理するとProvider階層が深くなり、テスト・保守で負担が増える
- TypeScript対応はTanStack Query/Zustandに比べて型推論の精度がやや劣る

## 決定理由

- **サーバー状態とクライアント状態の分離**: 本プロジェクトはサーバー状態（予定データ・タグ等）とクライアント状態（表示ビュー・モーダル開閉等）が明確に異なる性質を持つ。両者を分離することで、それぞれに最適な機能（キャッシュ / 局所グローバル状態）を素直に使い分けられる
- **複数端末間のデータ鮮度管理（PRD-001）**: TanStack Queryは `refetchOnWindowFocus` `refetchOnReconnect` `staleTime` などのキャッシュ制御をシンプルなAPIで提供する。RTK Queryも同等機能を持つがAPIの表現力でTanStack Queryが優位、SWRは機能面で劣る
- **ビュー切り替えパフォーマンス（PRD-002 制約: 1秒以内）**: TanStack Queryのキャッシュ機構により、月/週/日ビュー切り替え時の再フェッチを抑制でき、ADR-005で決定したReact 18のconcurrent renderingと組み合わせて要件を達成しやすい
- **Clean Architectureとの整合**: `useQuery` / `useMutation` をカスタムフックにラップし、UseCase呼び出しに委譲する設計により、状態管理ライブラリ依存をAdapter層（フック層）に閉じ込められる。ADR-001の狙いと一致する
- **ボイラープレートの少なさ**: Redux Toolkitに比べてTanStack Query + Zustandの記述量が明確に少なく、開発速度と保守負担で優位
- **TypeScript対応**: 両ライブラリともTypeScriptファースト設計で、型推論の精度がRedux Toolkit・SWR + Contextに勝る
- **ブラウザ通知連携（PRD-006）**: TanStack Queryの `useMutation` の `onSuccess` コールバックからNotification APIを呼び出す、Zustandのストアで通知許可状態を保持するなど、素直に組める

Redux Toolkitは単一ストアの一貫性が魅力だが、本プロジェクトの規模ではボイラープレートが過剰で、Adapter層への閉じ込めやすさもフック集約型のTanStack Query + Zustandに劣る。SWR + Contextは軽量だがサーバー状態機能・再レンダリング制御でTanStack Query + Zustandに明確に劣るため見送る。

## 結果

### 良い影響

- サーバー状態とクライアント状態が役割で明確に分離され、コード上で責務が視覚的に区別できる
- TanStack Queryのキャッシュ機構により、月/週ビュー切り替え時の再フェッチを抑制でき、PRD-002の「1秒以内」を達成しやすい
- `refetchOnWindowFocus` 等の標準機能により、複数端末間のデータ鮮度管理（PRD-001）が最小限のコードで実現できる
- Zustandは Providerが不要で、テスト時のセットアップが最小限で済む
- カスタムフックにUseCase呼び出しと状態管理を集約することで、コンポーネントを純粋なViewに保ちClean Architecture（ADR-001）と整合する

### 悪い影響

- 2つのライブラリを併用するため、サーバー状態とクライアント状態の分離ルールをチームで統一する必要がある
- 単一ストアではないため、開発ツールで状態全体を俯瞰する体験はReduxに劣る（両ライブラリともDevToolsは個別に提供される）
- サーバー状態の一部をクライアント状態にキャッシュしたい場面での使い分け判断が発生する
- 選定した2ライブラリのアップデート追従を個別に行う必要がある
