# ADR-004: Webフレームワーク

- ステータス: 承認済

## コンテキスト

ADR-003でバックエンド言語としてGoを採用した。これを前提に、HTTPルーティング・ミドルウェアを担うWebフレームワークを選定する。

本プロジェクトのAPIは、認証（PRD-001）・予定CRUD（PRD-003）・共有URL（PRD-004）・タグ管理（PRD-008）などをRESTfulに提供する。Webフレームワークの選定にあたっては、以下の観点で評価する必要がある。

- ADR-001で採用したClean ArchitectureのAdapter層への閉じ込めやすさ（Domain層・UseCase層をフレームワーク非依存に保てるか）
- `net/http` 互換性（ハンドラー関数の型がフレームワーク独自型に置き換わるか）
- ミドルウェア機構のシンプルさ（認証・ロギング・CORS等を素直に組めるか）
- コミュニティ・エコシステムの成熟度と長期メンテナンスの安心感
- 将来的なgRPC（別プロトコルによるサービス間通信）やGraphQL（`/graphql` エンドポイント追加）への拡張が容易かどうか

候補としてchi、Gin、Echo、`net/http`（標準ライブラリのみ）を検討する。

## スコープ外

- 認証ミドルウェアの具体的な実装・セッション管理ライブラリの選定はPRD-001の詳細設計時に決定する
- APIスキーマ定義（OpenAPI等）とコード生成方針は本ADRの対象外
- リクエストバリデーションライブラリの選定は詳細設計時に決定する
- レートリミット・監視ミドルウェアの選定は運用設計時に別途決定する

## 決定

Webフレームワークとして **chi**（`github.com/go-chi/chi/v5`）を採用する。

chiはルーティングとミドルウェアに限定して利用し、ハンドラー関数の型は `http.HandlerFunc`（`http.ResponseWriter` と `*http.Request`）を維持する。

## 検討した選択肢

### 選択肢1: chi

#### 概要

`net/http` の `http.Handler` インターフェースに完全準拠した軽量ルーター。サブルーティング・ミドルウェア機構・URLパラメータ抽出を提供するが、独自のContext型は導入しない。

#### メリット

- `net/http` と完全互換で、ハンドラー関数の引数が `http.ResponseWriter` と `*http.Request` のままになる。Adapter層以外にフレームワーク依存が入らず、Clean Architecture（ADR-001）のDependency Ruleを厳格に守れる
- ミドルウェアも `func(http.Handler) http.Handler` の標準的なシグネチャで書けるため、`net/http` エコシステムのミドルウェアがそのまま流用できる
- コードベースが小さく、内部構造を追いやすい
- サブルーティング（`Route`）による階層的なルート定義が明快で、REST APIのリソース設計に素直に対応できる
- 依存が少なく、長期メンテナンスの安心感がある
- **gRPC/GraphQL拡張への対応**: GraphQL（gqlgenの`http.Handler`実装）をchiルートにマウントするだけで追加できる。gRPCサーバーを別ポートで並列稼働する際も、UseCase層が`net/http`非依存なためgRPCハンドラーから直接呼び出せる

#### デメリット

- Gin/Echoに比べてビルトインの便利機能（バインディング、レンダリング等）が少なく、リクエストパース・レスポンス整形は自前で書くことが多い
- ドキュメントは十分だが、Gin/Echoに比べて日本語の学習リソースが少ない

### 選択肢2: Gin

#### 概要

Goで最も人気のあるWebフレームワークの一つ。独自の `gin.Context` を通じてリクエスト/レスポンス操作・バインディング・レンダリングを一括で提供する高機能フレームワーク。

#### メリット

- リクエストバインディング・バリデーション・JSONレンダリングなどがビルトインで揃っており、開発初速が速い
- コミュニティが大きく、日本語を含む学習リソースが豊富
- ルーティング性能がベンチマークで上位

#### デメリット

- ハンドラー関数のシグネチャが `func(c *gin.Context)` となり、`net/http` 標準と非互換。Adapter層以外でリクエスト/レスポンスに触れる箇所（例：一部のミドルウェア）がGin依存になりやすい
- `gin.Context` がリクエスト・レスポンス・バインディング・エラーハンドリングを一手に担うため、Clean ArchitectureのAdapter層に閉じ込めようとしても境界がぼやけやすい
- 独自エコシステム（`gin.HandlerFunc`）を持つため、`net/http` 標準のミドルウェアをそのまま使うにはアダプタが必要
- ビルトイン機能が多く、フレームワーク自体の学習コストがchiより高い

### 選択肢3: Echo

#### 概要

Ginと同様の高機能Webフレームワーク。独自の `echo.Context` を通じてリクエスト/レスポンス操作を提供する。ミドルウェアやバインディングの機能が充実している。

#### メリット

- リクエストバインディング・バリデーション・レンダリングがビルトインで揃っている
- ミドルウェアが豊富に用意されている
- ルーティングDSLが直感的

#### デメリット

- ハンドラー関数のシグネチャが `func(c echo.Context) error` となり、`net/http` 標準と非互換。Ginと同じくフレームワーク依存が広がりやすい
- `echo.Context` を経由するため、Clean ArchitectureのAdapter層以外の場所にEcho依存が漏れやすい
- `net/http` 標準ミドルウェアの流用にはアダプタが必要

### 選択肢4: net/http（標準ライブラリのみ）

#### 概要

Goの標準ライブラリのHTTPサーバー機能のみでルーティング・ハンドラーを構築する構成。Go 1.22以降は `http.ServeMux` にパスパラメータ機能が追加された。

#### メリット

- 外部依存が一切なく、長期メンテナンスの安心感が最も高い
- 学習コストが低く、標準ライブラリの知識だけで完結する
- Clean ArchitectureのAdapter層への閉じ込めやすさは最良（そもそもフレームワークがない）

#### デメリット

- サブルーティング・ミドルウェアチェーンなど、実運用で必要な機能を自前で組む必要がある
- ミドルウェア機構を自作すると、標準的なパターンがない分チームで実装スタイルが揺れやすい
- ルート定義が肥大化した際の可読性・保守性がchiに劣る
- 認証・CORS・ロギング等のミドルウェアも自前実装または既存ライブラリの寄せ集めになる

## 決定理由

- **Clean Architectureとの整合**: chiは `net/http` と完全互換で、ハンドラー関数の引数が `http.ResponseWriter` と `*http.Request` のままになる。Gin/Echoは `gin.Context` / `echo.Context` を経由するため、Adapter層以外にフレームワーク依存が漏れやすい。chiであればADR-001のDependency Ruleを最も素直に守れる
- **ミドルウェアの標準性**: chiのミドルウェアは `func(http.Handler) http.Handler` の標準形で書けるため、`net/http` エコシステムのミドルウェア（既存の認証・ロギング等）をそのまま流用できる
- **必要十分な機能**: 標準の `net/http` だけでは自前で組む必要があるサブルーティング・URLパラメータ・ミドルウェアチェーンを、chiは最小限の抽象で提供する。`net/http` 単体より生産性が高く、Gin/Echoよりフレームワーク依存が薄い
- **長期メンテナンス**: chiは依存が少なくコードベースが小さいため、長期運用でも追跡・アップデートしやすい
- **Domain/UseCase層の非依存性**: Adapter層のハンドラーは `http.HandlerFunc` として書き、UseCase呼び出しに委譲する。フレームワークがハンドラーの外に染み出さないため、Domain層・UseCase層の単体テストがフレームワークなしで実行できる
- **gRPC/GraphQL拡張への対応**: `net/http` ベースのためGraphQL（gqlgen等の`http.Handler`）をchiルートにマウントするだけで追加可能。Gin/EchoではGin/Echo独自の型への変換アダプタが必要になる。gRPCへ移行する場合もUseCase層が`http.Handler`非依存なため、gRPCハンドラーへの置き換えコストが最小限

Gin/Echoは高機能で開発初速が高いが、独自Context型がAdapter層以外に漏れるリスクがあり、Clean Architectureとの整合を保つには常に境界に気を配る必要がある。`net/http` 単体は依存を最小化できるが、ミドルウェア機構・サブルーティングを自前で組む運用コストが大きい。両者の中間として、`net/http` 互換のchiが本プロジェクトに最も適合する。

## 結果

### 良い影響

- ハンドラー関数が `http.HandlerFunc` のままになり、Adapter層にWebフレームワーク依存を閉じ込められる。Domain層・UseCase層の単体テストがフレームワークなしで実行できる（ADR-001の狙いと一致）
- `net/http` 標準のミドルウェアをそのまま流用でき、認証・CORS・ロギングなどのエコシステムを幅広く活用できる
- chiのコードベースが小さく依存も少ないため、長期メンテナンスの負担が軽い
- サブルーティング機能によりRESTリソースごとのルート定義が整理される
- `net/http` 互換のため、将来のGraphQL追加（gqlgenの`http.Handler`をルートにマウント）やgRPC移行時のUseCase層再利用が容易

### 悪い影響

- Gin/Echoのようなバインディング・バリデーション・レンダリング機能はビルトインではないため、リクエストパース・レスポンス整形は自前で書くか別ライブラリを併用する必要がある
- Gin/Echoに比べて日本語学習リソースが少ないため、キャッチアップに公式ドキュメント（英語）を読む必要がある
- ミドルウェアやハンドラーのパターンをチームで揃えるための実装規約整備が必要
