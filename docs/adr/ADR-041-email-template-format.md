# ADR-041: メールテンプレートの形式とテンプレートエンジン

- ステータス: 承認済

## コンテキスト

PRD-010 のメール通知基盤では、メールの種類（`EmailKind`）ごとに件名・本文のテンプレート（`EmailTemplate`）を定義し、送信ワーカーが送信時に本文用パラメータ（`TemplateParams`）を埋め込んで件名・本文を作る（SPEC-010）。テンプレートはアプリケーション起動時に静的レジストリへ登録する。

SPEC-010 で決まっている制約:

- 件名・本文はテンプレートからだけ作り、ユースケースから文字列を直接渡せない
- テンプレートは埋め込むパラメータのキーを定義し、送信要求のキーと一致しない（不足・余分がある）場合は送信要求をエラーにする
- 送信時に埋め込みに失敗した場合は送信せず、失敗コード `template_render_failed` で「送信失敗」にする
- `EmailTransport` は宛先・差出人・件名・本文を受け取る

送るメールはパスワードリセット・アカウントロック通知（PRD-011）などのアカウントに関するお知らせで、本文の中心はリセット用URLなどのリンクと短い説明文になる。PRD-010 は差出人名・差出人アドレスでサービスからのメールだと見分けられることを求めており、本文の装飾は求めていない。

選定観点:

- パラメータの値（URL・ユーザー名など）を埋め込んだときに、本文・件名の構造を壊す注入が起きないか
- 迷惑メール判定・受信クライアントでの表示に不利にならないか
- テンプレートの記述・保守のコストが小さいか
- 追加の依存ライブラリが要らないか

## スコープ外

- 本文用パラメータの保存方式（[ADR-039](./ADR-039-email-template-params-storage.md)）
- 送信サービス・送信プロトコルの選定（`EmailTransport` の実装側で決める）
- メールの種類ごとの文面（メールの種類を追加する仕様書で定義する）
- 多言語対応

## 決定

1. 件名・本文はプレーンテキストだけにする。HTMLパートは持たない。`EmailTransport.Send` に渡す本文は1つで、`Content-Type: text/plain; charset=UTF-8` として送る
2. テンプレートエンジンには Go 標準ライブラリの `text/template` を使う。件名・本文それぞれを `Option("missingkey=error")` を付けてパースし、パラメータに存在しないキーを参照したら埋め込みをエラーにする
3. `TemplateParams` は文字列キー・文字列値のマップ（`map[string]string`）にする。テンプレートからは `{{.reset_url}}` のようにキー名で参照する
4. テンプレートで使える構文は、`{{.key}}` によるパラメータの参照、`if` / `else if` / `else`、関数呼び出し（`eq`・`printf` など）だけにする。`range`・`with`・変数（`$x := …`・`$.key`）・`.` 単体・`.key.sub`・`define` / `block` / `template` は使えない。これらは `.` の指す先を変えたり別のテンプレートへ参照を移したりするため、どのキーを参照しているかを構文木から読み取れない
5. `EmailTemplate` を生成するとき、以下を行う。どれかが失敗した場合は生成をエラーにし、アプリケーションの起動を失敗させる
    - 件名・本文をパースする（構文誤り）
    - パースした構文木（`text/template/parse`）を辿り、実行されるかどうかに関係なくすべての分岐から `{{.key}}` の参照を集める。決定4にない構文があればエラーにする。集めたキーが定義したキーと過不足なく一致しなければエラーにする（定義していないキーの参照・定義したのに使っていないキー）
    - 定義したすべてのキーにダミー値を入れて試しに埋め込む（関数の引数の数の誤りなど、構文木からは分からない誤り）
6. 埋め込んだ後の件名に改行文字（CR・LF）が含まれる場合は埋め込みの失敗として扱う（送信時は `template_render_failed`）。件名はメールヘッダーに入るため、改行を含む値によるヘッダーの注入を防ぐ

## 検討した選択肢

### 選択肢1: プレーンテキストだけ + `text/template`（採用）

#### 概要

件名・本文ともプレーンテキストのテンプレートを `text/template` で埋め込む。

#### メリット

- HTMLとして解釈される部分がないため、パラメータの値によるHTML・スクリプトの注入が起きない。エスケープ漏れを気にする必要がない
- URLはエスケープされずそのまま本文に入り、受信クライアントが自動でリンクにする
- テキストだけのメールは迷惑メール判定で不利になりにくく、どの受信クライアントでも同じように表示される
- メールの種類ごとのテンプレートが件名・本文の2つだけで済む
- 標準ライブラリだけで実現でき、依存が増えない

#### デメリット

- ロゴ・ボタンなどの装飾を入れられない
- 長いURLはクライアントによって折り返され、読みにくくなる場合がある

### 選択肢2: HTMLだけ + `html/template`

#### 概要

本文をHTMLのテンプレートとし、`html/template` の文脈に応じた自動エスケープで埋め込む。件名は `text/template` で作る。

#### メリット

- ボタン・ロゴなどで、サービスからのメールらしい見た目にできる
- `html/template` の自動エスケープで、パラメータの値による注入を防げる

#### デメリット

- テキストパートのないHTMLだけのメールは迷惑メール判定で不利になりやすく、テキスト表示のクライアントで読みにくい
- 受信クライアントごとにHTML・CSSの対応差が大きく、表示の確認コストがかかる
- HTMLのメールはフィッシングでもよく使われる形式で、PRD-010 の「正規のメールだと見分けられる」に寄与しない

### 選択肢3: マルチパート（テキスト + HTML）

#### 概要

`text/template` のテキスト本文と `html/template` のHTML本文を両方定義し、`multipart/alternative` で送る。

#### メリット

- HTML対応のクライアントでは装飾した表示、テキスト表示のクライアントではテキストで読める
- 迷惑メール判定でもHTMLだけより不利になりにくい

#### デメリット

- メールの種類ごとにテキスト版・HTML版の2つの本文を書き、内容を一致させ続ける必要がある
- `EmailTransport.Send` が本文を2つ受け取る形になり、SPEC-010 の「宛先・差出人・件名・本文を受け取る」から変わる
- 装飾が要件にない現状では、保守コストに見合う効果がない

## 決定理由

- **注入の防止**: 選択肢1は本文にHTMLとして解釈される部分がなく、エスケープの正しさに依存しない。件名は決定6の改行チェックでヘッダーの注入を防げる。選択肢2・3はHTMLの注入対策を `html/template` のエスケープに頼り、テキストとHTMLで2系統の対策が要る
- **到達性・表示**: プレーンテキストのメールは迷惑メール判定で不利になりにくく、クライアントによる表示差がない。PRD-010 の成功指標（送信失敗率1%未満）に対しても不利な要素がない
- **保守コスト**: 選択肢1はメールの種類ごとに件名・本文の2つのテンプレートだけを保守すればよい。選択肢3は本文が2つになり、内容のずれが起きうる
- **依存**: 3つの選択肢とも標準ライブラリで実現でき、この観点では差がない
- 装飾は PRD-010 の要件になく、サービスからのメールだと見分ける手段は差出人名・差出人アドレスと送信ドメイン認証が担う

## 検証結果

Go 1.27 で以下を確認した。

- `Option("missingkey=error")` を付けた `text/template` に `map[string]string` を渡し、マップにないキーを参照すると `map has no entry for key "url"` のエラーで埋め込みが失敗する
- `text/template` は値をエスケープせず、`https://x/?a=1&b=2` や `<b>&` は埋め込み後もそのまま残る
- 全キーに同じダミー値を入れる試しの埋め込みだけでは、`{{if eq .plan "pro"}}{{.pro_url}}{{end}}`（キーは `plan` だけ）のように実行されない分岐の中の参照を見つけられない。構文木を辿る方式では、この参照も `else` / `else if` の中の参照も起動時にエラーになることを単体テストで確認した

## 結果

### 良い影響

- 本文用パラメータの値がHTMLとして解釈されないため、メール本文への注入の心配がない
- テンプレートの誤り（構文誤り・定義していないキーの参照・使っていないキー）は、分岐の中にあってもアプリケーションの起動時に見つかる。送信時の `template_render_failed` は想定外の場合だけになる
- 依存ライブラリが増えない

### 悪い影響

- 本文を装飾できない。装飾が要件になった場合は、本ADRを置き換えてマルチパート（選択肢3）を再検討する
- `range`・`with`・変数を使えないため、繰り返しのある本文は書けない。アカウントに関するお知らせの本文は短い説明文とリンクで足りるので、この制限を受け入れる。繰り返しが必要になった場合は、本ADRを置き換えて照合方法を再検討する
