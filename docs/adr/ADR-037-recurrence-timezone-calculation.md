# ADR-037: 繰り返し予定の日時計算をサーバーで行う

- ステータス: 承認済
- 関連Issue: #26
- 関連ADR: ADR-036（APIで扱う日時のタイムゾーン）

## コンテキスト

繰り返し予定（SPEC-009）では、1回の登録で最大2年分の回を生成する。各回の開始・終了の時刻は、シリーズを作成した端末のタイムゾーンの壁時計時刻で最初の回と同じにし、夏時間の切り替えをまたいでも時刻をずらさない。例えば `America/New_York` で毎週月曜10:00の予定は、夏時間の前後どちらでも10:00に開始する（UTCでは15:00から14:00に変わる）。

ADR-036は、APIの日時をUTC（末尾 `Z`）に統一し、ローカルの区切りの計算はクライアントで行う方針を決めた。日付とIANAタイムゾーン名を受け取ってバックエンドで計算する案（ADR-036の選択肢2）は、バックエンドにタイムゾーンデータベースが必要になること、クライアントとバックエンドで計算が分かれることを理由に採用しなかった。

繰り返しの各回の日時を計算するには、2年分の各回について、ローカルの壁時計時刻をUTCに変換する必要がある。この計算をどこで行うかを決める。ADR-036の決定1〜6（日時の形式・範囲検索・pgxの設定）は変えない。

選択肢は以下の観点で評価する。

- 正確さ: 夏時間をまたいでも、すべての回の壁時計時刻が最初の回と同じになるか
- リクエストの単純さ: 作成・「以降すべて変更」・「すべて変更」のリクエストが、回の数によらず一定の大きさで済むか
- 整合性: 「以降すべて変更」などでシリーズを作り直すとき、作成時と同じ規則で再計算できるか

## スコープ外

- 予定の表示・入力をユーザー設定のタイムゾーンで行う機能（ADR-036のスコープ外と同じ）
- 繰り返しの各回を予定として保存するか、表示時に展開するか（SPEC-009の設計で決定）

## 決定

1. 繰り返しの各回の日時は、バックエンドが計算する。クライアントは最初の回の `startAt` / `endAt`（UTC、ADR-036の決定1）と、シリーズのタイムゾーンをIANAタイムゾーン名（例: `Asia/Tokyo`）で送る
2. クライアントは、タイムゾーン名を `Intl.DateTimeFormat().resolvedOptions().timeZone` で取得する
3. バックエンドは、タイムゾーン名を `time.LoadLocation` で解釈し、壁時計時刻のまま日付を進めてからUTCに変換する。解釈できないタイムゾーン名は 400 `VALIDATION_ERROR`（ADR-013）を返す
4. タイムゾーン名はシリーズに保存し、「以降すべて変更」「すべて変更」で回を再計算するときも同じタイムゾーン名を使う
5. バックエンドのバイナリに `time/tzdata` パッケージを埋め込み、実行環境のタイムゾーンデータベースの有無に依存しないようにする
6. この方式は繰り返しの回の生成にだけ使う。範囲検索などその他の日時の扱いはADR-036に従う

## 検討した選択肢

### 選択肢1: IANAタイムゾーン名を受け取り、バックエンドで計算する（採用）

#### 概要

クライアントは最初の回の日時とIANAタイムゾーン名を送る。バックエンドが2年分の各回の日時を計算する。

#### メリット

- 夏時間をまたいでも、すべての回の壁時計時刻を最初の回と同じにできる
- リクエストの大きさが回の数によらず一定
- シリーズに保存したタイムゾーン名で、作り直しのときも同じ規則で再計算できる

#### デメリット

- バックエンドにタイムゾーンデータベースが必要になる
- 回の日時の計算がバックエンドに、カレンダー表示のローカル日時への変換がクライアントにあり、両者のタイムゾーンデータの版の差で結果が食い違う可能性がある

### 選択肢2: クライアントが各回の日時を計算して送る

#### 概要

ADR-036の方針どおり、クライアントがローカルのタイムゾーンで2年分の各回の日時を計算し、UTCで送る。

#### メリット

- バックエンドにタイムゾーンデータベースが不要で、ADR-036の方針から外れない

#### デメリット

- リクエストが回の数に比例して大きくなる（毎日の繰り返しで約730回分）
- 「以降すべて変更」「すべて変更」のたびに、クライアントがすべての回を計算し直して送る必要がある
- 送られた日時がシリーズの規則（パターン・除外日・2年以内）に合っているかを、バックエンドで別途検証する必要がある

### 選択肢3: 分単位のUTCオフセットを受け取り、バックエンドで計算する

#### 概要

クライアントは最初の回の日時と、`540` のようなUTCオフセット（分）を送る。バックエンドはそのオフセットで各回の日時を計算する。

#### メリット

- バックエンドにタイムゾーンデータベースが不要
- リクエストの大きさが回の数によらず一定

#### デメリット

- オフセットは1つの値なので、夏時間をまたいだ回は壁時計時刻が1時間ずれる

## 決定理由

- 正確さ: 選択肢1・2は夏時間をまたいでも壁時計時刻を保てる。選択肢3は夏時間をまたいだ回の時刻がずれ、SPEC-009の要件を満たせない
- リクエストの単純さ: 選択肢1・3はリクエストの大きさが一定。選択肢2は回の数に比例して大きくなる
- 整合性: 選択肢1は保存したタイムゾーン名で、作成時と同じ規則のまま再計算できる。選択肢2は、作り直しのたびにクライアントの計算結果をバックエンドで検証し直す必要がある

ADR-036で選択肢2（バックエンドでの計算）を採用しなかった理由のうち、タイムゾーンデータベースへの依存は決定5で解消する。計算の分担による食い違いは、繰り返しの回の生成だけに限定する（決定6）。

## 検証結果

- Go 1.25.0 で、`time.LoadLocation("America/New_York")` を使い、2026-03-02（月）10:00 から `AddDate(0, 0, 7)` で週ごとに日付を進めた。夏時間の開始日（2026-03-08）をまたいでも、ローカル時刻はすべて10:00で、UTCは `15:00Z` から `14:00Z` に変わることを確認した
- `time.LoadLocation("Invalid/Zone")` が `unknown time zone Invalid/Zone` のエラーを返すことを確認した
- Node.js で `Intl.DateTimeFormat().resolvedOptions().timeZone` が、環境変数 `TZ` に応じて `Asia/Tokyo` や `America/New_York` のIANA名を返すことを確認した
- `time/tzdata` を埋め込んだバイナリが、システムのタイムゾーンデータベースがない環境でも `time.LoadLocation` を解決できることは、`time/tzdata` パッケージのドキュメントで確認した。システムのデータベースがない環境での実行は確認していない

## 結果

### 良い影響

- 夏時間のあるタイムゾーンのユーザーでも、繰り返し予定の時刻がずれない
- 繰り返し予定の作成・変更のリクエストが、回の数によらず小さく済む

### 悪い影響

- `time/tzdata` の埋め込みで、バックエンドのバイナリが約450KB大きくなる。影響は小さいため対処しない
- バックエンドに埋め込んだタイムゾーンデータと、ブラウザのタイムゾーンデータの版が異なると、タイムゾーン規則が変わった地域で回の時刻が食い違う可能性がある。Goのバージョンを上げると埋め込みデータも更新されるため、Goの定期的な更新で対処する
