# ADR-034: E2Eテストフレームワークと実行構成

- ステータス: 承認済

## コンテキスト

フロントエンド（Vite + React）とバックエンド（Go + PostgreSQL）を通した、ブラウザ操作によるシナリオテストの仕組みが必要になった（Issue #129）。
既存のテストは単体テスト（Vitest・Go test）とバックエンド結合テスト（testcontainers）に限られ、画面からAPI・DBまでを通した動作はCIで検証されていない。

次の3点を決める必要がある。

- E2Eテストフレームワーク
- モノレポ内での配置先
- CIでのシステム（DB・バックエンド・フロントエンド）の起動方法

## スコープ外

- 個別のE2Eシナリオの設計（最初のスモークテストを除く）
- ビジュアルリグレッションテスト
- 本番・ステージング環境に対するE2Eテスト

## 決定

- フレームワークに **Playwright**（`@playwright/test`）を採用する。
- E2Eテストは独立したワークスペースパッケージ `apps/e2e` に置く（`apps/web` には含めない）。
- ブラウザは Chromium のみを対象とする。
- CIでは次の構成でシステムを起動してテストを実行する。
  - PostgreSQL: GitHub Actions の `services` で起動し、`make migrate-up` でマイグレーションを適用する。
  - バックエンド: `go run ./cmd/server` で起動する。
  - フロントエンド: `apps/web` をビルドし `vite preview` で配信する。`/api` へのリクエストは `vite.config.ts` のproxy設定でバックエンドへ転送する（`preview.proxy` は `server.proxy` を引き継ぐ）。
  - Playwright の `webServer` 設定でバックエンドとフロントエンドの起動と待機を管理する。
- E2Eは専用ワークフロー `e2e-ci.yml` で実行する。実行コストを抑えるため、PRに `run-e2e` ラベルが付いている場合のみ実行する（全PRでの自動実行はしない）。バックエンド結合テストは既存の `backend-ci.yml` で引き続き全PRで実行する。

## 検討した選択肢

### 選択肢1: Playwright

#### 概要

Microsoft製のブラウザ自動化・E2Eテストフレームワーク。

#### メリット

- `webServer` 設定で複数プロセスの起動・ヘルスチェック待機をテスト設定に含められる
- 自動待機（auto-waiting）により不安定なテストを減らしやすい
- 失敗時のトレース・スクリーンショットをCIアーティファクトとして残せる
- ブラウザのインストールとCI向けの依存解決が `playwright install --with-deps` で完結する

#### デメリット

- ブラウザバイナリのダウンロードでCI時間が増える（キャッシュで軽減可能）

### 選択肢2: Cypress

#### 概要

ブラウザ内でテストを実行するE2Eテストフレームワーク。

#### メリット

- テスト実行中のデバッグUIが充実している

#### デメリット

- 複数タブ・複数オリジンの扱いに制約がある
- 並列実行が有償機能（Cypress Cloud）に依存しやすい
- バックエンド・フロントエンドの起動管理をテスト設定の外（ワークフローのシェル）で行う必要がある

### 選択肢3: Vitest Browser Mode

#### 概要

既存のVitestでブラウザ上のテストを実行する機能。

#### メリット

- 既存のテストツールチェーンと統一できる

#### デメリット

- コンポーネントテスト向けであり、複数プロセスを起動してのシステム全体のシナリオテストを想定していない

## 決定理由

- バックエンドとフロントエンドを起動してシナリオを流す用途に対し、`webServer` 設定でプロセス管理まで完結できるPlaywrightが最も構成が単純になる。
- `apps/web` から分離することで、Web本体のビルド・lint・依存関係にE2E用の依存（ブラウザ・テストランナー）を混ぜず、`web-ci.yml` の対象パスにも影響させない。
- `vite preview` + proxy にすることで、ブラウザからは同一オリジンとなり、CORSやCookie設定をE2E専用に変更する必要がない。

## 結果

### 良い影響

- 画面・API・DBを通した回帰を、PRごとに自動で検出できる
- E2E専用の依存が `apps/e2e` に閉じる

### 悪い影響

- 実行時にDB・Go・Node・ブラウザのセットアップが走り、CI時間が増える
- ラベル起動のため、ラベルを付け忘れたPRではE2Eが実行されず、回帰を見逃す可能性がある（必須チェックにもできない）
- E2Eのシナリオ追加に伴い、CIの実行時間とメンテナンスコストが増える
