# ADR-031: フロントエンドコンポーネントライブラリ（Base UI への変更）

- ステータス: 承認済
- 本ADRは [ADR-015](./ADR-015-frontend-component-library.md) を置き換える

## コンテキスト

ADR-015でコンポーネントライブラリとしてshadcn/ui（Tailwind CSS + Radix UI）を採用した。その後、以下の状況変化により再検討が必要になった。

- **Base UI v1 正式リリース（2025年）**: MUI チームが開発するヘッドレス UI ライブラリの安定版がリリースされ、Radix UI と同等のアクセシビリティ・カスタマイズ性を持ちながら、より一貫した API 設計と活発なメンテナンスが見込めるようになった
- **shadcn/ui の「コピーペースト」モデルとの不整合**: shadcn/ui はコンポーネントソースをプロジェクトに直接コピーする設計だが、`packages/ui` パッケージでラッパーを管理する現アーキテクチャ（ADR-002 モノレポ）では、npm パッケージとして依存関係を持つ方が変更管理がシンプル

ADR-015の主目的（カスタマイズ性・アクセシビリティ・TypeScript対応・Tailwind CSSとの統合）は維持しつつ、採用するライブラリをBase UIへ変更する。

## スコープ外

- カレンダー描画専用ライブラリ（FullCalendar、react-big-calendar等）の選定は詳細設計時に別途決定する（ADR-027で決定済）
- CSS処理系（Tailwind CSS等）の選定はBase UI + 自前ラッパー採用の前提として本ADRに含む
- アイコンライブラリの選定は詳細設計時に別途決定する
- フォーム管理ライブラリ（React Hook Form等）の選定は詳細設計時に別途決定する

## 決定

コンポーネントライブラリとして **Base UI + Tailwind CSS**（自前ラッパー）を採用する。`@base-ui/react` のプリミティブを `packages/ui` でラップし、`cva`（class-variance-authority）によるバリアントスタイリングと組み合わせる。

### コンポーネントの実装ルール

元の「shadcn/ui の CLI でソースをコピー」方式に代わり、以下のルールを採用する。

- `@base-ui/react/[component]` のプリミティブをラップして `packages/ui/src/` に配置する
- `className` prop は外部に公開しない（variant/size prop のみ）
- スタイリングは `cva`（class-variance-authority）+ Tailwind CSS で行う

## 検討した選択肢

### 選択肢1: shadcn/uiを継続（現状維持）

#### 概要

ADR-015の決定を維持し、Radix UIベースのshadcn/uiを使い続ける。

#### メリット

- 既に導入済みのため移行コストがない
- Radix UIの実績とコミュニティ規模が大きい

#### デメリット

- コンポーネントソースをプロジェクトに直接コピーする設計のため、`packages/ui` でラッパーを一元管理する現アーキテクチャと噛み合わず、Radix UIやTailwind CSSのアップデート追従が手動作業になる
- Radix UIからBase UIへの移行が今後発生する場合、導入が進むほど移行コストが増す

### 選択肢2: Base UI へ移行

#### 概要

shadcn/uiが内部で利用しているRadix UIを、MUIチームが開発するヘッドレスUIライブラリ Base UI に置き換える。`packages/ui` でプリミティブをラップし、npmパッケージとして依存関係を持つ。

#### メリット

- npm パッケージとして依存関係を持つため、`packages/ui` での一元管理とバージョンアップが容易
- 全コンポーネントで一貫した Props パターン（`data-slot`・`data-[state]` 属性・`render` prop）を持ち、独自ラッパーとの統合コストが低い
- ダイアログ・ドロップダウン・ポップオーバー等のインタラクティブコンポーネントにおいてキーボードナビゲーション・WAI-ARIAが標準で組み込まれており、Radix UI と同等水準のアクセシビリティを達成している
- `cva` + Tailwind CSS でバリアントスタイリングを行い、月ビュー・週ビュー・タイムライン等の独自UIにも対応できる
- `packages/ui` でラッパーを一元管理することで、Base UI 固有の API を Adapter 層に閉じ込めやすく、ADR-001 の狙いと整合する

#### デメリット

- Base UI のバージョンアップ時に API 変更が生じた場合、`packages/ui` のラッパー側での追従が必要
- DataGrid 等のエンタープライズ向けコンポーネントは Base UI に含まれず、必要になった場合は自前実装または別途ライブラリ選定が必要
- Tailwind CSS の習熟が前提となるため、チームメンバーへの学習コストが生じる

## 決定理由

- **変更管理のシンプルさ**: Base UI は npm パッケージとして依存関係を持つため、shadcn/ui の「ソースコードをプロジェクトに直接コピー」方式と異なり、`packages/ui` での一元管理とバージョンアップが容易
- **API の一貫性**: Base UI は全コンポーネントで一貫した Props パターン（`data-slot`・`data-[state]` 属性・`render` prop）を持ち、独自ラッパーとの統合コストが低い
- **アクセシビリティ**: Base UI はダイアログ・ドロップダウン・ポップオーバー等のインタラクティブコンポーネントにおいてキーボードナビゲーション・WAI-ARIAが標準で組み込まれており、Radix UI と同等水準を達成している
- **カスタマイズ性**: `cva`（class-variance-authority）+ Tailwind CSS でバリアントスタイリングを行い、月ビュー・週ビュー・タイムライン等の独自UIにも対応できる
- **Clean Architectureとの整合**: `packages/ui` でラッパーを一元管理することで、Base UI 固有の API を Adapter 層に閉じ込めやすく、ADR-001 の狙いと整合する

MUIとAnt Designはコンポーネントの種類は豊富だが、カレンダー固有のカスタマイズコストとバンドルサイズで劣るため見送る（ADR-015での評価を維持）。Chakra UIはアクセシビリティの水準は高いが、v3の安定性蓄積中の状況とTailwind CSSとの二重管理リスクから劣ると判断する（ADR-015での評価を維持）。

## 結果

### 良い影響

- Base UI を npm パッケージとして依存関係を持つため、バージョン管理がシンプルでアップデートの追従が容易
- Base UI のアクセシビリティプリミティブ（キーボード操作・ARIA）が標準で組み込まれ、個別対応のコストを削減できる
- `cva` + Tailwind CSS による一貫したバリアントスタイリングで、デザインシステムの統一性を維持しながら独自UIを構築できる
- `packages/ui` でラッパーを一元管理するため、Adapter 層に外部ライブラリの API が漏れるリスクを最小化できる（ADR-001 と整合）

### 悪い影響

- Base UI のバージョンアップ時に API 変更が生じた場合、`packages/ui` のラッパー側での追従が必要
- DataGrid 等のエンタープライズ向けコンポーネントは Base UI に含まれず、必要になった場合は自前実装または別途ライブラリ選定が必要
- Tailwind CSS の習熟が前提となるため、チームメンバーへの学習コストが生じる
