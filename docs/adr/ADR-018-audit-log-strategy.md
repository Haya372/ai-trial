# ADR-018: 監査ログ設計方針

- ステータス: 承認済

## コンテキスト

SPEC-001（ユーザー認証仕様）の設計中に、認証イベント（ログイン・ログアウト・サインアップ）の監査ログをどのテーブルで管理するかを決定する必要が生じた。将来的にはカレンダーイベント操作・共有設定変更など複数ドメインにわたる監査ログが追加される見込みであり、初期設計が全ドメインの監査ログ方針に影響する。

監査ログに求められる要件は以下の通り。

- いつ・誰が・何をしたかを記録できること
- 複数ドメインにまたがる横断的な監査クエリが可能であること
- ドメイン追加時のスキーマ管理コストが低いこと

## スコープ外

- 監査ログの保持期間・アーカイブポリシー
- 監査ログのアクセス制御（閲覧権限の設計）
- ログの可視化・検索UIの設計
- ADR-014（オブザーバビリティ方針）で定義したアプリケーションログとの連携

## 決定

**共通 `audit_logs` テーブル**を採用する。`entity_type`（対象ドメイン）と `entity_id`（対象エンティティのID）で全ドメインの監査イベントを一元管理し、ドメイン固有の属性は `metadata`（JSONB）カラムで表現する。

テーブル定義の基本構造は以下の通り。

```sql
CREATE TABLE audit_logs (
    id          UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    entity_type TEXT        NOT NULL,  -- 例: 'user', 'event', 'share'
    entity_id   UUID        NOT NULL,
    action      TEXT        NOT NULL,  -- 例: 'signup', 'login', 'logout'
    actor_id    UUID,                  -- 操作を行ったユーザー（システム操作の場合はNULL）
    metadata    JSONB,                 -- ドメイン固有の補足情報
    occurred_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

## 検討した選択肢

### 選択肢1: 共通 `audit_logs` テーブル（`entity_type` + `entity_id`）

#### 概要

全ドメインの監査イベントを1つのテーブルで管理する。各レコードに `entity_type`・`entity_id`・`action`・`actor_id`・`metadata`（JSONB）・`occurred_at` を持ち、ドメイン固有の属性は `metadata` に格納する。

#### メリット

- テーブル数が少なくシンプルで、スキーマ管理コストが低い
- 新ドメイン追加時にマイグレーション不要（`entity_type` の値を増やすだけ）
- 複数ドメインにまたがる横断的な監査クエリが1テーブルで完結する
- `occurred_at` によるタイムライン全体の時系列ソートが容易

#### デメリット

- ドメイン固有の属性をJSONBで表現するためDBレベルの型安全性が低い
- テーブルが肥大化した場合、`entity_type` によるパーティショニングが必要になる可能性がある
- `entity_type` の取りうる値がDB制約で表現できず、アプリケーション層での管理が必要

### 選択肢2: ドメインごとの個別テーブル（`user_audit_logs`, `event_audit_logs` 等）

#### 概要

各ドメインに専用の監査ログテーブルを作成する（例: `user_audit_logs`、`event_audit_logs`）。各テーブルにはそのドメイン固有のカラムを定義できる。

#### メリット

- ドメイン固有の属性をカラムとして明示でき、DBレベルでNOT NULL・型制約を表現できる
- ドメイン単位のクエリがシンプルになり、テーブルが小さいため検索が高速
- テーブル肥大化のリスクをドメイン単位で分散できる

#### デメリット

- ドメイン追加のたびにマイグレーションが必要でスキーマ管理コストが高い
- 複数ドメインにまたがる横断的な監査クエリにUNIONまたはJOINが必要で、クエリが複雑になる
- PRD-002〜009で追加予定のドメインが多く、テーブル数が増大するリスクがある

### 選択肢3: Event Sourcing

#### 概要

全ての状態変化をイベントとして記録するアーキテクチャパターン。イベントストアが監査ログを兼ねる構成。

#### メリット

- 任意の時点の状態を再現できる（完全な変更履歴）
- イベント駆動設計と親和性が高く、CQRSパターンと組み合わせやすい

#### デメリット

- 実装の複雑さが大幅に増し、ADR-001のClean Architectureのレイヤー設計との整合を保つ設計コストが高い
- 現プロジェクトの規模・フェーズに対して過剰設計であり、開発速度を低下させる
- チームのEvent Sourcing経験を前提とするため、学習コストが高い

## 決定理由

- **スキーマ管理コストの最小化**: PRD-002〜009のドメインが追加されるたびに監査テーブルを増やす選択肢2は、将来のスキーマ管理コストが高い。現フェーズでは共通テーブルによるシンプルな構造を優先する
- **横断クエリの容易さ**: 複数ドメインにまたがる監査クエリ（特定ユーザーの全操作履歴等）は共通テーブルの方が1クエリで完結する。選択肢2ではUNIONが必要になり複雑度が増す
- **ドメイン固有属性への対応**: JSONBの `metadata` カラムにより、ドメイン固有の補足情報を柔軟に格納できる。PostgreSQLのJSONB演算子を使えばメタデータ内の特定フィールドへのフィルタリングも可能で、実用上の問題は限定的
- **Event Sourcing の排除**: 認証・カレンダー管理のユースケースではイベントの再生による状態復元が必要な場面がなく、過剰設計になる。ADR-001のClean Architectureへの影響も大きいため採用しない

## 結果

### 良い影響

- 単一テーブルへの書き込みで全ドメインの監査ログを記録でき、アプリケーション層の実装がシンプルになる
- 新ドメインの監査ログを追加する際、スキーマ変更なしに `entity_type` の値を増やすだけで対応できる
- `actor_id`・`entity_type`・`occurred_at` のインデックス設計により、ユーザー別・ドメイン別・期間別の典型的な監査クエリを効率的に実行できる

### 悪い影響

- `entity_type` の取りうる値をアプリケーション層（定数・enum等）で管理する必要があり、DB制約で強制できない
- 長期運用でテーブルが肥大化した場合、`entity_type` によるパーティショニングへの移行が必要になる可能性がある
