# ADR-010: DBマイグレーションツール

- ステータス: 承認済

## コンテキスト

ADR-003でGoを、ADR-008でPostgreSQLを採用した。これを前提に、DBスキーマの継続的な変更を管理するマイグレーションツールを選定する。

本プロジェクトは開発初期からリリース後まで、ユーザー・予定・タグ・共有リンク等のスキーマ変更を継続的に管理する必要がある。マイグレーションツールの選定にあたっては、以下の観点で評価する必要がある。

- GoプロジェクトへのCLI・ライブラリ統合のしやすさ（アプリ起動時実行 / CIから実行 / 開発者ローカル実行のいずれにも対応できるか）
- マイグレーションファイルの形式（SQL vs Go）と、レビュー・Git管理のしやすさ
- ロールバック対応（down マイグレーションの表現力）
- CI/CDパイプラインとの統合のしやすさ

候補としてgolang-migrate、goose、Atlasを検討する。

## スコープ外

- スキーマ変更のレビュー・承認プロセスは運用設計時に決定する
- 本番環境でのマイグレーション実行タイミング（デプロイ前 / アプリ起動時等）は運用設計時に決定する
- 大規模テーブルのオンラインスキーマ変更（gh-ost等）は本ADRの対象外
- シードデータ投入の仕組みは本ADRの対象外
- テスト用DBのスキーマ準備方法は品質保証設計時に決定する

## 決定

DBマイグレーションツールとして **golang-migrate**（`github.com/golang-migrate/migrate/v4`）を採用する。マイグレーションファイルは素のSQL（up/down）で管理する。

## 検討した選択肢

### 選択肢1: golang-migrate

#### 概要

Goで書かれたマイグレーションツール。CLI・Goライブラリの両方で利用でき、素のSQLファイル（`{version}_{name}.up.sql` / `{version}_{name}.down.sql`）でマイグレーションを管理する。PostgreSQL・MySQL・SQLite等多数のDBに対応。

#### メリット

- **CLI・ライブラリの両対応**: CIパイプライン・開発者ローカルではCLIから実行し、必要ならアプリ起動時にGoライブラリから実行できる。運用形態を選ばない
- **素のSQLファイル**: マイグレーションが純粋なSQLで書かれるため、DBAや非Go開発者もレビューでき、Git上のdiffが読みやすい
- **バージョン管理の明快さ**: `{version}_{name}.up.sql` / `{version}_{name}.down.sql` の命名規則により、Git管理・レビューが素直
- **ロールバック対応**: `down` マイグレーションを明示的に書くことでロールバック可能
- **Docker公式イメージ**: CLIのDockerイメージが公式提供されており、CI/CDパイプラインでの統合が容易
- **エコシステム成熟度**: 長期にわたり広く利用されており、実運用ノウハウが豊富

#### デメリット

- `down` マイグレーションを常に書く運用ルールが必要で、down忘れが発生しやすい（レビュー観点で担保する必要がある）
- 素のSQLのため、条件分岐や動的なマイグレーションはGoで別途スクリプトを書く必要がある（ただし本プロジェクトでは想定されない）
- マイグレーションの依存関係やロールバックの整合性チェックはAtlasほど強力ではない

### 選択肢2: goose

#### 概要

Pressly社が開発するGo向けマイグレーションツール。SQLファイルとGoファイルの両方でマイグレーションを書ける柔軟性を持つ。

#### メリット

- SQLファイル・Goファイル両対応で、複雑なマイグレーションをGoで書ける柔軟性がある
- CLI・ライブラリ両対応
- 単一バイナリで動作し、導入が簡単
- コミュニティが活発で、Go開発者の間で人気

#### デメリット

- SQLファイル形式は golang-migrate と類似だが、up/down を1ファイルにアノテーション（`-- +goose Up` / `-- +goose Down`）で分ける形式で、golang-migrateの2ファイル形式に比べてGit差分が読みにくい場面がある
- Goファイル形式のマイグレーションを許容すると、レビュー時にビジネスロジックが混入するリスクがある（規約整備でカバーする必要がある）
- Docker公式イメージの整備状況・普及度でgolang-migrateにやや劣る

### 選択肢3: Atlas

#### 概要

Ariga社が開発するモダンなスキーマ管理ツール。DSL（HCL）またはSQLでスキーマを宣言的に記述し、差分から自動的にマイグレーションを生成する。スキーマ差分検出・依存関係チェック等の機能を持つ。

#### メリット

- スキーマを宣言的に記述し、差分からマイグレーションを自動生成する（宣言的マイグレーション）
- スキーマ変更の依存関係チェック・破壊的変更の検出などが強力
- CI連携機能が組み込まれており、PR上でのスキーマdiffレビューを支援
- モダンな設計で、活発に開発されている

#### デメリット

- HCLベースのDSLを学ぶ必要があり、素のSQLに比べて学習コストが高い
- 宣言的アプローチは強力だが、複雑なマイグレーション（データ移行を伴うスキーマ変更等）では手続き的な記述が必要になり、ツールの想定から外れる場面がある
- コミュニティ・エコシステムの成熟度がgolang-migrate/gooseに劣る（比較的新しいツール）
- 一部の高度機能（CI連携等）が有償プラン前提となる場合がある
- 素のSQLで管理する場合と比較して、Atlas固有の記法・ツールチェーンへの依存が生じる

## 決定理由

- **CLI・ライブラリ両対応の柔軟性**: golang-migrateはCLIとGoライブラリの両方で利用でき、CIパイプライン・開発者ローカル・（必要なら）アプリ起動時のいずれにも対応できる。運用形態を将来変更する余地がある
- **素のSQLファイルの明快さ**: マイグレーションが純粋なSQLで書かれるため、Git上のdiffが読みやすくレビューしやすい。DBAや非Go開発者もレビューに参加できる
- **up/down 2ファイル分離**: golang-migrateの `.up.sql` / `.down.sql` 2ファイル形式は、gooseのアノテーション形式に比べてGit差分が明確で、変更内容が視覚的に把握しやすい
- **PostgreSQL固有機能への対応**: 素のSQLで書くため、ADR-008で採用予定の `tstzrange` 型・JSONB・GiSTインデックス等の固有機能を制約なく利用できる
- **CI/CD統合の容易さ**: 公式Dockerイメージがあり、CIパイプラインでのマイグレーション実行が単純に組み込める
- **エコシステム成熟度**: 長期にわたる利用実績と豊富な運用ノウハウがあり、トラブル時の情報も充実している
- **学習コストの低さ**: 素のSQLだけで完結するため、Atlasのような独自DSL学習が不要

gooseはGoファイル形式の柔軟性が魅力だが、SQL/Go混在によるレビュー難度の上昇と、golang-migrateに比べたDocker統合の整備状況を考慮して見送る。Atlasは宣言的アプローチが強力だが、独自DSLの学習コストと本プロジェクト規模での機能過多、および比較的新しいツールとしてのエコシステム成熟度の懸念から見送る。

## 結果

### 良い影響

- 素のSQLファイルでマイグレーションが管理でき、Git上のdiffが読みやすくレビューしやすい
- CLI・Goライブラリ両対応により、CI/開発者ローカル/（必要なら）アプリ起動時のいずれでも実行できる
- 公式Dockerイメージにより、CI/CDパイプラインへの統合が単純
- PostgreSQL固有機能（ADR-008の `tstzrange` / JSONB / GiST等）を素のSQLで制約なく記述できる
- スキーマ変更履歴がSQLファイルとしてGitに残るため、レビュー・監査・ロールバック検討がしやすい

### 悪い影響

- `down` マイグレーションを常に書く運用ルールが必要で、down忘れを防ぐレビュー観点を整備する必要がある
- 破壊的スキーマ変更の自動検出などAtlasのような支援機能はなく、レビューで担保する必要がある
- マイグレーションファイルの命名規則（`{version}_{name}.up.sql` / `{version}_{name}.down.sql`）をチームで統一する必要がある
- 動的・条件分岐が必要な複雑なデータ移行は素のSQLでは表現しにくく、別途Goスクリプトを書く必要がある場合がある（本プロジェクトでは当面想定されない）
