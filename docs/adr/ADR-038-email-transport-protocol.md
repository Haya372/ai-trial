# ADR-038: メール通知の送信方式

- ステータス: 提案中

## コンテキスト

PRD-010 のメール通知基盤では、アプリケーションがユーザーの登録メールアドレスへ通知メールを送る必要がある。
どの送信サービス（マネージドメール配信サービス・自前のSMTPリレー等）を本番で使うかはインフラ選定と一体で、現時点では確定していない。

送信サービスごとに（a）クライアントライブラリ、（b）接続プロトコル、（c）SPF・DKIM・DMARCの設定方法、（d）バウンス通知の受信経路が異なる。
送信サービスを選定する前にアプリケーション実装を進めるため、「アプリケーション側で何を前提にメール送信を実装するか」を本ADRで決める。

選定観点:

- 送信サービスを特定しないままアプリケーション実装を進められること
- ローカル開発・テストで本番と同じインターフェースを検証できること
- 単体テストで送信処理をスタブに差し替えられること
- ADR-001 の Dependency Rule を守り、ドメイン層・ユースケース層が送信サービスの詳細に依存しないこと

## スコープ外

- 本番で使う送信サービス（具体ベンダー）の選定
- SPF・DKIM・DMARC のDNS設定方法
- バウンス通知の受信方式（[ADR-041](./ADR-041-bounce-webhook-auth.md)）
- 非同期送信・再送の実装方式（[ADR-039](./ADR-039-email-async-outbox.md)）
- `docker-compose.yml` などローカル環境の構成ファイルへの反映（実装 Issue で扱う）

## 決定

1. アプリケーションは **SMTP** プロトコル経由でメールを送る
2. 送信は `EmailTransport` インターフェース（例: `Send(ctx, msg) (messageID string, err error)`）経由で行う。本番の実装として SMTP クライアント（例: `net/smtp`、`github.com/wneessen/go-mail` 等のSMTPに閉じたライブラリ）を注入し、テストではスタブを注入する
3. ローカル開発・テストでは Mailpit（SMTPサーバー + HTTP UI でメールをキャプチャするツール）を SMTP の送り先として使う
4. 本番で使う送信サービスはインフラ選定時に決める。選定後は `EmailTransport` の本番実装がどのSMTPエンドポイントへ接続するかを設定で差し替えるだけで切り替えられる

## 検討した選択肢

### 選択肢1: SMTPプロトコル + EmailTransport 抽象（採用）

#### 概要

アプリケーションから送信サービスへの接続プロトコルは SMTP に固定する。送信処理はユースケース層が持つ `EmailTransport` インターフェースに依存し、Infrastructure 層に SMTP クライアントを使った実装を置く。ローカルでは Mailpit を SMTP の送り先として使い、本番では送信サービスの SMTP エンドポイントへ接続する。

#### メリット

- SMTP はほぼ全てのメール送信サービスが提供する最大公約数のプロトコルで、送信サービスの選定を後ろ倒しできる
- `EmailTransport` インターフェースによりユースケース層が送信サービスに依存せず、ADR-001 の Dependency Rule を保てる
- テストでは `EmailTransport` のスタブを注入でき、実際の送信を行わずに送信パスの挙動を検証できる
- ローカル・CI で Mailpit を使い、本番と同じ SMTP プロトコルで送信動作を検証できる
- 送信サービスが変わっても SMTP に閉じている限り、アプリケーション側のコード変更は接続設定だけで済む

#### デメリット

- SMTP で提供されない機能（送信サービスの API 経由で取得する統計・テンプレート管理機能など）はこの抽象では使えない。必要になった時点で `EmailTransport` の拡張または別の抽象で対応する
- バウンス通知は SMTP の応答で得られない範囲があり、別経路（Webhook）で受ける必要がある

### 選択肢2: 送信サービスの HTTP API/SDK を直接利用する

#### 概要

送信サービス（SaaS）の HTTP API または公式 SDK をアプリケーションから直接呼ぶ。

#### メリット

- 送信サービス固有の機能（テンプレート管理・統計 API・バウンス取得 API など）を全て利用できる
- SMTP より認証・エラー情報が豊富で、障害調査がしやすい場合がある

#### デメリット

- 送信サービスを特定しない現時点では実装できない
- SDK に依存するとベンダーロックインが強くなり、送信サービス変更時の変更範囲が広がる
- テスト時に SDK のモックを用意する必要があり、SMTP サーバー（Mailpit）を立てる方法と比べて検証粒度が落ちる

### 選択肢3: SMTP を使うが抽象化レイヤーを置かず `net/smtp` を各所から呼ぶ

#### 概要

ユースケース層が直接 `net/smtp` などの標準 SMTP クライアントを呼ぶ。

#### メリット

- インターフェース定義や実装注入の定型コードが不要

#### デメリット

- ADR-001 の Dependency Rule に違反する（ユースケース層が送信ライブラリに直接依存する）
- 単体テストで送信処理を差し替えられない
- 送信サービスが SMTP 以外へ変わる場合に全呼び出し箇所を変更する必要がある

## 決定理由

- **送信サービス選定の後ろ倒し**: SMTP はどの送信サービスでも提供される最大公約数のプロトコル。送信サービスを特定しない前提で実装を進めるには SMTP が最適
- **Dependency Rule との整合**: `EmailTransport` インターフェースをユースケース層に置き、Infrastructure 層に実装を注入することで、ADR-001 の方針を守れる
- **ローカル検証の容易性**: Mailpit を使えば本番と同じ SMTP プロトコルで送信動作を検証でき、ローカル・CI での統合テストが現実的に書ける
- **ベンダーロックの最小化**: 選択肢2（SDK 直接利用）に比べて、送信サービスを切り替えるときの影響範囲が接続設定に限定される

## 結果

### 良い影響

- 送信サービスの選定を本機能の実装と切り離して進められる
- 送信サービスを切り替える場合、`EmailTransport` の本番実装の接続設定を差し替えるだけで済む
- テスト・ローカル開発では Mailpit で実送信せずに送信パスを検証できる

### 悪い影響

- 送信サービス固有の機能（配信統計の API 取得等）は SMTP の範囲内では使えない。必要になった時点で `EmailTransport` の拡張または別経路の追加で対応する
- バウンス通知は SMTP では受け取れないため、別の受信経路（[ADR-041](./ADR-041-bounce-webhook-auth.md)）が必要
