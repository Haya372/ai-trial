# ADR-023: OpenAPIスキーマ管理ツールの採用（Redocly CLI）

- ステータス: 承認済

## コンテキスト

ADR-016でOpenAPI 3.1によるスキーマ駆動開発を採用し、スキーマファイルを `packages/schema/` で管理することを決定した。スキーマファイルはエンドポイント・コンポーネントごとに複数ファイルへ分割して管理するため、以下の3つの操作が必要になる。

1. **リント**: スキーマの記述ミスや規約違反を自動検出する
2. **バンドル**: 複数ファイルを `$ref` 解決してコード生成用の単一ファイルに結合する
3. **スキーマビューア**: 開発中にAPIドキュメントをブラウザで確認する

これらをどのツールで担うかを決定する必要がある。

## スコープ外

- OpenAPIスキーマの記述ルール・リントルールの詳細設定（`redocly.yaml` で管理）
- フロントエンド・バックエンドのコード生成ツール選定（ADR-016で決定済み）
- CI/CDへのリント統合方法

## 決定

OpenAPIスキーマの**リント・バンドル・スキーマビューア**の3つの役割を **Redocly CLI** で統一して担う。

## 検討した選択肢

### 選択肢1: Redocly CLI（採用）

#### 概要

`@redocly/cli` をインストールし、`redocly lint`・`redocly bundle`・`redocly preview-docs` コマンドでリント・バンドル・ビューアをすべて賄う。リントルールは `redocly.yaml` で設定する。

#### メリット

- リント・バンドル・ビューアを1ツールで担えるため、依存パッケージと設定ファイルが最小化される
- `$ref` をまたいだファイル分割構成を正確に解析してバンドルできる
- `preview-docs` が生成するUIはRedocベースで見やすく、開発中のスキーマ確認に適している
- `redocly.yaml` でリントルールを宣言的に設定でき、チーム内で統一できる

#### デメリット

- Redocly社のツールに依存するため、ライセンスや将来の方針変更のリスクがある
- バンドル・ビューア機能は一般的なOpenAPIツールにも存在するため、差別化が少ない

### 選択肢2: Spectral + swagger-ui-express + custom bundler

#### 概要

リントに **Spectral**（OAS向けのオープンスタンダードなリンター）、ビューアに **Swagger UI**、バンドルに **@apidevtools/swagger-parser** または **openapi-merge** を使う。

#### メリット

- 各ツールがそれぞれの役割に特化しており、置き換えが容易
- Spectralはルールセットのエコシステムが豊富で、カスタムルールも書きやすい

#### デメリット

- 3つの別々のツールとその設定ファイルを管理する必要があり、セットアップコストが高い
- ツール間でスキーマの解釈が微妙に異なる場合に不整合が生じうる
- Swagger UIのローカル起動には別途サーバー設定が必要

### 選択肢3: リント・ビューアなし + 手動バンドル

#### 概要

専用ツールを導入せず、スキーマの正しさはコード生成（oapi-codegen・orval）のエラーで確認する。バンドルはスクリプトで実装する。スキーマの内容確認はYAMLを直接読む。

#### メリット

- ツール依存がなく、構成がシンプル

#### デメリット

- コード生成時のエラーメッセージはスキーマの問題箇所を特定しにくく、デバッグコストが高い
- 規約（`operationId` 必須・未使用コンポーネント禁止など）をツールで強制できない
- スキーマの内容確認にブラウザUIがなく、YAMLを直接読む必要があるため開発体験が低下する

## 決定理由

- **役割の統一**: リント・バンドル・ビューアを1ツールで担えることで、依存パッケージと設定ファイルが最小になる。Spectralを使う選択肢2は3ツール管理になるため採用しない
- **バンドルの正確性**: Redocly CLIの `bundle` コマンドは `$ref` をまたいだ複雑なファイル分割を正確に処理できる。orvalの入力として渡す `dist/openapi.yaml` の生成に使うため、信頼性が重要
- **スキーマ品質の担保**: コード生成エラーに頼る選択肢3ではエラー箇所の特定が難しく、スキーマ品質を維持しにくい。宣言的なリントルールで `operationId` 必須・未使用コンポーネント禁止を強制することで、コード生成前に問題を検出できる

## 結果

### 良い影響

- `redocly lint` がCIに組み込めるため、スキーマの記述ミスをコード生成前に検出できる
- `redocly preview-docs` により、開発中にAPIドキュメントをブラウザで即座に確認できる
- `redocly bundle` で生成した `dist/openapi.yaml` をorval・oapi-codegenの入力として使うことで、分割ファイル管理とコード生成を両立できる
- 1つの `redocly.yaml` でリントルールを一元管理できるため、設定の見通しが良い

### 悪い影響

- Redocly CLI 1ツールへの依存が生まれるため、ツールが廃止・有料化された場合は移行コストが発生する
- `redocly.yaml` のルール設定はRedocly固有の記述形式であり、別のリンターへの移行時に設定を書き直す必要がある
