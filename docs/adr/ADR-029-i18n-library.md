# ADR-029: i18nライブラリ選定

- ステータス: 承認済

## コンテキスト

`apps/web`（ADR-005 / ADR-006 で決定した React + Vite + TypeScript の SPA）はカレンダー機能・認証機能・イベント管理機能に日本語文言をハードコードしている。今後の多言語展開に備え、翻訳リソース経由で文言を扱う i18n 基盤を導入する（Issue #206）。

このADRでは、`apps/web` に導入する i18n ライブラリを1つ確定する。

前提となる技術的な条件は以下のとおり。

- SPA 構成であり、Next.js のような RSC 前提のライブラリは選定対象外（ADR-005 参照）
- ADR-015 で採用した `@repo/ui`（Base UI ベースの自前ラッパー）はどのライブラリの API にも依存していない
- Zod（ADR-021）が入力バリデーションで使われており、Zod スキーマ内の日本語メッセージも将来的に i18n 化する必要がある
- `apps/web/src/features/{auth,calendar,event}/` のフィーチャー単位ディレクトリ構成が既に確立している

## スコープ外

- リソースファイルの配置構造・言語検出方針・型安全化の実装方針など、ライブラリ選定以外の設計判断
- 個別文言の翻訳リソースへの移行（Issue #207・#208・#209 で機能単位に実施）
- 言語切り替えUI（ユーザー向けメニュー等）の実装
- サーバー側（`apps/backend`）の多言語対応
- 動的リソース分割・遅延ロード方針（初期は静的import + フル同梱で開始する）

## 決定

`react-i18next` + `i18next`（コア）+ `i18next-browser-languagedetector` の3パッケージを採用する。

| パッケージ | 役割 |
|---|---|
| `i18next` | i18n コアランタイム（リソース管理・キー解決・補間・複数形処理） |
| `react-i18next` | React バインディング（`useTranslation` フック・`Trans` コンポーネント） |
| `i18next-browser-languagedetector` | ブラウザの言語検出とlocalStorage永続化 |

## 検討した選択肢

### 選択肢1: react-i18next（本決定）

#### 概要

i18next（フレームワーク非依存の i18n コアランタイム）と、そのReact用バインディング `react-i18next` の組み合わせ。React エコシステムで事実上の標準として最も広く採用されている。

補間構文はデフォルトで `{{var}}` 形式。名前空間（namespace）機能で翻訳リソースを分割できる。TypeScript の module augmentation でリソース型を注入し、キーをコンパイル時に検証できる。

#### メリット

- Reactの i18n ライブラリとして最も広く採用されており、学習リソース・実装事例・トラブルシューティング情報が豊富
- 名前空間機能により、既存の `features/{auth,calendar,event}` ディレクトリ構成と対応する形でリソースを分割でき、後続 Issue #207-#209 の作業単位と自然に一致する
- TypeScript の module augmentation でリソース型を注入することで、`t('auth:login.title')` のようなキー参照をコンパイル時に検証でき、追加のコード生成ステップが不要
- 補間・複数形処理・Intl API を経由した日付/数値フォーマットを標準サポートしており、Zod スキーマの動的メッセージ（例: 「パスワードは8文字以上で入力してください」）にも対応できる
- 静的import・遅延ロード・HTTPバックエンド・localStorage永続化などのプラグインが揃っており、初期は静的importで始めて要求が変わってから拡張する漸進的移行が可能
- react-i18next の `initReactI18next` プラグインはランタイムに約10KB追加するのみで、SPA のバンドルサイズへの影響が小さい

#### デメリット

- i18next のコアは他候補（LinguiJS のコンパイル済み出力等）より若干大きい（gzip後 約15KB）が、SPA のバンドル全体から見れば無視できる範囲
- キーベース（文字列で参照する）方式のため、キー名のタイプミスは module augmentation の型検査に頼る必要があり、macros ベースの LinguiJS ほど「文言をコード上で自然に書ける」わけではない

### 選択肢2: LinguiJS (@lingui/react)

#### 概要

Babel/SWC マクロで JSX 上に `<Trans>Hello, {name}!</Trans>` のように直接文言を書けるライブラリ。ビルド時にキーとカタログを自動生成する。ICU MessageFormat を採用しており、複数形・性別・選択肢分岐が明示的に書ける。

#### メリット

- JSX 上に自然言語で文言を書けるため、ソースコードの可読性が高く、初回の i18n 化にあたって文言をそのまま「日本語→キー」に置換する手間が少ない
- ICU MessageFormat により、複数形などの言語差を型で強制しやすい
- ビルド時に未翻訳キーを検出でき、CI ゲートに組み込みやすい

#### デメリット

- Babel/SWC マクロに依存するため、Vite のプラグイン設定・ビルドチェーンにマクロを組み込む必要がある。ADR-006 で採用した Vite のシンプルな構成に追加設定を持ち込む
- コミュニティは活発だが react-i18next に比べて事例が少なく、トラブルシューティング時に情報が見つけづらい
- macros ベースの API は、Zod スキーマ内のメッセージ（JSX 外の純粋なJS/TS 文字列）で使うと `msg` テンプレートリテラル + `i18n._()` のような別 API に切り替える必要があり、ペイン境界を跨いだ整合性を維持するコストが高い

### 選択肢3: FormatJS (react-intl)

#### 概要

Yahoo（現 FormatJS チーム）が開発する ICU MessageFormat ベースのライブラリ。`<FormattedMessage id="..." defaultMessage="..." />` の形で文言を宣言し、`intl.formatMessage()` で JS 内から参照する。

#### メリット

- ICU MessageFormat の実装が最も成熟しており、Intl API との統合が厚い（日付・数値・相対時刻・リスト書式など）
- `defaultMessage` を JSX 内に併記することで、キーと英語原文をコロケーションできる
- 大規模プロダクトでの採用実績が多い

#### デメリット

- API 表面が広く、`<FormattedMessage>`・`useIntl`・`defineMessages`・extractor など学習コストが高い
- ICU MessageFormat の複数形・選択肢分岐構文は強力だが、現状のプロジェクト規模（1言語・小さめの文言セット）に対しては明らかにオーバースペック
- `useIntl` の返す `intl` オブジェクト経由でしか型情報が取得できず、キーの型安全化には別途 typed-intl のような追加ツールが必要

### 選択肢4: Paraglide.js (@inlang/paraglide-js)

#### 概要

inlang エコシステムのコンパイル型ライブラリ。ビルド時にリソースを Tree-shakeable な純粋関数（`m.hello_world()`）に変換し、ランタイムはほぼゼロ。TypeScript の型を静的生成する。

#### メリット

- ランタイムオーバーヘッドがほぼゼロで、Tree-shaking により未使用キーがバンドルから除外される
- 生成された関数は完全に型安全で、キー名を IDE 補完・go-to-definition できる
- SDK の設計がモダンで、Vite プラグインが公式提供されている

#### デメリット

- 2024-2025 に急速に発展したライブラリで、react-i18next と比べて実装事例・学習リソースが圧倒的に少ない
- inlang CLI ・Sherlock IDE 拡張などの周辺ツールが前提となる場面があり、独自エコシステムへのロックインを招く
- 名前空間・遅延ロード・複数形処理などの機能設計が react-i18next と大きく異なり、将来の要件変化への追従性が読みにくい

## 決定理由

- **学習資産と実装事例の厚み**: React + i18n の標準的組み合わせとして react-i18next が最も広く使われており、後続 Issue #207-#209 で複数機能を並列に i18n 化する際、実装者が参照できる事例・アンチパターンが豊富。小規模チームでの導入・保守コストが最も低い
- **既存構成との整合**: 名前空間ベースのリソース分割が `features/{auth,calendar,event}` ディレクトリと自然に対応する。ライブラリ側の思想を既存の実装単位に押し付けずに済む
- **型安全化のコスト対効果**: module augmentation による型安全化は追加ビルドステップなしで実現でき、コンパイル時にキーのタイプミスを検出できる。LinguiJS や Paraglide.js のようなビルド時変換に依存しないため、ADR-006 の Vite 構成に追加のバンドル時変換を挿入せずに済む
- **Zod との整合**: Zod スキーマ内のバリデーションメッセージも `t()` 関数の返り値で表現できる（後続 Issue #207 で採用パターンを確立予定）。文字列キー参照方式のため、JSX 内外を問わず同じ API で扱える。JSX 前提の LinguiJS より境界を跨いだ扱いが単純
- **要件過剰の回避**: FormatJS の ICU MessageFormat・Paraglide.js のコンパイル出力はいずれも「1言語からスタートし、必要に応じて2言語目を追加する」という現状の要件に対して機能過剰。YAGNI の観点から、必要最小限で始められる react-i18next を選ぶ

## 結果

### 良い影響

- Issue #207-#209 の文言移行作業は、フィーチャーごとの名前空間ファイル（`locales/ja/{auth,calendar,event}.json`）に文言を追加してコンポーネントを `t()` 呼び出しに置き換えるだけで進められる。作業単位が明確で並列化しやすい
- module augmentation による型安全化により、翻訳キーの typo をコンパイル時に検出できる。実装者は IDE 補完で存在するキーを確認できる
- 追加のビルドチェーン設定が不要で、ADR-006 で採用した Vite の設定に手を入れずに導入できる
- 将来 `en` を本格導入する際に、`i18next-http-backend` などのプラグインへ切り替えるだけで遅延ロード対応に移行できる。段階的拡張の余地が広い

### 悪い影響

- キーベース参照のため、コンポーネント上のテキストは `t('auth:login.title')` のような文字列参照になり、そのままでは何の文言か視認しづらい。IDE の go-to-definition・型補完・命名規約（後述の設計ドキュメントで規定）で補う必要がある
- ランタイム型（module augmentation）に依存するため、JSON リソース側の変更が TS の型再評価に反映されるまで一瞬遅延する場合がある（実行時は問題なし・保存後の再ビルドで解消）
- ライブラリ標準では未翻訳キーを警告するのみで例外化しないため、リリース前チェックとして key parity 検査を別途スクリプト化する必要がある（設計ドキュメントで方針を規定）
