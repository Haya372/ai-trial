# ADR-032: `/metrics` エンドポイントの Bearer トークン認証

- ステータス: 承認済

## コンテキスト

`/metrics` は Prometheus 形式の運用メトリクス（リクエスト数・レイテンシ分布・ルートパターン等）を返す。内部構造を推測する材料になるため、未認証の外部アクセスから保護する必要がある。

他のエンドポイントはセッションCookieによる認証（ADR-020）を使うが、`/metrics` を取得するのは Prometheus などのスクレイパーであり、ログインしてセッションCookieを保持する仕組みを持たない。そのため既存の `RequireAuth` をそのまま適用できない。

## スコープ外

- ネットワークレベルの制限（リバースプロキシ・セキュリティグループ等）の構築
- TLS 終端
- トークンのローテーション自動化・シークレット管理基盤の選定
- レートリミット

## 決定

`/metrics` にのみ、環境変数 `METRICS_BEARER_TOKEN` の値と照合する Bearer トークン認証ミドルウェア `RequireMetricsToken` を適用する。

- `Authorization: Bearer <token>` ヘッダーを検証する。比較は `crypto/subtle.ConstantTimeCompare` による定数時間比較で行う
- ヘッダーが無い・形式不正・トークン不一致の場合は 401（`UNAUTHORIZED`）を返し、`WWW-Authenticate: Bearer` ヘッダーを付ける
- `METRICS_BEARER_TOKEN` が未設定（空文字）の場合は全リクエストを拒否する（fail closed）。設定漏れで無認証公開になることを防ぐ
- ミドルウェアは `interface/middleware` に置き、トークンは `container.go` で環境変数から読み込んで渡す

## 検討した選択肢

### 選択肢1: 既存の `RequireAuth` を適用する

#### 概要

`/metrics` にセッションCookie認証を付ける。

#### メリット

- 新しい仕組みが不要

#### デメリット

- Prometheus はログインできず、スクレイプが成立しない
- 一般ユーザーのセッションで運用メトリクスが見えてしまう

### 選択肢2: 専用の静的 Bearer トークン認証

#### 概要

環境変数で与えたトークンを `Authorization: Bearer` で検証する。

#### メリット

- Prometheus の `authorization` 設定でそのまま対応できる
- アプリ内で完結し、デプロイ環境のネットワーク構成に依存しない
- 実装が小さい

#### デメリット

- 環境変数とシークレットの管理が増える
- トークンの定期的な更新は手動運用になる

### 選択肢3: 別ポートの内部リスナーに分離する

#### 概要

`/metrics` を内部ネットワーク専用ポートで公開する。

#### メリット

- アプリ層の認証が不要で、公開ポートから完全に切り離せる

#### デメリット

- サーバー起動処理とシャットダウン処理の変更が大きい
- ネットワーク分離が前提になり、環境ごとの構成に依存する

## 決定理由

スクレイパーから取得できる認証方式という要件を満たしつつ、最小の変更で閉じられるのは選択肢2。ネットワーク制限は環境依存のため、アプリ側の認証を必須とし、ネットワーク制限は多層防御として運用ガイドラインで推奨する。

## 結果

### 良い影響

- `/metrics` が未認証の外部アクセスから保護される
- 設定漏れ時も公開されない（fail closed）

### 悪い影響

- 本番・開発環境で `METRICS_BEARER_TOKEN` の設定と Prometheus 側のトークン設定が必要になる
- トークン漏洩時は手動で差し替える必要がある
